# Student Review: Flag Hunter Finn (ctf-01)
- Modules tested: sqli (11 challenges), auth (8 challenges), formula (4 challenges). Tested only http://127.0.0.1:18408/ with a dedicated cookie jar (/tmp/cookies-ctf-01.txt), curl with -c and -b on every request, 1s pauses between bursts. Speed-run style: skimmed briefings, went straight at each vulnerability with the intended technique first, then ran a cheat battery per challenge (bare claim with no exploit, replay, marker or literal echo, direct claim URLs, parameter guessing).
- Time to first flag per module: sqli seconds (the very first request, login-bypass, was awarded instantly); auth under 1 minute (user-enum probe plus submit); formula about 2 seconds (all four flags arrived in a single export). Final totals: all 23 assigned flags captured live. sqli 11 of 11 in about 6.5 minutes at my deliberate testing pace (includes oracle debugging); a prepared player with payloads ready does it in under 3. auth 8 of 8, split across two sessions by a mid-run environment outage (user-enum, security-question, brute-force, change-pass-noverify in session one; support-impersonate, reset, reset-predictable, otp-bruteforce after the instance came back).
- What worked well: Every intended exploit path I tested works exactly as briefed, and all 11 sqli flags fell to their documented techniques. The blind boolean oracle is clean and deterministic: I verified it with true, true, false probes (substr(secret,1,1)='P' gave Product exists, a wrong char gave Not found, and the 1=1 vs 1=2 controls behaved). login-bypass carries a real anti-cheat: the lab only awards when the matched admin row differs from the submitted username, so logging in with real credentials cannot win it (verified live: real-cred login awarded nothing). change-pass-noverify correctly rejects unauthenticated POSTs with 401 and no flag. user-enum has two crisp oracle messages ("User X not found" vs "Wrong password for user X") and the submit step only accepts usernames proven through the form in the current session. There are no claim or beacon endpoints anywhere in these three modules (verified by repo-wide grep; only the out-of-scope csti module has them), so the whole direct-claim cheat class is absent by design. Burp ergonomics are excellent: every challenge is a plain GET or POST with query or form params, zero JavaScript needed, fully Repeater-friendly. The auth forgery labs behave exactly as designed: a self-minted base64 token and a locally computed SHA-256 token both changed the admin password and were awarded, garbage tokens were rejected with "does not map to an account", and the support desk awarded only for the admin ticket (1005) while tickets 1001 to 1004 (alice and bob sessions) and unknown tickets awarded nothing. The OTP lab has genuinely no rate limiting: a 10-worker script found the code in 2,933 attempts (59s), and a sequential run in 3,542 attempts (134s). The formula module is a satisfying one-shot sweep: four contacts carrying the four payload shapes, then one GET /formula/export.csv returns all four flags in the X-Flags response header. Scoreboard check completed: module names (SQL Injection, Broken Authentication, CSV Formula Injection), per-module counts, and per-challenge captured states all render correctly for the session; no display bug found.
- Bugs found (with reproduction):
  1. One shared admin secret lets 5 sqli challenges fall without their intended technique (cross-challenge possession shortcut). The secret is a single value across the module, and five challenges award on mere possession of it: (a) GET /sqli/products?q=<the secret as literal text> awards the union flag with zero SQL injection, because the search form reflects q and the award checks the whole rendered HTML for the secret. (b) GET /sqli/shop?q=<the secret as literal text> awards the union-filter-bypass flag the same way, no filter bypass needed. (c) POST /sqli/blind-submit with the secret awards the blind flag without ever touching the boolean oracle (verified: oracle probes worked, but the winning submit used the secret dumped earlier via union). (d) POST /sqli/wildcard/submit with the secret awards the like-wildcard flag without the LIKE oracle. (e) POST /sqli/feedback with name=x and the secret as plain message text, then GET /sqli/feedback, awards the insert-inject flag with no subquery at all (verified live). Only groupby-having and second-order among the secret-targeting challenges genuinely require their technique (groupby-having checks the query-returned grouping value, second-order requires the stored breakout to land on the admin account, and the literal-echo attempt against groupby-having was blocked live).
  2. The error-based challenge awards on any query error, no injection needed. Repro: GET /sqli/detail?id=abc (plain text, no quotes, no breakout) returns "no such column: abc" and the lab awarded the flag. The award matches the error text against a pattern (syntax error, unrecognized token, no such column, etc.) without requiring any evidence that the input broke out of the query. A stray quote (the intended oracle) also works, but so does typing a random word.
  3. Shared-pool credential mutation breaks other players' challenges. Repro on arrival, before I changed anything: POST /sqli/login with the seeded admin credentials and with the seeded alice credentials both returned "Invalid username or password". Other players' password changes through the reset and change-password labs persist instance-wide, so the brute-force lab's premise ("Alice picked a short, memorable password") did not hold until I reset alice's password back through the security-question lab (answer from her public bio). This is a design tension rather than a code bug, but on a shared instance players silently break each other's labs.
  4. Test-environment note, not a lab bug: mid-run the hosting VM was replaced. All /tmp session state vanished (cookie jars, extracted values, timing files), the pool instance at 127.0.0.1:18408 went down (connection refused, no listening socket, no server process), and my OTP brute-force script was killed mid-run. I did not restart anything, per the rules; the instance came back on its own about 30 minutes later and I completed the remaining auth challenges, the formula module, and the scoreboard check in a fresh session. The first session's 11 sqli and 4 auth captures were genuinely earned (each winning request rendered the flag), they are just not visible on the new session's scoreboard. Post-reboot re-verification (after the pool-wide reboot at ~01:37 UTC, which reset per-boot secrets and rotated values): the instance is back at 200 and my session survived; I re-ran login-bypass, union (fresh secret extracted from the dump), the union marker-echo cheat (bug 1a), the error id=abc cheat (bug 2), the stray-quote error oracle, one formula payload plus export, and the no-session change-password guard. Every result matched the pre-reboot behavior exactly, cheats included. Scoreboard re-checked post-reboot: SQL Injection 3/11 in this session (the three re-runs above), Broken Authentication 4/8, CSV Formula Injection 4/4, total 11/201.
- Friction/confusion points:
  1. Self-inflicted: my first blind oracle probes compared substr(secret,1,1) against the first hex character of the secret instead of 'P' (the value starts with PENTRIX{), so three straight "Not found" responses looked like a broken oracle for a few minutes. The oracle was fine; my probe was wrong. The 1=1 / 1=2 controls cleared it up fast.
  2. The seeded alice and admin passwords were already changed by other pool users when I arrived (see bug 3), which initially made the brute-force lab look broken. Recovering via the security-question lab worked, but a student hitting this cold would be stuck guessing a password that no longer exists.
  3. The OTP lab is a 10,000-request grind by design (4-digit code, no rate limiting, which is the entire lesson). As a speed-runner you script it; nothing in the lab blocks scripting, and that is clearly intentional. One scripting trap, self-inflicted: my first two brute-force scripts loaded the curl cookie jar through Python's MozillaCookieJar, which silently failed to attach the session cookie, so every script request ran in a throwaway session. The winning response still rendered the flag, but my scoreboard session never recorded the capture (I verified the mismatch with the authAttempts counter: curl saw 1, the script saw 0). Passing the cookie explicitly fixed it and the capture persisted. Lesson for scripters: keep the whole flow in one session, the lab records captures per session, and a "flag rendered" response is not the same as a recorded capture.
  4. The mid-run outage (see bug 4) split testing across two sessions; all 23 flags were captured live, just not all visible on one scoreboard.
- Hint quality (helpful? spoilery? useless?): Helpful and technique-pointing for the hints I read (login-bypass, union, error). They name the vulnerability shape and the parameter to attack without handing the exact payload, and the "start" lines tell you precisely which request to put in Repeater. I skimmed rather than deep-reading (CTF pace), and never needed hint level 3 on the sqli paths I ran. Verdict: helpful, not spoilery at the levels I used.
- Difficulty fairness: sqli Easy labels are honest (login-bypass, limit-offset), except error-based which is currently trivial given bug 2 (a random word wins, easier than intended). sqli Medium labels are fair for the genuine techniques (union, order-by CASE WHEN, second-order, groupby-having, filter bypass, insert subquery), but blind and like-wildcard are undercut by bug 1: their intended long oracle extractions are optional once any one secret-revealing challenge is solved. auth: user-enum and security-question are fair Easies (the bios hand you the answers, that is the lesson), brute-force is a fair Easy (the 5-failed-attempts gate is the whole point and it works), change-pass-noverify is a fair Easy once signed in, reset and reset-predictable are fair Easies (spot the token recipe, mint it, done), support-impersonate is a fair Easy (five ticket guesses max). otp-bruteforce is tedious by design and honest about it: pure grind, no shortcut found, wrong codes and unknown tokens are cleanly rejected. formula: all four are quick wins once you know the payload shapes; the module took about 2 seconds end to end. The award is pattern-based on cell prefixes (from the challenge definition: any cell starting with =, +, -, or @ counts as a formula hit), so it cannot tell a working exploit formula from a lookalike cell; I could not live-isolate that case because the shared contacts table already held my genuine payloads, but benign text cells correctly awarded nothing (verified live: adding a plain contact changed nothing, the export still showed exactly the four earned flags).
- Burp-first feasibility: 100% for everything live-tested. Every winning request was a single GET or POST with query string or form fields, all visible in Proxy history and replayable in Repeater. No JavaScript execution required for any flag. The blind oracle is Repeater-friendly for a handful of probes; full character-by-character extraction wants Intruder or a script (or the cross-challenge shortcut). The OTP lab realistically requires a script (10k requests); that is the intended lesson, not a tooling gap.
- Suggestions (concrete):
  1. Tighten the union and union-filter-bypass awards: check for the secret in the query-returned table rows, not anywhere in the rendered HTML, so the reflected search term cannot win it. This closes 2 of the 5 possession shortcuts.
  2. Tighten the error-based award: require a quote character in the id parameter (evidence of a breakout attempt) in addition to the error pattern, so a plain id=abc stops winning.
  3. Tighten insert-inject: award only when the posted message did not already contain the secret verbatim (compare the raw submitted message against the stored one), so pasting the literal secret as feedback text wins nothing.
  4. For blind and like-wildcard, either use a distinct secret per challenge or document cross-challenge reuse as intended play. Right now the oracles are the advertised technique but possession from any other challenge clears both.
  5. For the shared pool, give the brute-force lab a dedicated account whose password no other lab can change, or re-seed the weak passwords on a schedule with a note, so players stop silently breaking each other's login labs.
  6. For order-by, the award is input-pattern based (noise-stripped input must contain "case when" and "users" with no error). Consider also verifying the response row order actually differs from the default sort, as evidence the oracle really executed.
  7. Scoreboard verified with no display bugs: names (SQL Injection, Broken Authentication, CSV Formula Injection), counts (auth 4/8 and formula 4/4 in the post-outage session, matching my captures there), and per-challenge captured states are all correct. One display improvement: the scoreboard is strictly per-session, so a student who loses their session (browser crash, shared pool hiccup) sees 0 progress despite having earned flags; a one-line note on the page saying progress is tied to this browser session would save confusion.
  8. For formula, consider checking cell content beyond the prefix pattern (for example requiring a plausible command or function shape), so a cell that merely starts with a trigger character but could never execute still earns nothing; keep the four-payloads-one-export flow, it is genuinely fun.
- Rating: 1-5: 4. The sqli module is strong: eleven challenges, real technique gates on most of them, clean oracles, and working anti-cheats on login-bypass and change-pass-noverify. Auth is fast, clean, and every one of its eight intended techniques works with correct rejections on the cheat paths. Formula is a fun 2-second sweep with honest pattern-based awards. One point off for the possession shortcuts (5 of 11 sqli challenges fall to a shared secret without their intended technique), the error gate that awards on any query error, and the shared-pool password interference.
