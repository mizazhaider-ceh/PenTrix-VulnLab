# Student Review: Day-One Marco (beginner-04)

- Modules tested:
  - Host Header Injection (hostheader): all 5 challenges, flags awarded for all 5. Password Reset Poisoning (rewrote the Host header on the forgot-password POST, carried the token from the poisoned email link to the attacker collector), Cache Poisoning via Host (planted a page rendered under an attacker Host, then re-requested the same path with the normal Host), SSRF via Host Header (Host set to the loopback internal agent address named on the challenge page), Forwarded-Host Header Poisoning (X-Forwarded-Host, and again with X-Host-Override), Absolute Continue URL (login POST with a poisoned Host, flag arrived in the body of the 302 response).
  - OAuth Flaws (oauth): all 8 challenges, flags awarded for all 8. Redirect URI Prefix Bypass (authorized with http://app.pentrix.lab.evil.com/cb and approved), Authorization Code Leaked in Server Log (read alice's code out of the public IdP log, exchanged it while logged in as bob), Login CSRF (minted a code as bob, opened the callback link in a second session where the IdP user was alice; the victim's client session became bob), Implicit Flow Token in URL Fragment (ran the implicit flow as alice, then presented her token to userinfo from bob's session), Scope Tampering (authorized as bob with scope=admin, exchanged the code, read the admin data endpoint), Client Secret in Public JavaScript (read the secret out of the public app.js bundle, exchanged my own code directly at the token endpoint with it), Authorization Code Replay (exchanged the same code twice; the flag arrived in the second token response), PKCE Downgrade (authorized with a code_challenge, exchanged with no code_verifier at all).
  - Everything was done with curl standing in for Burp Repeater (edit header, resend) and curl jars standing in for browser sessions (/tmp/cookies-beginner-04.txt as the main session, a second jar for the "bob" / attacker session), with sleeps between bursts. A third fresh jar was used for the cache-poison cheat test and a forced-session-cookie test on Absolute Continue URL.

- What worked well:
  - The Host Header module briefing is the best orientation I have seen so far: it names the attack (`curl -H "Host: evil.com"`), names the collector page, and says a flag is awarded only when the poisoned value flows through the real code path. I never had to guess what "done" looks like.
  - The password reset pages play both sides for you: the "Email sent (lab view)" page shows the exact link the app built, so a beginner can SEE the attacker domain sitting in the link before doing anything clever. The collector page also explains itself ("It awards the flag when a reset token that was issued under a poisoned host arrives here").
  - The SSRF challenge page prints the server-side fetch target it is about to use. Watching the target change when I edited the Host header taught the whole lesson in one screen.
  - The OAuth module index explains the flow in 30 seconds, lists every endpoint in a table, and shows my two sessions (IdP user and client user) at the top. The "Your two hats" framing is exactly what a beginner needs, because half the OAuth labs are about which session you are wearing.
  - Hint ladders render as three collapsed rungs (Nudge, Technique, Explicit) with click-to-reveal. Nothing spoils itself by accident; I only opened rung 3 when I was truly stuck.
  - The OAuth consent screen lists redirect_uri, response_type, scope, state, and code_challenge in plain text before you approve. Seeing the parameters spelled out made the tampering labs feel fair.
  - Scoreboard display checked for both modules: Host Header Injection shows all 5 rows with correct names, difficulty pills (Medium, Hard, Medium, Easy, Easy), and per-row Captured / Not captured states that matched what I had actually earned on each session; OAuth Flaws shows all 8 rows with correct names and difficulties (Medium, Easy, Medium, Medium, Easy, Easy, Medium, Medium) and correct captured states on both of my sessions (2/8 on the main session, 6/8 on the bob session, exactly the flags each session earned). Module counts and percentages agreed with the rows. No display bug found in names, counts, or captured states. One expected behavior worth knowing: progress is per browser session, so my flags were split across my two "browsers" and neither scoreboard view showed all 13.

- Bugs found (with reproduction):
  - BUG 1 (cache-poison flag awarded with no exploit, shared cache): the portal cache is shared by every visitor of this instance. Reproduction: session A poisons GET /hostheader/app with Host set to an attacker domain. Then a brand new session B (fresh cookie jar, never sent a poisoned request) simply opens GET /hostheader/app with the normal Host. The lab awarded the flag to session B and its scoreboard showed 1/201, even though B did nothing but load the page. After visiting /hostheader/app/clear and reloading normally, no flag was awarded (correct). On a shared instance, a beginner can be handed this flag by another student's work, and a student who genuinely poisons the cache cannot tell whether their own poison or someone else's earned it.
  - BUG 2 (stale port in every OAuth Repeater template): six of the eight OAuth challenge pages print `Host: localhost:3000` in their copy-paste Repeater blocks (code-leak, implicit, scope-upgrade three times, secret-in-js twice, code-replay, pkce-skip), the scope-upgrade page also prints a full authorize URL starting with http://localhost:3000, and the code-leak "Starting point" text tells you to open the log at http://localhost:3000/oauth/idp/log. This instance does not listen on port 3000, so a beginner who pastes these blocks into Burp Repeater verbatim gets a connection failure and no explanation. Reproduction: copy the token exchange block from the code-replay page into Repeater exactly as printed and send it: connection refused, because the Host line names a port nothing is listening on. The Host Header module pages are clean (they use relative paths), which made the contrast obvious.
  - OBSERVATION (one code can earn two challenge flags): I exchanged a PKCE-bound code with no verifier (the lab awarded the PKCE Downgrade flag, correct), then sent the same code a second time with a wrong verifier. The second response carried the Authorization Code Replay flag. Both weaknesses are real, so this may be intended, but a strict student could finish two challenges with one authorization flow and never run the replay lab's own steps.
  - MINOR (replay re-shows flags): re-running a completed exploit (for example, bringing a second poisoned token to the collector, or logging in again with a poisoned Host) re-displays the flag box. The scoreboard does not double count (verified: counts stayed correct), so this is cosmetic and learner-friendly, not a score cheat.

- Friction/confusion points:
  - The implicit flow lab nearly lost me. The intended path needs a real browser (the token lives in a URL fragment and a script records it into the simulated browser history). Working from curl I could not follow steps 3 and 4 as written; I only finished because the approval page prints the full redirect target, token included, so I could lift the token from there and present it to userinfo from the second session. A beginner without that shortcut would be stuck at "paste it after the #" without understanding what a fragment is.
  - Hint 1 on the implicit lab is a riddle, not a nudge: "Which in-lab page records the victim's full URL, fragment included, and through which Burp Proxy history entry does that record travel?" I read it three times and learned nothing. Hint 2 (look for the POST to the history-log endpoint in Proxy history) is the one that actually teaches.
  - Two-session labs (Login CSRF, code-leak, implicit) are where a day-one student gets lost on mechanics, not concepts: which login belongs to which session, and how to make Repeater act "as alice" while the browser is bob. The no-state page's attack plan explains this well ("Open that link in a second session where the IdP user is alice"), but the module index does not warn you up front that you will need two separate browser sessions or cookie jars.
  - Absolute Continue URL plus curl equals a vanishing scoreboard tick: the flag text appears in the login response, but when I checked the scoreboard the challenge still showed Not captured. Cause: tools that key cookies to the Host header (curl does) attach the session to the spoofed host, so the award lands on a throwaway session. Reproduction: POST /hostheader/login with a poisoned Host and a fresh cookie jar, flag awarded in the response; GET /scoreboard with the same jar shows 0/201 and the challenge as Not captured. Repeating the POST with my real session cookie forced into the request made the scoreboard flip to Captured immediately. In Burp Repeater this works naturally because you keep your browser's Cookie header, but a curl-first student will think the lab ate their flag.
  - The redirect-bypass challenge page hands you the finished attacker URI in a labeled payload block, with a note explaining why it works. I never had to invent anything; I just clicked through. Kind for a first OAuth lab, but it teaches "follow the recipe" rather than "spot the prefix check".
  - Small copy friction on the IdP log: the arrow in each log line renders as an escaped entity in the page source, so searching the raw page for "->" finds nothing. Harmless in the browser, confusing if you are grepping like I was.
  - Cache Poisoning is labeled Hard, but with the module briefing plus Hint 1 ("Poison first, victim second") it took me two requests. The Hard label seems to price in the concept, not the work.

- Hint quality (helpful? spoilery? useless?):
  - host-reset-poison: helpful. Hint 2 (rewrite the Host header of the forgot-password POST in Repeater, watch where the lab email link points) unlocked it. Hint 3 is nearly a full walkthrough, appropriately behind the last rung.
  - host-cache-poison: helpful. Hint 1 alone ("whatever your first request's Host header says gets baked into the cached copy") plus the note printed on the portal page was enough. Unlocked at Hint 1.
  - host-ssrf: helpful. The challenge page itself names the internal agent's address, and Hint 2 (edit the Host header so the server's fetch reaches that agent) unlocked it.
  - host-xforwarded: helpful. Hint 1 (the app trusts X-Forwarded-Host; can you add that header in Repeater?) is the whole insight. Unlocked at Hint 1.
  - host-abs-url: helpful. The login page's own tip (poison the Host header, log in, read the 302 Location) plus Hint 1 was enough. The demo credentials printed on the page (alice / alice123) remove the only other way to get stuck. Unlocked at Hint 1.
  - redirect-bypass: spoilery. The challenge page prints the exact attacker redirect_uri before you ever open a hint, so the ladder adds nothing. Unlocked at Hint 0, by the page itself.
  - code-leak: helpful. The page is a walkthrough (open the log, find the authorize line, exchange as someone else) and Hint 3 states the one rule that matters: exchanging your own code earns nothing. Unlocked at Hint 1 plus the page steps.
  - no-state: helpful. The page's three-step attack plan is clearer than the hints; Hint 3 adds the useful Repeater detail (replay the callback link in a session whose IdP user is alice). Unlocked by the page, confirmed by Hint 3.
  - implicit: mixed, weakest ladder of the thirteen. Hint 1 useless (a riddle, see friction). Hint 2 helpful (find the history-log POST in Proxy history, lift the token). Hint 3 helpful (present the token to userinfo from a session that is not alice's). Unlocked at Hint 2.
  - scope-upgrade: helpful, borderline spoilery. The page lists every step with the exact payloads, including the scope=admin authorize link as a button. Unlocked at Hint 1; honestly the page alone sufficed.
  - secret-in-js: helpful. Hint 1 (fetch the public bundle in Repeater and read it) plus the page steps cover everything. Unlocked at Hint 1.
  - code-replay: helpful and fair. Hint 1 asks the right question (are codes single-use?), Hint 2 (resend the identical exchange and compare) unlocked it. The page note about pasting your session cookie into Repeater is the detail a beginner actually needs.
  - pkce-skip: helpful. The page explains PKCE in one paragraph and gives the challenge value; Hint 2 (replay the token POST with no code_verifier at all) unlocked it.

- Difficulty fairness:
  - hostheader: Forwarded-Host (Easy) and Absolute Continue URL (Easy) are fairly rated. Password Reset Poisoning (Medium) and SSRF via Host Header (Medium) are fair: one idea each, but you have to assemble two or three steps. Cache Poisoning via Host is labeled Hard and felt like a Medium at most once Hint 1 was read; nothing about the execution is hard.
  - oauth: code-leak, scope-upgrade, and secret-in-js (all Easy) are fair Easys, mostly because their pages walk you through. Redirect URI Prefix Bypass (Medium) plays like an Easy because the page supplies the payload. Login CSRF, implicit, code-replay, and PKCE Downgrade (all Medium) are fair Mediums: the concepts are one step deeper and the two-session or replay mechanics earn the rating. Implicit is the hardest of the eight in practice, purely because of the browser-fragment simulation.

- Burp-first feasibility:
  - All 13 challenges are doable in Burp Community with Proxy and Repeater only. No Intruder, no extensions, no scripting needed anywhere.
  - hostheader: every challenge is a single header edit in Repeater (Host, X-Forwarded-Host, or X-Host-Override) plus, for the two reset labs, one browser visit to the collector. Cache poisoning is two Repeater sends of the same path. SSRF is one Repeater send. Absolute Continue URL is one Repeater POST where you read the 302 Location in the response; keep your browser's Cookie header in the request and the scoreboard tick lands on your real session.
  - oauth: redirect-bypass, scope-upgrade, secret-in-js, and pkce-skip are browser authorize/approve plus Repeater token exchanges. Code-leak is a browser read of the log plus one Repeater POST. Code-replay is the purest Repeater lab in the set (send, resend, compare). Login CSRF needs two sessions: two browser profiles, or one browser plus a Repeater tab carrying the other session's cookie, exactly what Hint 3 describes. Implicit is the only lab that truly needs the proxied browser, because the fragment handling and history recording happen in page JavaScript; Repeater then finishes it at userinfo.
  - Caveat that applies to all OAuth labs: the Repeater templates printed on the pages carry the stale port from Bug 2. A Burp-first student hits that before any of the intended lessons.

- Suggestions (concrete):
  - Fix the OAuth Repeater templates: replace every `Host: localhost:3000` and the http://localhost:3000 authorize URL with the lab's actual address, or print "Host: (leave as your lab address)" so the blocks survive any port. Same for the code-leak Starting point text that sends students to port 3000 for the log.
  - Cache poisoning: warn on the challenge page that the cache is shared by everyone on the instance, so a flag can appear from another student's poison; or key the award to the poisoned host value the visiting session itself planted earlier (for example, remember per session which host it poisoned and only award when the served entry matches). At minimum, add a line to the portal page: "If the links already point somewhere strange, someone poisoned this before you; clear the cache and plant your own."
  - Rewrite implicit Hint 1 as a plain nudge: "Fragments never reach the server, so the token cannot come to you in a request. The victim's browser writes the full URL somewhere readable. Where?" Keep the history-log detail in Hint 2, where it already works.
  - Add one line to the OAuth module index: "Labs 2, 3, and 4 need two separate sessions (two browsers, two profiles, or two cookie jars): one for the victim, one for the attacker." This is the single piece of setup knowledge every two-session lab assumes.
  - Add one line to the Absolute Continue URL page: "The scoreboard tick follows your session cookie. In Repeater, keep the Cookie header from your logged-in browser request, or the flag lands on a session you are not looking at."
  - Move the finished attacker redirect_uri on the redirect-bypass page behind Hint 3. The page already explains the prefix check well; let the student derive "trusted prefix plus attacker suffix" once before showing the string.
  - Decide whether one authorization code earning two flags (PKCE Downgrade, then Code Replay on the resend) is intended. If not, make the replay award require a code that was not already used to earn another token-endpoint flag.
  - Consider re-rating Cache Poisoning via Host from Hard to Medium, or make the Hard honest by removing the "cache key is the path only" confession from the portal page and letting Hint 2 carry it.

- Rating: 4
