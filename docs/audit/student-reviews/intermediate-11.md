# Student Review: Grinder Quinn (intermediate-11)
- Modules tested:
  - postMessage Flaws (postmsg): 5 challenges reviewed. The lab awarded the flag for 4 of 5 (no-check, data-xss, substring, csrf-action) via curl-simulated victim requests. For wildcard, the anti-cheat was verified (wrong token rejected) but the flag path itself could not be completed with curl alone in my setup, see the bugs section.
  - Server-Side Request Forgery (ssrf): all 9 challenges solved with curl (basic, bypass, ssrf-redirect, ssrf-userinfo, ssrf-hex-ip, ssrf-octal-ip, ssrf-zero-ip, ssrf-metadata, ssrf-file). The lab awarded the flag on every one.
  - Business Logic Flaws (bizlogic): all 8 challenges solved with curl (price tamper, negative quantity, coupon stacking, currency confusion, tampered refund, email change takeover, client-side OTP bypass, skipped checkout step). The lab awarded the flag on every one.
  - Scenario "Ghost in the CMS" (extra duty): COMPLETED end to end, post-reboot. Walked the full kill chain in order: stage 1 misconfig/git (reconstructed the repo over HTTP: HEAD, branch ref, object store, commit diff), stage 2 auth/reset-predictable (forged the admin reset token offline with sha256 of admin plus the printed salt, changed the admin password without ever requesting an admin reset), stage 3 upload/upload-double-ext (uploaded shell.svg.jpg carrying SVG markup; the viewer served it back as image/svg+xml, active content), stage 4 xss/stored (planted a stored guestbook payload, confirmed it renders raw on the guestbook page, then fired the collect beacon the payload would produce). All four stage flags captured in my session and the scenario completion flag was awarded on the scenario page. Final scoreboard: 25 of 201 (4 stage flags + 4 postmsg + 9 ssrf + 8 bizlogic; the scenario completion flag itself is not counted in the 201).
  - Verification note: the pool VM rebooted midway through this review, which reset per-boot state. Every module exploit and anti-cheat check above was re-run and re-verified live on the post-reboot instance, and every result held exactly. The scenario run was done entirely post-reboot, on fresh state.
- What worked well:
  - postmsg bare-claim protection is solid where it counts. Calling /postmsg/beacon with no token, a wrong token, or (for csrf-action) before any account deletion happened returned 400 and no flag was awarded, every time, both before and after the reboot.
  - postmsg replay protection works. Re-sending a beacon request that had just succeeded returned 400, so a captured beacon in Burp history cannot be farmed.
  - The csrf-action beacon is correctly gated on real lab state: the flag only landed after the delete POST actually ran in my session.
  - The claim-status endpoint (/postmsg/claim-status) reported captured state accurately after each solve.
  - SSRF fetchers behave exactly as briefed. The blocklist fetcher returned a clean 403 with a plain message ("Blocked: URL contains a forbidden host") for a direct 127.0.0.1 attempt, and every documented bypass technique (decimal IP, 0.0.0.0, redirect bounce, userinfo, hex, octal, metadata, file scheme) worked first try.
  - Fetching /ssrf/internal/secret directly in my own session awarded nothing: the flag only comes through the vulnerable fetchers, which is the right design.
  - bizlogic flows are smooth end to end. Balance and order state stayed consistent across challenges, and the email takeover chain (change email with no re-auth, request reset, use the reset link, set a new password) read like one believable story and awarded the flag at the end.
  - Hint ladders in all three modules follow the same honest pattern: level 1 nudges, level 2 teaches the technique, level 3 shows the payload shape. As an intermediate student I rarely needed level 3.
  - Scenario gating works exactly as promised. On first load, stage 1 was open with a challenge link and stages 2 to 4 were locked with no link shown. After each stage flag, exactly the next stage unlocked and gained its link (/misconfig#git, then /auth/sha-reset, then /upload#upload-double-ext, then /xss/guestbook). On completion the scenario flag banner appeared, and revisiting the scenario page re-showed the same flag so it can be re-copied.
  - Scenario narrative coherence is good: each stage briefing picks up the ghost story (slip in unseen, wear a face, plant a shell, haunt the page) and the technique in that stage matches the story beat. The four challenges connect into a believable chain instead of feeling like four random labs stapled together.
- Bugs found (with reproduction):
  - postmsg: the flag beacon can be claimed without any postMessage ever firing, which skips the entire skill the module teaches. Reproduction (no-check): GET /postmsg/no-check with a session cookie, read the per-session page token out of the inline script in the returned HTML, then GET /postmsg/beacon?v=no-check&d=no-check:anything&n=<token>. The lab awarded the flag. The same shape worked for data-xss and substring. For csrf-action: POST /postmsg/csrf-action/delete directly (no forged message, no iframe), then GET /postmsg/beacon?v=csrf-action&d=csrf-action:account-deleted, and the lab awarded the flag. The token binds the claim to "the victim page was loaded in this session", not to "the message handler ran", and the token sits in plain view in the page source, so the browser and Burp workflow is optional.
  - SSRF module index page gives away every answer. The "Quick links" list on /ssrf contains ready-made, one-click exploit URLs for all nine challenges, labeled plainly ("Fetch the internal secret via the open fetcher", "Bypass attempt: decimal loopback", "Userinfo trick vs the pentrix.lab allowlist", "Cloud metadata credentials", "file:///etc/passwd", and so on). A student can clear an "Advanced" module in under a minute by clicking down the list, no hints opened, nothing learned.
  - bizlogic challenge pages embed the finished exploit. The price-tamper page prints a complete Burp Repeater request with price already lowered to 1, and the refund page prints one with the refund amount already raised to 5000. Same spoiler class as the SSRF quick links, smaller scale.
  - SSRF fetcher placeholders and bizlogic sample requests reference the wrong port. The hex-ip form placeholder literally shows "http://0x7f.0.0.1:PORT/ssrf/internal/secret" (the word PORT), and the bizlogic Repeater samples show "Host: localhost:3000", while the shared instance actually runs on port 18406. Copy-pasting a sample verbatim sends the student to a dead address.
  - Minor: the bizlogic email-change endpoint answers a wrong field name with "Invalid email" (400). I sent newEmail instead of new_email and the error pointed at the address format, not the missing field, which sent me debugging the wrong thing for a minute.
  - Scenario stage 4 shares the postmsg-style shortcut: the stored-XSS flag beacon needs the page token rendered as window.__px on the guestbook page, so a curl-only student can read the token from the page source and fire /xss/collect directly without any browser executing the stored payload. The payload genuinely stores and renders raw (I verified that part), but the "a browser ran it" proof is, again, only "the page was loaded".
- Friction/confusion points:
  - The mid-session instance reboot wiped my captured flags and per-boot state. Re-running everything was fast and all results reproduced, but a student mid-sprint would lose progress with no warning. A visible "instance restarted" notice on the scoreboard would soften this.
  - postmsg wildcard: the per-session secret the beacon wants is printed into the victim page's own HTML source, so "intercept the broadcast with a listener" and "view source" are the same amount of work. The challenge still teaches the right lesson, but the capture step feels theatrical once you notice.
  - The postmsg module is browser-first by design (iframes, message events). That is fine, but the briefings promise you can watch the beacon in Burp Proxy history, and thanks to the token shortcut above, a lazy student never has to. The intended path and the shortest path diverge. Same for scenario stage 4: the last stage is the one that most needs a real browser, and the token shortcut is the only way through without one.
  - Scenario completion is easy to miss: the completion flag appears on the scenario page, not on the guestbook page where stage 4 finishes. I went back to /scenarios/ghost-in-the-cms and found it, but nothing on the final challenge page points you there.
  - Scenario story nit: the narrative says "haunt the front page", but the actual stage 4 target is the guestbook page, not a news front page. Small mismatch between the story text and the surface you attack.
  - The guestbook behind stage 4 is shared pool state, not per-student: other students' stored comments render on the same page. In a busy pool the page could fill with other people's payloads, which is confusing when you are checking whether yours rendered.
  - bizlogic: the OTP challenge's real code is compared inside the page's own JavaScript, which is the intended lesson, but it also means the "wrong code plus client says ok" path and the "read the real code" path are both one glance at the source away. Fair for the topic, just very fast.
  - No reset or "start over" affordance was obvious on the postmsg victim pages once a token was spent; replaying a lab means reloading the page for a fresh token, which I only understood after the first 400.
- Hint quality (helpful? spoilery? useless?):
  - The ladders themselves: helpful and well graded. Level 1 points at the right surface, level 2 names the technique, level 3 shows the payload shape without quite typing it. Good Burp anchoring throughout (Proxy history, Repeater, intercept).
  - The spoilery parts live outside the ladders: the SSRF quick links (full answers, always visible, no click-to-reveal) and the bizlogic pages' pre-filled Repeater samples (tampered values included). These undercut the ladders completely. A student who reads the page top to bottom is spoiled before ever opening a hint.
  - Scenario briefings: well judged. Each one states the goal and the flavor without handing over the payload; the real guidance lives in the linked challenge's ladder, which is where it belongs. Stage 2's challenge hint does print the full token recipe, but that is the challenge's own design (the page itself teaches the recipe), and the scenario briefing honestly says so.
  - Nothing useless found. Even the one-line hints on the module cards matched what the challenge actually required.
- Difficulty fairness:
  - postmsg: fair. no-check, data-xss, substring, csrf-action at Medium all felt Medium for an intermediate student; wildcard at Easy is right, it is meant to fire on page load.
  - ssrf: individual labels are mostly fair (userinfo and zero-ip at Easy, the IP-spelling family at Medium), but "bypass" at Hard is generous: the decimal-IP trick is one idea, closer to Medium. The module banner says Advanced, which the content does not support, especially with the quick links present. With the quick links removed it would be a solid intermediate module, still not Advanced.
  - bizlogic: fair overall. Price tamper and negative quantity at Easy are genuinely Easy. Currency confusion at Medium is soft (one parameter change: pay 50 JPY), coupon stacking at Medium is right because you have to read the page and add percentages past 100. Email takeover at Medium is the best calibrated challenge in the set: three linked steps, each simple, the chain is the lesson.
  - Scenario "Ghost in the CMS" at Intermediate: fair. Stage 2 (forging the token offline) is the only step that asks for a tool outside the browser, and the challenge page teaches the recipe before you need it. Stage order also teaches well: each stage is a different module family, so the chain doubles as a tour. Total time for an intermediate student: roughly 20 to 30 minutes, which feels right for the label.
- Burp-first feasibility:
  - ssrf and bizlogic: perfect Burp Community labs. Every exploit is a plain GET or form POST, fully Repeater-friendly, no JavaScript, no paid features needed. I reproduced everything with curl, which maps one to one onto Repeater.
  - postmsg: feasible with Burp Community as a passive proxy plus a normal browser, exactly as the briefings describe (watch the victim iframe load, fire the payload, find the beacon in Proxy history). Nothing needs Intruder or the scanner. The caveat is the token shortcut in the bugs section: Burp-first is possible but not enforced.
  - Scenario: Community-feasible. Stages 1 to 3 are pure HTTP (Repeater covers all of them; I did them with curl). Stage 4 is designed for a proxied browser, and that is the intended flow; without a browser it only completes via the token shortcut noted above.
- Suggestions (concrete):
  - Delete the SSRF "Quick links" payload list, or move those URLs behind hint level 3 so they cost the student the same as reading the ladder. Keep the fetcher forms; they are the lab.
  - On the bizlogic price-tamper and refund pages, keep the sample request shape but blank the tampered values (price=..., amount=...), so the page teaches the request format without pre-solving it.
  - For postmsg (and the xss collect beacon used in scenario stage 4), make the beacon depend on something that only exists after the handler or payload actually runs, not only on a token printed in the page. Alternatively, document openly in the briefing that source-reading is an accepted shortcut. Right now the design implies a guarantee it does not keep.
  - Fix the port references: put the real instance port (or a clear placeholder instruction) in the SSRF form placeholders and the bizlogic sample requests, so copy-paste works on the shared instance.
  - Change the bizlogic email 400 response to say the field is missing or malformed by name, so students debug the request, not the address.
  - Add a one-line note on postmsg victim pages that reloading the page issues a fresh token, so a spent token (400 on replay) does not read like a dead end.
  - Scenario: when the final stage flag lands, show a banner or link on the challenge page pointing back to the scenario page ("Return to Ghost in the CMS to claim your completion flag"). Right now the payoff is one navigation away and easy to miss.
  - Scenario: align the story wording with the target (guestbook, not front page), or rename the stage surface in the briefing so the narrative and the mechanics match.
  - Scenario: consider per-student or clearly labeled guestbook entries for stage 4, so a student can spot their own stored payload in a shared pool without wading through everyone else's.
  - Add an "instance restarted, progress reset" notice somewhere visible (scoreboard header is a good spot) so a pool reboot does not look like lost work.
- Rating: 4
