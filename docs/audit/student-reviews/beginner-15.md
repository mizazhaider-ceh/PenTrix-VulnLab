# Student Review: Day-One Ravi (beginner-15)
- Modules tested: JWT Attacks (/jwt: none-admin, weak-secret, kid-sqli, jku, alg-confusion, no-expiry, aud-bypass, kid-default), all 8 challenges exploited via curl against http://127.0.0.1:18405 with a dedicated cookie jar (/tmp/cookies-beginner-15.txt), simulating the Burp Repeater and Intruder flows the hints describe. Total 8 flags earned in JWT. Open Redirect (/redirect: double-slash, javascript-scheme, data-scheme, backslash, pollution): NOT exploited. I read the module briefing and all 5 hint ladders, but the shared pool instance went offline partway through my run (connection refused, nothing listening on the port) and never came back during the session. My instructions forbade booting or restarting any server, so the redirect challenges are untested and everything below about them is marked as briefing-only. No repo code was changed; only this review file was written.

- What worked well:
  - The JWT module page teaches the token format first (three base64url segments: header.payload.signature, what alg and kid mean, what the signature proves) in plain words before any attack steps, so I understood what I was breaking before I broke it.
  - Every challenge page shows a legitimate sample token first, so I always knew what "normal" looked like before forging anything.
  - none-admin: the page shows a sample unsigned token and says "Try changing the role". I hand-built a token with role admin and an empty signature segment, posted it, and the lab awarded the flag with a "Welcome, admin" page. A perfect first win for a day-one student.
  - Success and failure feedback is crisp everywhere: success shows "Welcome, admin" plus a flag card, and wrong keys or bad signatures get a plain HTTP 403. I never had to guess whether an attempt worked.
  - Every capture page includes a short "The fix" section with an OWASP link, so I learned the defense at the same moment as the attack (reject alg none, validate exp, validate aud, fail closed on missing kid, and so on).
  - jku is fully self-contained: the lab runs its own attacker key server at /jwt/attacker-keys where I registered a kid and secret, and the challenge page spells out the exact JWKS URL shape to point the jku header at. No external hosting needed, which is exactly right for a beginner.
  - kid-sqli: the challenge page prints the key lookup query shape itself, so the mechanism was visible before I exploited it. My injected kid made the lookup return a key of my choosing, I signed with that key, and the lab awarded the flag.
  - Cheat resistance was solid everywhere I probed, and I probed every challenge: empty token, garbage token, and a guest-role token on none-admin all failed; the unchanged signed guest token and an admin token signed with a wrong secret failed on weak-secret; the unchanged sample token and an injected kid with a wrong signing key (403) failed on kid-sqli; a jku token pointing at an unregistered kid and a token with no jku header at all both got 403 on jku; the unchanged RS256 guest token and an HS256 admin token signed with a random secret (403) failed on alg-confusion; a tampered-payload version of the leaked expired token got 403 on no-expiry; a tampered partner token got 403 on aud-bypass; a kid-less token signed with a wrong key got 403 on kid-default. I found no shortcut that awarded a flag without performing the actual exploit.
  - Open Redirect briefing (read only, not tested): the module page teaches one clean verification habit, run curl -i and read the Location header as the proof, and states a flag is awarded only when the evil destination is genuinely honored. That is a good beginner framing, but I could not verify any of it live.

- Bugs found (with reproduction):
  - Scoreboard did not reflect my captures. Reproduction: (1) fresh cookie jar, (2) exploit /jwt/none and note the "Flag captured, Saved to your scoreboard" banner, (3) keep exploiting with the same jar (8 captures total, each with the banner), (4) GET /scoreboard with the same jar. Expected: 8/201 with the JWT challenges marked Captured. Actual: 0/201 and "No flags captured yet". Mid-run, after 6 captures, an error page in the same session also showed the topbar counter as 1/201, so the counter was inconsistent as well as low. Caveat: I shared one jar file between curl and a small python HTTP client, so a session mix-up on my side is possible; but from the student's seat, the core progress feedback silently vanished even though every capture banner promised it was saved.
  - POST to the aud challenge page URL returns a 404. Reproduction: curl -X POST with a token field to http://127.0.0.1:18405/jwt/aud returns a "404 Lost in the lab?" page. The real submit endpoint is /jwt/aud/login, which the on-page form uses correctly. Every other JWT challenge posts to its own page URL, so a student who types the request by hand (or follows the module hint "submit the login form" without reading the form) hits a dead end that looks like a broken lab.
  - The RSA public key page (/jwt/confusion-pubkey) returns an HTML page, not plain key text, while the hints say to "open the RSA public key page and copy the PEM text". Copying from a rendered page is exactly how the byte-level problem in the friction section below happens.

- Friction/confusion points:
  - Every "Starting point" on the JWT module index page points at http://localhost:3000/... addresses (for example http://localhost:3000/jwt/none), but the lab actually runs on http://127.0.0.1:18405. A beginner copy-pasting the starting point lands on a dead address and has no way to know the port is wrong. The jku challenge page itself uses localhost:18405, so the two pages disagree with each other.
  - alg-confusion (Hard): my first correctly built HS256 token, signed with the public key text exactly as copied from the page, was rejected with 403. It only verified after I added a trailing newline to the end of the key text. Nothing on the page or in any hint mentions this, and a bare 403 cannot tell a beginner whether the alg, the kid, or the key bytes are wrong. I burned several attempts here and only solved it by changing one byte-level detail at a time.
  - weak-secret and kid-default both hinge on guessing a small secret, but no wordlist is provided or linked anywhere. The module page mentions node and jsonwebtoken are installed, yet a curl-first beginner has to invent candidate secrets unaided and write their own signing loop. I found the weak secret with a small offline candidate list and the default key on my second guess ("test" after "secret" failed); a student with different first guesses gets nothing but 403s and no sense of progress.
  - Registering a key on /jwt/attacker-keys took about 16 seconds to respond while every other request in the run answered in under a second. I nearly assumed the form had hung and was about to retry, which could have double-registered keys.
  - The bottom of the JWT module page repeats the line "Fix mode is not available for this module yet" once per challenge (8 times), which reads like leftover placeholder copy rather than information.
  - The aud challenge has two forms on one page (a token vending machine and the login form) and the module hint says "submit the login form" without naming its URL, which combined with the 404 above cost me a few confused minutes about which form and which address actually grade the exploit.

- Hint quality (helpful? spoilery? useless?):
  - none-admin: helpful, not spoilery. Rung 2 (decode the sample token to see the header and payload shape) is what unlocked it; rung 3 confirms the method. The challenge page text nearly gives it away, which is fine for the first challenge of a module.
  - no-expiry: helpful. Rung 1 alone is enough because the challenge is a single step; rung 3 ("It does not. Replay the leaked token as-is") states the answer outright, but there is nothing deeper to hide here.
  - weak-secret: helpful. Rung 1 ("a classic default, what are the usual suspects?") plus rung 2 (sign the same admin claims per candidate and sniper the tokens through Intruder, grepping for the success marker) is exactly the method I used. No rung names the secret. Unlocked at rung 2.
  - kid-sqli: helpful and the best ladder in the module. Rung 2 ("make the SELECT return a key of your own choosing") is the real insight, and rung 3 confirms the flow without printing a literal payload. Unlocked at rung 2.
  - jku: helpful, arguably over-documented: the challenge page itself, before any hint, describes the whole flow including the URL shape, so rung 1 alone would have sufficed. Not a complaint from a beginner, but the ladder adds little here.
  - alg-confusion: helpful on concept, incomplete in practice. Rung 3 correctly states the server uses its own public key bytes as the HMAC secret, and that unlocked the idea, but no rung mentions the exact byte handling (trailing newline) that actually decided success or 403 for me.
  - aud-bypass: helpful. Rung 2 (decode the partner token, notice aud says billing-service while the signature verifies under this app's key) teaches the real lesson. Unlocked at rung 2.
  - kid-default: the weakest ladder. Rung 1 is pure process (send the POST to Repeater), rung 2 is a riddle ("what tiny guessable key would a developer hardcode while testing?"), rung 3 just says a 403 means try the next guess. It works only because the key really is tiny; it teaches guessing stamina, not a technique.
  - Useless: none. Every hint I opened was accurate and pointed at the real mechanism, and the rungs are honestly graduated: nudge, technique, explicit.

- Difficulty fairness:
  - Easy (none-admin, no-expiry): fair. One idea each, quick wins that build confidence, exactly right at the front of the module.
  - Medium (weak-secret, kid-sqli, aud-bypass, kid-default): fair overall. kid-sqli is the best Medium (one real technique, visible mechanism, satisfying payoff). aud-bypass is fair once you read the payload. weak-secret and kid-default are luck-dependent: the difficulty is vocabulary, not skill.
  - Hard (jku, alg-confusion): jku felt easier than several Mediums because the lab hands you the attacker key server and the exact URL shape; I would swap its label with aud-bypass. alg-confusion is genuinely Hard, but part of its difficulty is the invisible trailing-newline detail rather than the concept, which is accidental difficulty, not designed difficulty.
  - Open Redirect difficulties (Easy and four Mediums per the briefing): not rated, the challenges could not be run.

- Burp-first feasibility:
  - All 8 JWT challenges are doable in Burp Community. Every flow is a single POST with one token field, which is pure Repeater work, plus offline token crafting (Burp Decoder for base64, any local JWT tool for signing). weak-secret and kid-default map to Intruder Sniper with a short payload list exactly as the hints describe, though Community Intruder is throttled, so a beginner may finish faster with the node one-liners the module page mentions. Nothing in the module needs a browser-only feature, a second origin, or a paid Burp feature.
  - In this run I had no live browser or Burp available, so I sent the identical requests with curl (same method, same fields, same session cookie jar); the requests the hints describe and the requests I sent match one to one.
  - Open Redirect: not verified. The briefing's own method (read the Location header) suggests Repeater-only feasibility, but the server was down and I will not claim feasibility I did not test.

- Suggestions (concrete):
  1. Fix the module index "Starting point" URLs to the address the lab actually serves on (they currently say localhost:3000; the lab answers on 127.0.0.1:18405), or drop the host and port and show paths only.
  2. On alg-confusion, either serve the public key as plain text so copy-paste is byte-exact, or add one line to rung 3: "copy the key exactly, including the final newline". This removes the accidental difficulty and keeps the Hard rating about the concept.
  3. Investigate the scoreboard mismatch: after in-session captures the scoreboard should show them, and if captures are bound to one exact session, say so on the capture card ("saved to this browser session") so a student is not told their progress was saved when it was not.
  4. Ship a tiny starter wordlist on the weak-secret and kid-default pages (ten or so classic defaults), so those challenges test the cracking and fallback techniques instead of vocabulary luck.
  5. Name the aud login endpoint (/jwt/aud/login) in the module-page hint text, since POSTing to the page URL returns 404, unlike every other challenge in the module.
  6. Speed up POST /jwt/attacker-keys/register, or add a "publishing your key" note, so a 16 second wait does not read as a hang.
  7. Replace the 8 repeated "Fix mode is not available for this module yet" lines on the module page with a single note.
  8. Re-run the Open Redirect module review when the pool instance is back: the five challenges (protocol-relative, javascript scheme, data scheme, backslash allowlist, parameter pollution) still need live exploitation, cheat tests, and hint grading.

- Rating: 4 (for the JWT module, which I tested end to end: clear teaching, honest hints, strong cheat resistance, held back by the wrong-port starting points, the PEM newline trap, and the scoreboard feedback problem. Open Redirect is not rated: the server was down for that half of the assignment, so I tested none of it.)
