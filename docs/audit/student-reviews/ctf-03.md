# Student Review: Shellcode Sam (ctf-03)
- Modules tested: api (5 challenges), csti (5 challenges), lfi (9 challenges), plus the full "Authentication Assassin" career path (11 steps). All captures re-verified on the live instance AFTER the second VM reboot (~02:47 UTC): api 5/5, csti 5/5, lfi 9/9, path 11/11, scoreboard reads 30/201 for my session. I never quote flag values in this file, only whether the lab awarded the flag.
- What worked well: Time-to-first-flag was seconds per module. API exposure: first-ever GET /api/users returns the flag in an X-Pentrix-Flag header (intended). CSTI: load the lab page, parse CSTI_NONCE, then GET /csti/beacon?v=basic&d=49&n=<nonce> awards the flag with zero template evaluation (worked for all 5 labs; constructor takes any non-empty d). LFI: all 9 fell to plain curl payloads. Path order is sensible: user enum, brute-force, reset flows, OTP, security question, fixation, predictable sessions, JWT kid, OAuth replay, support impersonation. Progress tracking works: the path page moved from 0/11 to 11/11 as I captured, scoreboard hit exactly 30/201, and the certificate PNG downloaded (200, valid PNG) once complete. Hint ladders are genuinely good and progressive. The log-poison chain is the best-designed multi-step challenge in the set. No broken step links; every path step link landed on a working page.
- Bugs found (with reproduction):
  1. CSTI flags fall with no template exploitation at all. Repro: GET /csti/basic (parse CSTI_NONCE from page source), then GET /csti/beacon?v=basic&d=49&n=<nonce> -> 200, the lab awarded the flag, claim-status confirms captured. Repeat for filter-bypass, constructor (d=anything), attr, stored. The design only proves "a client loaded the page", and the basic lab's own level-2 hint teaches the beacon replay. The intended JS evaluation technique is optional, so a curl-only player clears the whole module in ~30s per lab.
  2. LFI double-encode awards without any traversal. Repro: GET /lfi/double?page=%73ecret.txt (only the letter "s" is percent-encoded, no ".." anywhere, nothing double-encoded) -> the lab awarded the flag. The award check asks whether the raw input contains "%", not whether encoding was the actual bypass. The intended double-encoded ../ payload was never needed.
  3. Session predictable hands you the answer. Repro: GET /session/predictable shows "Your session id: N" and "Their session id: N+1" in plain text, so no pattern analysis is required; setting the lab_sid cookie to the shown admin value and opening /session/predictable/admin awards the flag. The briefing says to study the pattern, but the page prints the admin sid directly.
  4. Cross-challenge interference in the API module. Repro: PATCH /api/me with {"role":"admin"} (the mass-assignment solve) leaves your session as admin, so GET /api/v1/users/3 returns 200 and GET /api/v2/users/3 no longer awards the flag (both key off the session-cached role). Recovery: PATCH {"role":"user"}, then re-login via GET /api/login/alice to refresh the session. On a shared instance, any tester's PATCH breaks this challenge for others too.
  5. Auth reset (v1) has a global race. Repro: POST /auth/reset/confirm with token=base64("admin") earned no flag before the first reboot (another tester had already requested admin's reset, so the "was it ever issued" record was polluted), but the identical request earned the flag after the reboot on fresh state. A correct forged-token solution can fail depending on what other testers did first.
  6. Briefings reference the wrong port. Several 'start' texts and the code-replay payload block say http://localhost:3000 or Host: localhost:3000 while the lab runs on 127.0.0.1:18410. Students mapping the challenge to the live instance get confused.
- Friction/confusion points: The shared account records are mutable across testers, so alice/admin passwords drifted from briefing defaults twice during my run (once pre-reboot, once post-reboot), silently breaking rate-limit, ratelimit-xff, and fixation attempts until I re-locked passwords through the reset flows. Progress is session-based with no recovery: when the VM rebooted and when two curl processes wrote my cookie jar at once (my own mistake: the OTP brute-force script and my foreground work shared one jar), captures were orphaned and I had to re-run steps. The OTP challenge is the grindiest step: ~0.7s per attempt on a loaded shared instance, so 10,000 attempts takes well over an hour single-threaded; I parallelized into 10 workers (batches of 100, sleep 1 between bursts) and it finished in ~7 minutes, finding the code 2800.
- Hint quality (helpful? spoilery? useless?): Helpful and well tiered. The API rate-limit and LFI filter hints describe the exact technique without giving the payload. The CSTI basic level-2 hint goes further and teaches the beacon replay, which undercuts the module's own goal (see bug 1). The predictable-sessions briefing overstates the work involved since the page shows the admin sid (see bug 3).
- Difficulty fairness: Fair for API (exposure trivial by design, mass-assignment easy, version-bypass fair, ratelimit-xff genuinely instructive) and LFI (traversal/absolute/config-read easy, filter-bypass/nested-deep medium, log-poison the right kind of hard). CSTI is mislabeled in practice: the intended technique (browser JS evaluation) needs a real browser, but the beacon shortcut makes every lab trivial via curl. The OTP step is the only genuinely slow one, and only because of request latency on the shared instance, not skill.
- Burp-first feasibility: API fully Repeater/Intruder friendly. LFI fully Repeater friendly. CSTI's intended path needs Burp's embedded browser (JS), but the shortcut works from Repeater. Path steps: auth enumeration, brute-force, resets, and OTP are Intruder friendly; fixation/predictable are cookie edits in Repeater; kid-sqli needs token crafting (Repeater plus a JWT tool or a small script); code-replay needs a browser for the IdP authorize/approve flow, then the double exchange works from Repeater.
- Suggestions (concrete): (1) CSTI: require proof of real evaluation in the beacon, for example make the expected d value a per-load randomized arithmetic challenge rendered into the page, so a static d=49 replay fails; and remove the replay instructions from the hint ladder. (2) LFI double-encode: award only when the single-decoded check had no ".." but the double-decoded path did, instead of testing for a bare "%" in the raw input. (3) Predictable sessions: stop printing the admin's session id on the guest page; keep the sequential scheme but make students infer the next id. (4) Isolate or reseed the mutable account records per tester (or add a reset endpoint per session) so other testers' password changes cannot break challenges. (5) Fix all localhost:3000 references in briefings and payload blocks to the real instance address. (6) Offer a progress export/import on the paths page so a lost session or a VM reboot does not wipe a student's whole run.
- Rating: 4
