# Student Review: Proxy Paula (burp-01)
- Modules tested: proto (Prototype Pollution, 6 challenges), ssti (Server-Side Template Injection, 9 challenges)
- What worked well: Every single challenge is solvable with Burp Community Proxy plus Repeater alone, no Pro features needed anywhere. The challenge pages render hint ladders that name the right Burp tool for each step (Proxy to capture, Repeater to replay and mutate), and each page includes a copy-paste Repeater request block. The payload blocks and "Starting point" texts are accurate about the endpoints, methods, and Content-Types. The scoreboard is honest: my jar went 0/201 to 15/201 exactly as I solved things, and replays do not inflate the count. The SSTI filter bypasses are genuinely fun and well-staged (arithmetic first, then the real payload), and the proto challenges build a real skill ladder (query pollution, JSON pollution, blacklist bypass, DoS, client-side, unicode bypass). Per-challenge isolation is good where it exists: proto-dos uses a per-request scope, so breaking it does not poison anyone else.
- Bugs found (with reproduction):
  1. Free flags via cross-session pollution inheritance (shared instance). Reproduction: with a brand new cookie jar that never sent an exploit, request GET /proto/query/admin, /proto/json/admin, /proto/constructor/admin and /proto/unicode/admin. All four awarded a flag and the fresh jar's scoreboard read 4/201. Prototype pollution is process-wide, and nothing on the admin checks verifies that this session performed the merge. On a shared pool instance this means any student can harvest these four flags without solving anything.
  2. Bare claim awards the proto-client flag with no browser demonstration. Reproduction: with a fresh cookie jar, GET /proto/client/claim?theme=dark. The lab awarded the flag even though no page ever rendered a polluted theme in a browser. The claim endpoint trusts whatever theme parameter arrives, so a Burp Repeater user never needs the built-in browser at all. The hints, start text and tools pill (BZ, B, DT) all insist the browser path is the way, but the cheapest working exploit is one Repeater GET.
  3. Wordfilter hint 3 recommends a dead-end technique. The hint ladder says "try case tricks and encoding variants", but the filter regex is case-insensitive (/gi). Reproduction: ?input={{eval("vault"+"SECRET")}} produced no flag. The working payload needs a split like {{eval("vaultSe"+"cret")}}. Case tricks can never work here, so the hint wastes a student's time.
  4. Duplicate route registration in SSTI. Both basic.js and rce.js register router.get('/greet'); basic's handler wins because it is registered first in index.js, so rce.js's handler is dead code. User-visible behavior is still correct because the one live handler awards both the basic and rce challenge ids, but it is a trap for anyone reading the code.
  5. Stale host in payload blocks and guidance. The proto-query and proto-json payload blocks hardcode "Host: localhost:3000", the unicode guidance says "Host: localhost:3000", and the proto-client start text says to navigate to http://localhost:3000/proto/client, but this instance runs on 127.0.0.1:18406. Copying the block verbatim into Repeater sends the wrong Host header. It is harmless here (the server ignores Host), but a Burp-first learner will wonder why the given block does not match their target.
- Friction/confusion points:
  - curl URL globbing bites when students cross-check with curl: a raw ?__proto__[role]=admin gets expanded by curl into multiple requests and the merge silently never runs. You need curl -g. Burp Repeater sends the text as typed, so the Burp path is fine, but anyone verifying with curl will get confused. Worth a one-line note.
  - The wordfilter hint ladder also suggests "Send the request to Intruder and fuzz ways to build the blocked word". Burp Community Intruder is rate-limited, and this challenge is much better solved by thinking in Repeater (split the blocked word at a different boundary). Suggesting Intruder here pushes learners toward an awkward, slow approach for a problem that is really a reasoning problem.
  - ssti-dotblock hint 3 says "resend once to confirm it reproduces, then claim it". There is no claim endpoint for that challenge; the flag is awarded inline in the rendered response. "Claim it" sent me looking for a claim URL that does not exist.
  - proto-client's tools pill lists DT (DevTools), which is never needed. The intended path uses Burp's built-in browser (which does exist in Community edition), and the shortcut needs only Repeater.
  - proto-query's start text tells students to type the query string into the browser merge field, while the hint ladder tells them to use Repeater. Both work, but the two instructions read like they describe different intended paths.
- Hint quality (helpful? spoilery? useless?): Mostly helpful and well-staged. The proto ladders correctly sequence: Proxy the traffic, spot the merge, pick the magic key, Repeater it, verify with the admin check. The SSTI ladders correctly sequence: prove evaluation with arithmetic first, then attack the filter. The ssti-rce ladder is a model hint ladder: confirm evaluation, remember require() exists, build the command, render the output. Spoilery in the right places: the how fields and payload blocks hand over exact payloads, but only after the hints have done the teaching. Useless or misleading spots: wordfilter hint 3 (case tricks dead end, unneeded Intruder), dotblock hint 3 ("claim it"), and proto-client hints never mentioning that the claim is a plain GET.
- Difficulty fairness: Fair overall. proto-query/json Medium, constructor Medium, dos Easy, client Easy, unicode Hard all land right. ssti-nobrackets/dotblock/curly Medium are fair single-idea puzzles. ssti-noquotes Hard is fair (char codes plus eval is a genuine two-step). ssti-rce Hard is fair as a capstone. One nit: proto-client is rated Easy, but the intended browser-based path is fiddly for a first-timer while the bare-claim shortcut makes it trivial; the rating matches the shortcut, not the intended path.
- Burp-first feasibility: 15/15 doable in Burp Community. Proxy captures everything (forms are GET, merges are GET/POST). Repeater replays everything, including the text/plain unicode merge (the hints correctly say to set Content-Type manually). Intruder is suggested once (wordfilter) but never required, and Community's Intruder throttling would make that suggestion painful if followed; Repeater suffices. The built-in browser (proto-client intended path) ships with Community. Nothing here needs Intruder payloads at scale, Grep-Match, Comparer, Decoder beyond basics, or any Pro-only feature. Missing from the lab's own Burp guidance: any mention of Intruder payload setup (not needed here), Grep-Match rules (not needed, flags render inline), and Repeater parallel send (not needed). The lab's guidance names the right tool every time; it just over-suggests Intruder once and over-insists on the browser once.
- Suggestions (concrete):
  1. Gate the proto admin checks on the polluting session: record which session performed a successful merge and only award the flag when the same session opens the admin check (or reset Object.prototype.role between checks). This closes the cross-session free flags on the shared instance.
  2. Bind the proto-client claim to a server-issued proof: when /proto/client is served, mint a one-time signed token tying the session to a nonce, and require claim?theme=...&proof=<token>. Bare theme claims should stop awarding flags. Until then, drop DT from the tools pill since DevTools is never used.
  3. Replace hardcoded "localhost:3000" in payload blocks, Host lines and start text with the actual instance host/port, or a {HOST} placeholder plus a note that the Host header value does not matter.
  4. Rewrite ssti-wordfilter hint 3: remove "case tricks" (impossible against a /gi filter) and the Intruder suggestion; instead hint at splitting the blocked word across string concatenation at a boundary the filter cannot see, or building characters from codes.
  5. Reword ssti-dotblock hint 3: "the flag appears in the rendered response" instead of "then claim it".
  6. Dedupe the /greet registration in the SSTI module into a single handler that awards both challenge ids, and delete or clearly mark the dead one.
  7. Add a one-line note to proto-query's guidance that brackets in the query string must be sent raw (curl users need -g to disable globbing).
  8. proto-client: either keep the browser path as the intended solve and fix the claim endpoint (suggestion 2), or acknowledge in a late hint that the claim is a plain GET. Teaching students the browser demo while the server accepts a bare claim undermines the lesson.
- Rating: 4
