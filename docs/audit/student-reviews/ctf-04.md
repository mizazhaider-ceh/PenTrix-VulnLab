# Student Review: Exploit Eve (ctf-04)
- Modules tested: cmdi (9 challenges), http (3 challenges), postmsg (5 challenges). All flags captured: cmdi 9/9, http 3/3, postmsg 5/5, on the shared pool instance http://127.0.0.1:18401/ with a dedicated jar (/tmp/cookies-ctf-04.txt; one extra jar /tmp/cookies-ctf-04b.txt for the cache-deception attacker role). NOTE: the VM rebooted mid-session (~01:37 UTC); the server on 18401 died during testing and auto-recovered, and the pool was later rebooted wholesale. Every capture below was re-verified post-reboot and the scoreboard re-checked: cmdi 9/9, postmsg 5/5, http 2/3 on the main jar (cache-deception captured under the attacker jar), plus hostheader host-abs-url, cors cors-reflect, oauth code-replay, api mass-assignment from the SOLUTIONS.md checks.

- What worked well:
  - cmdi: the evidence-based award (flag only when real command output appears) is excellent, and the six later challenges gate the award on the actual technique marker in the raw input ($IFS, ${IFS}, literal newline, backtick, ?, tab), so the intended bypass is genuinely required. The "Sanitized value sent to the shell" readout on each gadget page makes filter behavior instantly visible and is the best single learning aid in the module.
  - http: verb-tamper and crlf-log are crisp and fast; the crlf-log award requires the forged lines to actually render in the log viewer (evidence-based, not input-pattern), which is the right call. Cache-deception's X-Flag header + two-session flow teaches the whole primitive faithfully.
  - postmsg: the bare-beacon, forged-nonce, and no-nonce attempts all return 400, so the page-bound one-time token defense holds against direct beacon poking. Each challenge's attacker page and "How to claim this flag" card with the live claim-status widget give a complete browser-first workflow.
  - SOLUTIONS.md (api mass-assignment aside): oauth code replay, hostheader absolute-URL, and cors reflected-origin all work as documented (ports in the doc say 3000/3111/3109; the pool instance runs on 18401, so swap the port).

- Bugs found (with reproduction):
  1. PATCH /api/me returns HTTP 500 for the SOLUTIONS.md-documented body, and the request crashed the 18401 server process. Repro: GET /api/login/alice, then curl -X PATCH http://127.0.0.1:18401/api/me -H 'Content-Type: application/json' -d '{"display_name":"alice","role":"admin"}' returns the 500 error page. Cause visible in code: the SET clause is built from every body key, but the users table has no display_name column, so the UPDATE throws. Shortly after this request, the node process on 18401 was gone (port closed, no node process) and recovered ~45 seconds later (supervisor restart). Correlation, not proven causation, but the crash followed the 500 immediately, and the same PATCH reproduced the 500 after the restart. Impact: the documented api mass-assignment solution does not award the flag; workaround body {"role":"admin"} alone returns 200 and the lab awards the flag. Verdict for that solution: stale/wrong.
  2. cmdi evidence check is spoofable by echoing output-shaped text (no genuine id/cat needed). Repro: GET /cmdi/ping?host=127.0.0.1;echo 'uid=1000(test)' (URL-encoded) renders the flag banner, and GET /cmdi/ping3?host=127.0.0.1;echo${IFS}'root:x:0:0:root:/root:/bin/bash' also renders the banner (the $IFS marker check passes on the raw input while the passwd evidence is faked by echo). The comment in the code claims bare echoes never match, but a fully-shaped line does. This is a cheat that works across the cmdi module's evidence checks wherever only the marker plus output-shape is required.
  3. All five postmsg flags are obtainable without a browser and without any postMessage being sent, via direct beacon calls. Repro: GET the victim page (e.g. /postmsg/no-check), scrape PM_NONCE from the HTML source, then GET /postmsg/beacon?v=no-check&d=no-check:test&n=<nonce> and the lab awards the flag. Wildcard: scrape SECRET_TOKEN from /postmsg/wildcard page source, then /postmsg/beacon?v=wildcard&d=wildcard:<secret> and the lab awards the flag. csrf-action: POST /postmsg/csrf-action/delete directly (the delete endpoint has no origin/CSRF guard of its own), then /postmsg/beacon?v=csrf-action&d=csrf-action:account-deleted and the lab awards the flag. The server cannot distinguish a genuine victim-page firing from a manual call, so the intended postMessage technique is never required. The 400 responses for missing/wrong nonces show the token binding works; it just does not prove a message was ever posted.
  4. curl-specific quirk (not a lab bug, worth knowing): on the hostheader login with -H "Host: evil.com", curl files the response's Set-Cookie under the evil.com domain, so the awarded session is orphaned in the jar and the scoreboard shows 0/5 for that jar. Reading the scoreboard with the same Host header (or in a browser, where the cookie binds to the real request host) shows the capture correctly. The lab behaves correctly here.

- Friction/confusion points:
  - The shared pool leaves cross-tester state: GET /api/me showed alice already at role "admin" before I PATCHed anything, because another tester had flipped it. Solutions that depend on pristine DB state are flaky in the pool.
  - ping7's wildcard hint suggests ? globs, but a naive absolute pattern like ;/???/c?t /???/?????? over-matches and makes cat dump binaries instead of passwd. The working shape is ;/???/c?t /?t?/passwd (only /etc matches ?t? in the middle).
  - For postmsg, the wildcard hint says to "replay" the beacon in Repeater, but the nonce labs' tokens are single-use, so a blind replay of a captured beacon 400s. Small inconsistency between the hint text and the token design.
  - The 400 "No flag" beacon page tells the user which payload shape the beacon expects; that is fine for a lab but it is also the page that documents how to skip the browser work (see bug 3).

- Hint quality (helpful? spoilery? useless?):
  - Helpful across all three modules. The ladders are genuinely progressive: level 1 nudges, level 2 teaches, level 3 shows the payload shape without handing over the exact command. None of them are spoilery (they never print a copy-paste payload), and none are useless. The cmdi hints correctly point at the exact filter gap each time, and the postmsg hints correctly route through Burp Proxy history. The ping7 hint 2 is the only one that under-specifies the gotcha above.

- Difficulty fairness:
  - Fair throughout. ping/ping2 are genuinely trivial (semicolon or &&), ping3-ping9 each demand the named technique (the award gate enforces it), so the curve from Easy to Medium is honest. http's three challenges are all Easy/Medium and fair; verb-tamper is maybe too easy but it is the module's on-ramp, fine. postmsg is Medium and fair in a browser; the curl shortcut (bug 3) makes it trivial for a player who reads the beacon code, but a student following the intended browser path gets a fair challenge.

- Burp-first feasibility:
  - cmdi: fully Burp-first; every challenge is one GET in Repeater, and the filter readout is right on the page.
  - http: fully Burp-first; verb-tamper is a method change in Repeater, crlf-log is encoded bytes in the request line, cache-deception needs a cookie-less second session which the docs call out explicitly.
  - postmsg: intended path is browser-first (Burp Proxy + browser + attacker page + claim widget, well documented), but the beacon endpoint is reachable from Repeater for inspection; note the curl shortcut above makes the whole module Repeater-solvable.

- Suggestions (concrete):
  1. Fix api mass-assignment: either add the display_name column or ignore unknown keys in the SET clause, and update SOLUTIONS.md to the working body. Also investigate the 500-then-crash sequence; a student fuzzing the PATCH body should not be able to take down the pool instance.
  2. Harden the cmdi evidence check against echo-spoof: for example, require the evidence to be consistent with a real execution (the injected command's output should not be byte-identical to a substring of the student's own input decoded differently), or run the check against output with the student's full echoed argument also scrubbed, or require two independent evidence types. At minimum, correct the code comment that claims echoes cannot match.
  3. For postmsg, consider making the beacon verify something only a real victim-page execution could produce (e.g. for data-xss, require the message data to contain an actual XSS-shaped payload that the victim's sink would render), or document the direct-beacon call as a known lab limitation so students do not accidentally skip the lesson.
  4. Tweak the ping7 hint to warn that absolute globs can over-match and to narrow the pattern, or make the challenge accept the broader pattern by using a more targeted award check.
  5. In the pool, reseed the shared users table (or isolate it per session) so role/admin and password state from other testers does not leak into solution reproducibility.

- Rating: 4

## SOLUTIONS.md accuracy (verified live on http://127.0.0.1:18401)
- (1) api mass-assignment: stale/wrong. Route exists (PATCH /api/me). Step 1 (GET /api/login/alice) works, step 2 works, but step 3's documented body {"display_name":"alice","role":"admin"} returns HTTP 500 and no flag is awarded (users table has no display_name column). Workaround verified: {"role":"admin"} alone returns 200 and the lab awards the flag (scoreboard showed Mass Assignment captured).
- (2) oauth code replay: accurate. Steps work verbatim after swapping the documented port (localhost:3111) for the live pool port. Authorize pentrix-spa as bob, approve, exchange the code twice at POST /oauth/idp/token: both responses return valid, different access tokens, and the second response carries the flag field. Award confirmed on scoreboard.
- (3) hostheader absolute-URL: accurate. Route exists (POST /hostheader/login). With Host: evil.com and alice's demo credentials, the response is 302 with Location: http://evil.com/hostheader/dashboard and the flag banner renders in the response body; the flag was awarded (visible on the scoreboard session; see bug 4 note about curl's cookie domain). Documented ports (127.0.0.1:3109) differ from the pool port.
- (4) cors reflected-origin: accurate. GET /cors/prove?vuln=cors-reflect&origin=https://evil.com awards the flag, and the raw check matches the docs exactly: /cors/api/profile returns Access-Control-Allow-Origin: https://evil.com plus Access-Control-Allow-Credentials: true.
