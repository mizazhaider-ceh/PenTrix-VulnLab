# Student Review: Grinder Lena (intermediate-06)
- Modules tested: Business Logic Flaws (bizlogic, 8 of 8 captured), Host Header Injection (hostheader, 5 of 5 captured), OAuth Flaws (oauth, 8 of 8 captured). All 21 were confirmed twice: flag shown in the exploit response and the scoreboard count rising (session total 25/201 including the 4 SOLUTIONS.md checks below). Note: the lab pool rebooted mid-session at about 01:37 UTC, so every result in this review was re-run and re-confirmed on the live instance after the reboot.
- What worked well:
  - Every assigned challenge is genuinely exploitable end to end with curl alone, and each one teaches the real technique (tampered form fields, stacked coupons, forged Host and forwarded-host headers, full OAuth grant abuse) instead of a trivia answer.
  - Cheat resistance is solid. Tested bare claims and replays: POSTing the OTP form with otp_ok left at 0 gave no flag; an empty coupon list gave no flag; the attacker collector with no token, or with a token issued for the legitimate host, gave no flag; a code-grant access token presented by a different user at the userinfo endpoint did not earn the implicit-flow flag (the grant type is actually checked); replaying an already captured exploit (negative quantity) showed no second flag and the scoreboard did not double count.
  - Scoreboard feedback is immediate and per challenge, which makes grinding efficient.
  - SOLUTIONS.md accuracy:
    - jwt alg=none: accurate. The /jwt/none route exists, the documented node one-liner builds a token the form accepts verbatim, and the lab awarded the flag.
    - crypto ECB oracle: accurate. All documented steps verified live: ciphertext is 32 bytes for input prefixes 0 to 3 and jumps to 48 bytes at a 4-byte prefix (block size 16), 48 identical input bytes produce three identical ciphertext blocks, the secret length is 28 as documented, the byte-at-a-time loop from step 4 recovered the full secret, and POST /crypto/ecb/solve awarded the flag. The example secret value in the doc is from an older boot, as the doc itself warns.
    - ssrf basic fetch: stale on this instance, accurate in substance. The /ssrf/fetch route exists and the technique works, but the documented URL literally targets localhost:3000, which returned "Fetch failed" here because this instance listens on a different port. Pointing the identical step at the live port awarded the flag on the first try.
    - upload GIF/HTML polyglot: accurate. POSTing the exact documented body to /upload/polyglot passed validation, GET /upload/poly/x.gif came back as Content-Type text/html with the body intact, and the lab awarded the flag.
- Bugs found (with reproduction):
  - Broken demo credential on hostheader login. The login page advertises "alice / alice123, bob / bob123", but POST /hostheader/login with username=alice and password=alice123 returns 401 on the live instance, while bob / bob123 returns 302 and works. Reproduction: curl -X POST -d "username=alice&password=alice123&continue=/hostheader/dashboard" http://127.0.0.1:18401/hostheader/login gives 401; swap in bob / bob123 for a 302.
  - Error pages can leak a full server stack trace. Once, during the pool restart window, POST /oauth/client/history-log with a JSON body returned an Express error page containing a TypeError stack trace with internal file paths instead of the normal JSON reply. The same request returns 200 after a full boot and a normal 404 page renders cleanly, so this looks like an error-handling path that breaks when session state is unavailable. Error pages should stay generic.
  - Host poisoning silently splits a curl session (tooling trap worth documenting). With curl, POST /hostheader/login with Host: evil.com returns the flag banner saying "Saved to your scoreboard", but curl files the session cookie under the poisoned domain, so the capture lands on a shadow session and the student's real scoreboard stays at 0 for that challenge. Reproduction: fresh cookie jar, one poisoned login (flag shown), then GET /scoreboard shows 0/201; manually pinning the original session cookie on the poisoned request makes the same exploit count (verified, scoreboard rose to 13/201). Browsers key cookies by the address bar host, so Burp users are unaffected, but curl-first students will burn time on this.
- Friction/confusion points:
  - The broken alice credential above cost real time at the very first hostheader challenge; I only got in by trying the second advertised account.
  - oauth implicit: the intended flow needs the simulated victim-browser step (posting the fragment URL to the in-lab history endpoint). Doable with curl, but hint level 1 frames it around Burp Proxy history entries, which does not map onto a terminal workflow; the challenge page attack plan is what actually unblocked me.
  - host-cache-poison: the poisoned cache is shared by everyone on the instance, so a stale entry from another tester can be sitting there. The Clear cache link exists and was needed before my own poison-then-visit run behaved.
  - Around the reboot, scoreboard totals bounced (0, then 12, then 5 with a challenge from a module I never touched shown as captured). After the reboot the counts were stable and matched my captures exactly, but a student mid-grind would read that as lost progress.
- Hint quality (helpful? spoilery? useless?): Mostly helpful and well laddered: level 1 nudges, level 2 teaches the mechanism, level 3 gives the payload shape. bizlogic hints are honest without spoiling at levels 1 and 2. The oauth code-leak page even states the exact flag condition (exchange a code that belongs to a different user), which prevents the most common wrong turn. host-ssrf hints name the internal agent address outright, which makes a Medium feel Easy. The only weak ladder is implicit level 1, which assumes a Burp Proxy history workflow and says little that helps a curl user.
- Difficulty fairness: Fair overall. In bizlogic, price tampering and negative quantity are true one-request Easys, while the email takeover is a fair three-step Medium. host-cache-poison as the module's only Hard is justified: two phases (poison, then visit as a normal user) plus a shared cache to manage. In oauth, code-leak and scope-upgrade are honest Easys, and code-replay plus pkce-skip are fair Mediums because each needs two controlled exchanges and a comparison. host-ssrf labelled Medium plays easier than that once the hints name the target address.
- Burp-first feasibility: Fully feasible with Burp Community. Every exploit in these three modules is a Repeater-grade edit: change a form field, rewrite the Host header, add an X-Forwarded-Host header, or resend one token exchange. Nothing here needs Intruder volume or paid features. The implicit lab needs one extra simulated-browser POST, which Repeater handles fine.
- Suggestions (concrete):
  - Fix the alice account so alice / alice123 works on /hostheader/login, or change the page text to only advertise credentials that actually log in.
  - Make error responses generic (no stack traces) and make the error page render even when session state is missing.
  - Add one line to the host-abs-url challenge text: curl users should pin their session cookie explicitly when poisoning Host, because curl re-scopes the cookie to the poisoned domain and the capture otherwise lands on a different session.
  - Surface the shared-cache warning on host-cache-poison above the fold ("other students share this cache, clear it first"), not just as a small button on the portal page.
  - In SOLUTIONS.md, note that URLs must use the port the lab actually runs on (3000 in the default local setup, different on shared instances); the SSRF entry fails verbatim otherwise.
- Rating: 4
