# Student Review: Prof. Ben (instructor-02)

- Modules tested: HTTP Layer Flaws (all 3 challenges: CRLF Log Injection, Verb Tampering, Cache Deception), postMessage Flaws (all 5 challenges: No Origin Check, Wildcard targetOrigin, Unsanitized Message Data as HTML, Substring Origin Check, Privileged Action via Forged Message). Also walked the career path "Zero to Web Pentester" and completed its steps 1 (Reflected XSS), 2 (SQLi Login Bypass) and 6 (Verb Tampering) end to end with curl. All testing was done with curl against a single shared instance, one cookie jar per simulated student, simulating the Burp Repeater workflow the briefings describe. Note on verification timing: the lab VM rebooted mid-review. After the reboot every capture was re-run and re-confirmed on the live instance (9 captures on my main session plus Cache Deception on the second, attacker session), so all results below are verified post-reboot.

- What worked well:
  - Every challenge card carries a briefing, a difficulty pill, a tools pill and a three-level hint ladder (Nudge, Technique, Explicit). As an instructor I can predict what a stuck student will see at each level.
  - CRLF Log Injection is the best-designed challenge I tested. The lab awarded the flag only after my forged line actually rendered as an extra line in the log viewer, not when I merely sent the injection. That is evidence-based grading, and it teaches students to confirm impact instead of trusting that a payload "should" work.
  - Verb Tampering's concept framing is classroom-ready: the briefing explains why a state-changing GET is dangerous (bookmarkable, loggable, forgeable), so the lesson is the design flaw, not the trick.
  - Cache Deception is honest about its own mechanics: the dashboard shows live cache state, who you are logged in as, and warns up front that the flag arrives in a response header because the response is CSS. I primed the cache as alice and pulled the flag from the X-Flag header in a second, cookie-fresh session. It worked exactly as documented.
  - The postMessage module briefing teaches the core pattern in 30 seconds (check event.origin, never use wildcard targetOrigin) before any lab starts, and each lab pairs a victim page with an attacker page plus a live claim-status widget so students can see whether the exploit registered.
  - Answer sharing is blunted by design. There is no "paste a flag" submission box anywhere; progress only counts when the lab itself awards the flag in that student's own session. postMessage claims additionally require a per-session, single-use token tied to a real victim-page load, so a classmate's copied beacon URL does not claim anything for you.
  - The career path page tracks per-step completion, shows a progress bar, and locks the certificate download until all 10 steps are captured (I confirmed the certificate route refuses an incomplete path).

- Bugs found (with reproduction):
  - Scoreboard showed another challenge as my capture, once (pre-reboot). Reproduction: with one fresh session I completed Verb Tampering (GET /http/feedback?msg=...) and CRLF Log Injection (inject via /http/track, then open /http/admin/log). The first /scoreboard fetch afterwards reported exactly 1 captured flag, and the captured row was "Query-String Pollution", a challenge I never visited. Two later fetches correctly showed my 2 HTTP captures. I could not reproduce it again, and it did not recur during the post-reboot re-verification, but a progress display that disagrees with itself even once is a grading-trust problem in a classroom.
  - The cache in Cache Deception is shared by every student on the instance, not per session. Reproduction: one session purges or primes /http/account.css and every other session sees the same cache state and the same Purge button. With 30 students on one instance, students will prime and purge each other's cache mid-exercise and the "victim versus stranger" story collapses.
  - Certificate verification codes are identical for every student. The verify code for a path depends only on the install, not on who completed it, and the certificate itself prints the generic name "PenTrix Student" because there is no account system. One student's certificate screenshot verifies just as well for any other student, so certificates cannot be used as proof of individual work.
  - A reboot wipes all student progress. The lab VM rebooted during this review; when the instance returned, my scoreboard was back to 0 of 201 and every capture had to be re-earned from scratch (I re-ran all 10 and re-confirmed them). In a class, one restart mid-semester erases the entire gradebook record, because progress lives only in per-boot session state with no persistence and no export.

- Friction/confusion points:
  - There are no student accounts at all. Progress lives only in a browser cookie session. I cannot roster 30 students, cannot tell whose scoreboard is whose, and a student who clears cookies or switches laptops loses all recorded progress with no recovery.
  - There is no per-student reset. The only way to restart clean is to abandon the session. A student who poisons shared state (see the cache bug) or locks themselves out of a lab flow has no supported reset path an instructor can point to.
  - There is no instructor view: no single page listing all students' per-module progress, no CSV export, nothing to paste into a gradebook. Running a class means opening 30 scoreboards by hand.
  - Briefings assume Burp is already installed and the browser is already proxied ("Send your browser through Burp Proxy" is step 1 everywhere). The home page and the career path contain no Burp setup guidance at all. For a real week-one class, tool setup is the biggest barrier and the lab is silent on it.
  - postMessage labs are presented as browser exercises, but all five can be claimed from curl alone by replaying the claim call the victim page would make (I did exactly that for all five). The browser interaction that teaches origin semantics is optional in practice.
  - The career path's step notes are one or two lines each. Step 2 (SQLi Login Bypass) assumes the student already reads SQL. Nothing in the path or the step note teaches the minimum SQL needed, so a true beginner stalls at step 2 of 10.

- Hint quality (helpful? spoilery? useless?): Helpful, well-layered, and spoilery by design at level 3. Level 1 nudges point at the right surface without naming the flaw (good). Level 2 teaches the actual technique, for example what %0d and %0a become after URL decoding (good teaching). Level 3 is effectively the worked answer: Verb Tampering level 3 says to replay the submission over GET with the parameter moved into the URL, Cache Deception level 3 names the exact response header to read, and the postMessage level 3 hints walk the student to the beacon replay step by step. For self-study this is excellent. For graded work it is a problem, because nothing records hint usage: there is no hint counter, no score penalty, and no way for me to distinguish a first-try solve from a level-3-guided solve. Difficulty-weighted scoring exists (Easy 1, Medium 2, Hard 3) but hints are free and invisible.

- Difficulty fairness: Mostly fair. HTTP is labelled Beginner with Easy, Medium, Medium challenges; the CRLF challenge earns its Medium because the student must understand URL encoding and then confirm the effect in a second view, and the ladder teaches both halves. postMessage is labelled Intermediate and that is honest: wildcard is a fair Easy, the other four are fair Mediums, although No Origin Check and Unsanitized Message Data overlap heavily (both end at "message rendered as HTML") so the module feels like four ideas in five labs. The career path curve is gentle until it is not: Reflected XSS first is right, but SQLi at step 2, the protocol-relative redirect at step 7, and CSV formula injection at step 8 (which needs a real spreadsheet program to even observe the payload firing) are the rough edges.

- Burp-first feasibility: Strong for the HTTP module. All three challenges completed cleanly with curl standing in for Repeater, including reading a flag out of a response header, which is exactly the skill Repeater teaches. Weaker for postMessage: the intended workflow (drive the attacker page, watch the victim page fire its claim in Proxy history) genuinely needs a browser, and the curl shortcut I used skips the very interaction the module exists to teach. A Burp-only student can finish the module without ever reasoning about origins in a live page.

- Suggestions (concrete):
  - Add lightweight student identity: a name or class code claimed at first visit, stored with the session, printed on the scoreboard and on certificates. Without it, no classroom feature below is possible.
  - Add an instructor dashboard: one page listing every active session's per-module and per-path progress, with a CSV export for the gradebook.
  - Add a per-student reset button (clear my progress) that only touches that student's session, plus an instructor reset for a single named student.
  - Make the Cache Deception cache per session (or per student namespace) and remove the global purge, so a class on one instance cannot interfere with itself.
  - Record hint usage per challenge (highest level opened) and show it on the scoreboard; optionally apply a published score decay so hint policy is a grading decision, not an honor system.
  - Bind certificate verification codes to the completing student session and print the student's claimed name on the certificate, so a certificate identifies one person.
  - Add a short "set up Burp in 10 minutes" onboarding page and link it from the home page, the path page, and every challenge start block that currently just says to proxy the browser.
  - Add a two-paragraph SQL primer before career path step 2, and a note on the CSV step naming a spreadsheet program (LibreOffice or Excel) the student needs to observe the result.
  - Persist progress across restarts (or add a one-click progress export per student), so a reboot or instance recycle cannot erase a semester of recorded work.

- Rating: 3
  - Verdict on the constant question: could I run a class on this? Not yet, and not because of the challenges. The challenge content, briefings and hint ladders are genuinely good teaching material, and I would happily assign the HTTP module and the career path as guided lab work with me in the room. What is missing is the classroom layer around them: student identity, an instructor progress view, per-student reset, hint accounting, and per-student isolation of shared lab state. Add those five things and this becomes assignable coursework.
  - Verdict on "Zero to Web Pentester" as week-one coursework: it is a genuine beginner curriculum in ordering and tone, and steps 1, 5 and 6 are true first-week material. I would not assign it as unsupervised week-one homework, because it assumes Burp is already set up and SQL is already readable, and neither is taught anywhere in the product. Assign it as a supervised lab after a 30 minute Burp setup session and a 15 minute SQL primer, and it works.
