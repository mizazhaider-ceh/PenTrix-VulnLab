# Student Review: Grinder Owen (intermediate-09)
- Modules tested: IDOR (7 challenges), Prototype Pollution / proto (6 challenges), SSTI (9 challenges). All tested on the shared pool instance http://127.0.0.1:18404/ with a dedicated cookie jar and curl as a Burp Repeater simulation.
- What worked well:
  - IDOR module is the strongest teaching of the three. Seven clean, distinct access-control patterns (profile lookup, unprotected admin panel, sequential invoice ids, client-supplied user_id on email change and API key regen, forced browsing to an unlinked admin function, comment deletion without authorship check). Every intended exploit worked exactly as briefed and the lab awarded the flag each time.
  - The API Key Regeneration challenge is a standout: it is a real two-step chain (rotate another account's key via the user_id parameter, then authenticate with the fresh key). The award logic correctly requires that YOU performed the rotation through the IDOR; merely reusing a shown key does not count. This is the best-designed anti-cheat in the three modules.
  - SSTI is a well-paced filter-bypass ladder: basic eval, curly strip, dot blacklist, bracket blacklist, quote plus word blacklist, underscore blacklist, word blacklist, then real RCE via child_process. Each challenge has exactly one intended bypass and all of them work. Naming the second challenge "Scope Leak (Data Exposure, Not RCE)" is honest teaching.
  - proto-unicode-bypass works as documented: the raw literal __proto__ is rejected with 400, the \\u005f-escaped version returns 200 and merges. The constructor.prototype bypass also executes correctly.
  - Admin-role sanity checks are solid on IDOR: anonymous users get no flag and a sign-in prompt; the admin account itself viewing /idor/admin or other profiles gets no flag; replays re-render the flag box but do not double count on the scoreboard.
- Bugs found (with reproduction):
  1. PROTO grading attribution is broken: one pollution earns four flags. Prototype pollution is process-global, but four challenges (proto-query, proto-json, proto-constructor, proto-unicode-bypass) each award on the same check (a fresh object's role reading 'admin'). Reproduction on a fresh instance: log in, send GET /proto/query?__proto__[role]=admin, then visit /proto/json/admin, /proto/constructor/admin, and /proto/unicode/admin WITHOUT performing their merges. The lab awarded all four flags from that single request. A student can skip the JSON, constructor, and unicode techniques entirely. (Re-verified post-reboot: scoreboard showed all three captured via bleed after one query-string merge.)
  2. PROTO proto-client claim endpoint is trust-the-client. GET /proto/client/claim?theme=dark with curl awards the flag; no browser ever loads /proto/client, no pollution happens anywhere. The server checks only that the theme value is non-empty and not the default, and nothing binds the claim to an actual page execution. A bare claim is a free flag. (I verified the intended path separately by executing the page's own parser and merge functions in node: the payload does pollute and would redirect to the claim URL, so the teaching is correct, but the claim gate is not.)
  3. PROTO proto-dos DoSes the shared lab instance. GET /proto/dos?__proto__[toString]=boom awards the flag (verified pre-reboot), but it writes a non-function toString onto the shared Object.prototype of the whole process. Immediately after, every endpoint (/, /scoreboard, /idor) refused connections (curl exit 7, connection refused) for an extended period. A challenge whose intended exploit kills the lab for all other students on the pool instance is a design flaw; at minimum it needs process isolation or a cleanup path.
  4. Minor doc nit: the API Key Regeneration and Comment Deletion "Starting point" boxes tell students to visit http://localhost:3000/..., but the pool instance runs on 127.0.0.1:18404. The relative login links (/idor/login/alice) work fine, but the hardcoded localhost:3000 text will confuse pool users.
- Friction/confusion points:
  - curl (and many tools) reject raw square brackets in URLs, so the proto payloads must be sent with curl -g. Burp Repeater handles them fine, so this is a tester-tooling note, not a lab bug.
  - IDOR Email Change and Comment Deletion mutate shared pool state (admin's email address, bob's comment deleted) for every other student. Expected for an intentionally vulnerable lab, but on a shared instance later students see a changed admin email and a missing comment.
  - proto-client cannot be done with curl alone; it needs a real browser or Burp's built-in browser. The briefing says this clearly, so it is fair, just slower for curl-only testing.
- Hint quality (helpful? spoilery? useless?):
  - IDOR hints are the best: three progressive levels (nudge, technique, explicit request shape), Burp-specific, and Hint 1 genuinely teaches observation before revealing the trick. For the Medium challenges Hint 3 is nearly the full solution, which is the stated design of level 3, so acceptable.
  - PROTO hints are helpful and accurate (the unicode Content-Type: text/plain hint and the client claim-response hint both match reality). The query challenge briefing even hands over the payload shape; fine for a Medium intro to the topic.
  - SSTI hints are good: the basic hint teaches proof-by-arithmetic first, and the noquotes hint ("spell the name with character codes and evaluate the result") points at the exact technique without writing the payload. None felt useless; none felt prematurely spoilery below level 3.
- Difficulty fairness:
  - IDOR: fair overall. Profile IDOR and Admin Panel as Easy are right. Email Change as Easy is right. Comment Deletion as Easy is right. Invoice Download and API Key Regen as Medium are right. Forced Browsing to Admin Function as Medium is questionable: it is the same single action as the Easy Admin Panel challenge (request an unlinked admin URL), so it reads as Easy-tier.
  - PROTO: fair. The four role-pollution variants teach distinct bypasses (raw, JSON own-property, constructor.prototype, unicode escape) and each is appropriately tiered; the unicode one earns its Hard. Polluting toString as Easy is right.
  - SSTI: fair overall. Basic Template Injection as Medium is a stretch (a single arithmetic probe is Easy-tier); everything else is correctly tiered, with noquotes and the real RCE earning Hard.
- Burp-first feasibility:
  - IDOR: fully Repeater-feasible, all seven.
  - PROTO: query, json, constructor, dos, unicode fully Repeater-feasible. Client-Side Pollution needs Burp's built-in browser (or any real browser), which is stated in the briefing; the claim step then shows in Proxy history. Feasible with Burp Community.
  - SSTI: fully Repeater-feasible, all nine, including the RCE (a single GET with an expr parameter).
- Suggestions (concrete):
  1. Fix proto attribution: give each pollution challenge a distinct property to pollute and check (e.g. role for query, isAdmin for json, level for constructor, clearance for unicode), or snapshot the target property before the student's merge and only award if that challenge's merge changed it. This closes the one-request-four-flags cheat and the cross-student pollution confusion.
  2. Bind the proto-client claim to real page execution: issue a one-time token when /proto/client is served and require it on /proto/client/claim. Reject bare claims that carry no token.
  3. Isolate or clean up proto-dos: run the widget merge in a sandboxed context, or provide a reset endpoint that deletes the polluted toString, so one student's DoS does not take the shared instance down for everyone.
  4. Downgrade Forced Browsing to Admin Function and Basic Template Injection one tier each (Medium to Easy), or add one extra step to justify Medium.
  5. Replace the hardcoded localhost:3000 links in the IDOR starting-point boxes with relative links so pool users are not sent to the wrong port.
- Rating: 3
