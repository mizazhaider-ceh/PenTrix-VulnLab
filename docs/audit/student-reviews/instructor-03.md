# Student Review: Prof. Cleo (instructor-03)
- Modules tested: JWT Attacks (jwt, all 8 challenges: none-admin, weak-secret, kid-sqli, jku, alg-confusion, no-expiry, aud-bypass, kid-default) and Open Redirect (redirect, all 5 challenges: protocol-relative, javascript: scheme, data: scheme, backslash allowlist bypass, parameter pollution). All 13 were solved end to end with curl and the lab awarded the flag for every one. Testing happened twice: once before the pool VM reboot and again after it, because the reboot reset session progress to 0/201. Every result below was re-verified post-reboot on the live instance (final scoreboard for my session: 17/201, the 13 assigned challenges plus the 4 SOLUTIONS.md checks). Extra duty: 4 documented solutions from SOLUTIONS.md verified live (see the SOLUTIONS.md accuracy section).
- What worked well:
  - The briefings teach before they test. The JWT briefing explains token anatomy (header, payload, signature), states the goal plainly (get a token with role "admin" accepted), and names the local tooling available. The redirect briefing is the best I have seen in a lab: it tells students exactly how to verify their work (curl -i, read the Location header) instead of leaving them to guess what success looks like.
  - Every challenge page hands you a legitimate sample first (a real guest token, a working form), so students start from a working baseline and diff their attack against it. That is proper onboarding.
  - The jku challenge runs its attacker key server inside the lab, so a class needs no external hosting, no tunnels, and no accounts to teach a genuinely advanced attack.
  - Redirect flags are awarded inside the 302 response body, so a student who does not follow the redirect still sees the award and the explanation of why it worked.
  - The scoreboard tracked my session accurately at every check, per module and overall (13/201 after the assigned modules, 17/201 after the SOLUTIONS.md checks).
  - Flags are randomly generated per install at first boot, and the lab awarded the flag only after my session actually performed each exploit. Scoreboard state, not the flag string, is the honest proof of work.
  - Difficulty labels are mostly honest, and the "Break then fix" section is upfront that fix mode is not available yet instead of shipping a broken button.
- Bugs found (with reproduction):
  - Parameter pollution: a protocol-relative second value is honored but earns no flag, with no explanation. Reproduction: GET /redirect/polluted?next=/dashboard&next=//evil.example.com/phish returns 302 with Location: //evil.example.com/phish, and the body contains no flag and no reason. Repeat with next=https://evil.example.com/phish and the lab awarded the flag. The previous lab in the same module teaches //host as the canonical external target, so students will reasonably reuse it here, see a "successful" redirect, and conclude the lab is broken. Verified both before and after the reboot.
  - The alg-confusion "Starting point" block renders a literal "\n" at the end of the text, and its three steps run together on one line on the JWT module page. Students see the formatting artifact instead of steps.
  - Briefing URLs are hardcoded to the wrong port for this deployment. The JWT module page says http://localhost:3000 seven times and the redirect page once, while this pool instance serves on port 18404. A student who copies the text literally lands on a dead port. (On a default local install on port 3000 the text is presumably right; it just does not adapt.)
  - Minor: POST /jwt/aud returns a bare 404. The real submit endpoint is /jwt/aud/login, which the challenge page form uses correctly, so browser students are fine. A curl-first student who posts to the page URL gets a 404 with no pointer to the right endpoint.
- Friction/confusion points:
  - Two of the eight JWT challenges (weak-secret, kid-default) hinge on guessing one tiny secret with no candidate list anywhere in the briefing or hints. The lesson should be "weak secrets fall to a small wordlist", but as shipped it plays as "guess what the author picked". In a timed class, that is a lottery, and the strongest and weakest student stall for the same reason.
  - alg-confusion is byte-sensitive in a way the lab never warns about: the public key must be used exactly as published, and my first well-formed attempt was rejected until the key text was reproduced byte for byte. The denial page returns one generic "Signature invalid or role is not admin" message for every failure mode in the whole module (malformed token, bad signature, wrong role all look identical), which makes classroom debugging slow.
  - no-expiry and aud-bypass are pure copy and paste: the winning token is printed on the challenge page and only has to be submitted unchanged. They teach the concept (a check is missing) but demand zero technique, so a student can clear both in under a minute without understanding signatures at all. Fine as confidence builders, but an instructor should not count them as evidence of JWT skill.
  - Classroom answer sharing is wide open: the success page prints the flag in full, and nothing ties a flag to a student. One solved challenge can be read aloud to the whole room. Grade on scoreboard screenshots or live demos, never on submitted flag strings.
  - There is no instructor tooling at all. Progress lives in each student's own browser session. I found no accounts, no class roster, no instructor view of who solved what, no export, and no per-student reset (wiping browser cookies is the only reset I could find, and a server restart wipes everyone's progress, as the pool reboot demonstrated when my 13 captures went back to 0). Running a graded class on this today means collecting screenshots by hand.
  - Deployment warning found during the SOLUTIONS.md checks: one documented ReDoS request stalled the shared instance for about 21.5 seconds for everyone (a short failing input on the same endpoint answered in 0.6 seconds). On one shared instance, a class of 30 experimenting with ReDoS will freeze the lab for the whole room. Give that module its own instance or a warning in the briefing.
- Hint quality (helpful? spoilery? useless?):
  - The ladder format is excellent: three rungs per challenge, labeled Nudge, Technique, and payload shape, collapsed by default so students choose their own depth. This is the structure I wish other labs copied.
  - JWT ladders are the strong half. kid-sqli and jku sequence genuinely multi-step attacks correctly (smuggle the key, then sign with it; publish a key, then point the token at it) and rung 3 still makes the student assemble the payload rather than pasting it.
  - Redirect ladders are helpful but lean spoilery at rung 3: they state the key insight almost verbatim (for example, pollution rung 3 spells out that one value is checked and the other is honored). For a Beginner module that is a defensible choice, but an instructor should know rung 3 is effectively the answer.
  - The ladders coach tooling better than they coach the hard step. weak-secret rung 3 explains how to grep responses for the winner but never bounds the candidate list; kid-default rung 3 says "try the next one" without saying how large a guessing space is reasonable. The two guessing challenges are exactly where the ladder goes quiet.
  - no-expiry rung 3 is a complete solution ("replay the leaked token as-is"), which is proportionate to how thin that challenge is.
- Difficulty fairness:
  - The JWT curve is sensible: an Easy opener (none-admin), Mediums in the middle, and the two genuinely hard multi-step challenges (jku, alg-confusion) at the end. Redirect is flat and gentle throughout, which is right for a Beginner module, and its hardest idea (backslash: the server validates a string, the browser parses a URL) is a real insight worth the Medium label.
  - The unfair spots are the two guessing challenges. weak-secret and kid-default grade luck and prior familiarity with common defaults, not technique, and sit oddly at Medium next to kid-sqli, which grades real skill at the same label.
  - Everything else grades by technique: if a student understands the concept, the challenge falls; if not, no amount of random payload spraying I tried got anywhere, which is how it should be.
- Burp-first feasibility:
  - Fully feasible, and honestly optional. Every hint ladder is written as Burp steps (Proxy, Repeater, Intruder, Decoder), and I still completed all 13 challenges with curl and a local Node signer alone, twice. A class can standardize on Burp without fear, and students who lose their Burp setup mid-class can finish with curl.
  - Two practical notes for a Burp-first class: jku and alg-confusion both require signing tokens, so students need a JWT extension or the local jsonwebtoken install the briefing mentions (the briefing does mention it, good). Redirect is the ideal first Burp module: the Location header in Repeater is the whole lesson.
- Suggestions (concrete):
  - Add the missing classroom layer: named or initialed scoreboard entries, a CSV export of per-student progress, a "clear my progress" button for students, and an instructor reset for a whole class session. Without these, I can run this as a workshop but not as a graded lab.
  - Ship a small candidate list (about 10 entries) inside the weak-secret and kid-default briefings. The lesson becomes reproducible, and class time goes to the signing workflow instead of guessing.
  - Fix the pollution mismatch: either award the flag for a protocol-relative external target too, or make the response body say the redirect was honored but the target form was not accepted, so students get feedback instead of silence.
  - Split the generic denial message into at least three cases (malformed token, signature failed, role not admin). It costs one line per case and removes the most common support question in a live class.
  - Render briefing URLs with the port the app is actually serving on, and fix the literal "\n" in the alg-confusion starting point.
  - Add one line to the ReDoS briefing warning that the payloads stall the server for everyone on a shared instance, and recommend a separate instance for that module in class deployments.
  - Keep the two copy-paste JWT challenges, but label them honestly as concept demos in the module intro so instructors weight them correctly.
- SOLUTIONS.md accuracy:
  - (1) bizlogic, Coupon Stacking Past 100%: accurate. The documented route POST /bizlogic/coupon-stack exists, and submitting codes=SAVE50,SAVE40,SAVE30 exactly as documented produced the documented result (120% total discount, a negative total of -10 on the $50 item) and the lab awarded the flag. Verified post-reboot.
  - (2) proto, Query-String Pollution (solution 1 of the proto section): accurate. Following the documented steps in one session (GET /proto/query?__proto__%5Brole%5D=admin, then GET /proto/query/admin) worked verbatim and the lab awarded the flag. Verified post-reboot.
  - (3) formula, Classic Formula Injection (solution 1 of the formula section): accurate. POST /formula/add with name==cmd|'/c calc'!A0 and note=classic, then GET /formula/export.csv, returned the raw formula cell in the body and the flag in the X-Flags response header, exactly as documented. Worth knowing for instructors: the documented commands use no session cookie at all and still work, because the award travels with the export response. Verified post-reboot.
  - (4) redos, Catastrophic Email Regex (solution 1 of the redos section): accurate in substance, with one copy-paste flaw. The route and payload work: 30 "a" characters plus "!" took about 21.5 seconds and the lab awarded the flag, while a short failing input answered in 0.6 seconds. But the command as printed in SOLUTIONS.md is broken: the python3 one-liner is missing its closing parenthesis (print('a'*30+'!' ), so a student pasting it verbatim gets a Python syntax error and has to repair the quoting before anything runs. The documented port in that section (3112) also does not match this instance (18404), the same drift as the module pages. Verdict: accurate steps and outcome, stale presentation.
- Rating: 4
