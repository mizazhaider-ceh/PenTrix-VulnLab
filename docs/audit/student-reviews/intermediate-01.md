# Student Review: Grinder Gus (intermediate-01)
- Modules tested: sqli (11 challenges attempted, 11 flags awarded), auth (8 attempted, 7 flags awarded; the 4-digit OTP challenge had its mechanism verified but the full brute force was not completed), oauth (8 attempted, 8 flags awarded), plus the Shop Takeover scenario end to end (4 of 4 stages, scenario flag awarded). NOTE: all results below were re-verified on the live instance after the second reboot (~02:47 UTC), which wiped scoreboard progress and rotated secrets. My session scoreboard ended at 29 of 201 (11 sqli + 7 auth + 8 oauth + the idor, bizlogic and xss flags earned through the scenario stages). Cookie jar: /tmp/cookies-intermediate-01b.txt on every request, fresh jar for cheat tests.
- What worked well: award gating is honest on most challenges. The injected output has to actually contain the target secret before the lab awards the flag (union, groupby, insert-inject, second-order all check the real outcome), the login-bypass rejects a plain legitimate admin login with no injection, bare enum-submit with no in-session probing awards nothing, and the XSS beacon requires the per-session page nonce (bare beacon from a fresh jar returns "No flag"). The scenario stage locking works exactly as advertised: stages unlock one at a time, each stage's link points at the right challenge, and the story (front door SQLi, hidden admin panel, price tamper, guestbook signature) matches the kill chain text. Hint ladders are consistently layered: level 1 nudges, level 2 teaches, level 3 nearly shows it.
- Bugs found (with reproduction):
  1. Cross-challenge credential mutation. POST /auth/question-reset (answer Smith) and POST /auth/change-password change alice's credential globally, so doing them before brute-force makes the weak password unsolvable for that session and any later student on the shared instance. Repro on a fresh boot: request the question reset first, then POST /auth/login with the original weak password fails, while the same login succeeds if brute-force runs first. Challenges that share one credential pool should be order independent.
  2. Stale port in briefing "start" fields. Several challenge cards tell the student to open http://localhost:3000/... (sqli like-wildcard and limit-offset, auth otp-reset, reset, enum-login, support, question-reset) while the instance serves :18406. Copy-pasting gives connection refused, wasted minutes for a beginner.
  3. user-enum hint text breaks the taught technique. The login page renders the hint ladder on the same page as the form, and the hints contain both oracle phrases ("user not found", "wrong password"). Burp Intruder grep-match rules taught in hint 3 therefore match every response. Repro with curl: responses for a fake username and for alice both contain both phrases in page text, so the oracle cannot be grepped.
  4. order-by and limit-offset award on pattern, not proof. POST /sqli/sort?sort=(CASE WHEN (SELECT 1)=1 THEN name ELSE price END) awarded the flag with no extraction of the target secret, and /sqli/paged?limit=-1 awards for any non-numeric limit value with rows returned, no hidden-row dump required. Difficulty labels say Medium/Easy but the check is cheaper than the label.
  5. OAuth code-leak log is newest-first with no failure signal. A student who mints their own codes while working will grab the newest log entry (their own code), exchange it at /oauth/idp/token, get HTTP 200 plus a working token, and no flag, with nothing distinguishing this from a correct attempt. The seeded victim code sits one entry down and is easy to miss.
- Friction/confusion points: the token endpoint returning 200 for both awarded and non-awarded exchanges (point 5 above) cost real debugging time. Cross-challenge shortcut: the target secret is identical across sqli challenges in one boot, so solving union once lets you submit the same value to blind-submit and wildcard-submit without ever building the boolean oracle, short-circuiting the intended grind of two Medium challenges. The OAuth history-log endpoint accepts any URL posted by anyone, so the implicit flow's "victim browser records the fragment" step is pure theatre over curl and teaches less than the hints promise. The scenario reuses module challenges, so doing the modules first auto-completes scenario stages and the kill chain feels like a checklist, not a chain.
- Hint quality (helpful? spoilery? useless?): helpful overall, spoilery at level 3 by design (which the module index discloses). SQLi hints genuinely teach the technique before showing shape. The auth reset hints hand over the token recipe directly, appropriate for Easy. The OAuth implicit hints are the best in the set: they explain why Repeater cannot see fragments and where the token actually surfaces. Nothing I tested was useless. The only weak spot is user-enum hint 3, which is actively misleading given bug 3 above.
- Difficulty fairness: sqli is fair across the 11, with blind and like-wildcard earning their Medium labels if the shortcut in the friction section is closed. auth is fair except the two grind challenges: the 4-digit OTP (10,000 tries, no lockout, no expiry) and the login brute force are heavy for an intermediate on throttled tooling. oauth is fair; implicit is the hardest conceptually and the hints carry it. order-by and limit-offset are easier than labeled due to bug 4.
- Burp-first feasibility: most challenges are fully Repeater workable (login bypass, union, error, groupby, insert, second-order, all auth forgeries, all oauth flows). Pain points in Burp Community: the OTP 10k Intruder run is throttled to a crawl, I verified the no-lockout mechanism with a few probes and the flag-on-correct-code logic but did not run the full 10k through curl since that would hammer the shared instance; blind and like-wildcard character-by-character extraction is similarly impractical in throttled Intruder and students will realistically script it; user-enum's taught grep-match fails because of bug 3. Everything else is comfortable in Community.
- Suggestions (concrete): replace all localhost:3000 mentions with relative links or the real port; isolate mutable credential state per challenge or add a reset button and document the order dependence; reword the user-enum hints so the oracle phrases do not appear in page text, or move hints off the response used for probing; require the actual target secret in output for order-by and limit-offset instead of pattern matching; return a distinct non-200 or a hint line on token exchange when no award condition fired; list the IdP log oldest-first or tag the seeded victim entry; consider a 3-digit OTP or an intentional timing shortcut so Community users can finish it in a session.
- Rating: 4
