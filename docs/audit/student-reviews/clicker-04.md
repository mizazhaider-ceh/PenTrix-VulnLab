# Student Review: Clicker Dana (clicker-04)

Live re-run note (2026-10-20): This review combines the original source-level click-through with a full LIVE re-run on the pool instance at http://127.0.0.1:18404/. The re-run happened after the second reboot (the coordinator restart at ~02:47 UTC that wiped per-boot state and brought all pool instances back, verified HTTP 200). Every live step used curl with a fresh cookie jar (/tmp/cookies-clicker-04-live.txt), curl standing in for Burp Repeater: fetch the challenge page, mint or copy a token, POST it, read the response. Result: all 8 JWT challenges solved live, the lab awarded the flag on each one, and the scoreboard shows the JWT module at 8 of 8 captured (8 of 201 overall for this fresh session). The first session's code-level findings are kept below; anything the live run contradicted is corrected in place and marked as a live check.

- Modules tested: JWT Security, all 8 challenges, this time live (GET /jwt, /jwt/none, /jwt/weak, /jwt/kid, /jwt/jku, /jwt/confusion, /jwt/confusion-pubkey, /jwt/noexpiry, /jwt/aud, /jwt/aud/login, /jwt/kiddefault, plus /jwt/attacker-keys, /jwt/attacker-keys/register, /jwt/attacker-keys/jwks). Tokens were minted offline with the jsonwebtoken library the module brief itself points at, then submitted by curl POSTs. Cheat tests run live: a bare claims JSON object, an unsigned token replayed into an HS256 endpoint, and an admin token signed with a wrong key. UX sweep re-checked live: module starting points, scoreboard (GET /scoreboard), denied pages and back links, empty submits, and junk input on the attacker key server.
- What worked well:
  - Awards are instant and unambiguous live. Every genuine exploit returned HTTP 200 with a "Welcome, admin" page and the flag awarded on that same response. The scoreboard matched right after: JWT Attacks 8 of 8, 100 percent, every row marked Captured.
  - All 3 cheats failed live with HTTP 403 and no flag was awarded: a bare claims JSON object at /jwt/weak, the unsigned none token replayed into /jwt/weak, and an admin token signed with a wrong key. The shortcuts do not pay.
  - Every JWT challenge page and every denied page I hit live has a real back link to /jwt (label: "Back to the JWT module"). The public key page /jwt/confusion-pubkey links back to /jwt/confusion, the attacker key server links back to /jwt/jku, and the aud token vending page links back to /jwt/aud. I found no dead end inside the JWT module itself.
  - The module page /jwt is a good clicker map: 8 cards, each card title is a link to the real challenge route, each card shows difficulty, a how line, a "Starting point" copy block, a 3 level hint ladder, and a tools pill.
  - Empty and junk submits are handled safely live, not with a crash: a junk token and an empty token at /jwt/weak both return HTTP 403 with the shared "Access denied" page and a back link, and the aud vending machine returns HTTP 400 with "Audience is required." plus a back link when aud is blank.
  - Home and scoreboard search are written defensively: q is escaped before it is echoed back into the input value, and the difficulty value is only accepted if it matches a known difficulty list, otherwise it falls back to All. Junk, quotes, and script-like input should render as text, not execute.
  - The scoreboard's "No challenges match your filter" line is a hidden, filter-toggled empty state in the markup. Correcting my earlier code-level read: on a live load with no filter active it stays hidden and does not confuse anyone.
  - Path verify is forgiving for clickers: the code is trimmed and compared case-insensitively, and the verify form is a simple GET form, so back, refresh, and re-paste all work without a broken state.
- Bugs found (with reproduction):
  - BUG 1, wrong address in almost every JWT starting point (highest impact for a clicker), CONFIRMED LIVE. Repro: open GET /jwt on the live instance and copy any "Starting point" block. 7 of 8 challenges tell you to open http://localhost:3000/... (none-admin, weak-secret, kid-sqli, alg-confusion, no-expiry, kid-default, plus aud-bypass) while the lab actually runs on http://127.0.0.1:18404/. A student who pastes that address gets a dead page or a different app. Steps: 1) GET /jwt, 2) read the weak-secret card, it says "Browse to http://localhost:3000/jwt/weak", 3) open it, connection fails. Only the jku starting point uses a relative path (/jwt/attacker-keys) and survives.
  - BUG 2, attacker key server prints a localhost JWKS host, PARTIALLY CORRECTED BY LIVE CHECK. Repro: 1) GET /jwt/attacker-keys, 2) register a kid, 3) the published list prints a JWKS address built as http://localhost:<PORT>/jwt/attacker-keys/jwks?kid=<kid>. In the source the port defaults to 3000, but on this pool the port is set, so live the address reads http://localhost:18404/... and the jku flow works when copied. The host is still written as localhost rather than the 127.0.0.1 address the student actually browses, and on any deployment where the port is not set it falls back to 3000 and the copy paste breaks again. Lower severity than my source read, still worth fixing.
  - BUG 3, live pool instance down during the whole first test window, RESOLVED BY THIS RE-RUN. First session repro: curl to http://127.0.0.1:18404/ returned HTTP 000 (connection refused) on repeated tries, and ports 18400 to 18410 were all refused, so that session earned 0 flags live because there was nothing to click. After the coordinator restarted all pool instances (second reboot at ~02:47 UTC), the same address answers HTTP 200 on / and /jwt, and the full module was completed live in this re-run: 8 of 8 flags earned, scoreboard 8 of 201 overall. The health check suggestion below still stands.
  - BUG 4, empty token submit gives a generic denial, no "you sent nothing" help, CONFIRMED LIVE. Repro: POST /jwt/weak with an empty token field returns HTTP 403 with the same "Access denied" page as a wrong token, and a junk token gets the identical page. A clicker cannot tell "form was empty" from "token was wrong". The one good exception is POST /jwt/aud/mint with a blank aud, which does return 400 and says the field is required.
  - BUG 5, junk on the attacker key server is accepted silently, CONFIRMED LIVE. Repro: POST /jwt/attacker-keys/register with kid=x and secret=y returns a redirect to /jwt/attacker-keys and the junk is listed as a published key, no validation message, no warning that the secret format matters later. Empty values do get a 400, but one character of junk passes.
- Friction/confusion points:
  - The starting point copy and the real address disagree (see Bug 1). This is the single biggest clicker friction in the module: the very first instruction sends you to the wrong place.
  - Two link styles fight each other. Card titles go to real routes like /jwt/weak, but each challenge also carries a link value like /jwt#weak-secret that lands on the module page anchor, not the challenge. Coming from scenarios or paths, a clicker lands mid-page on /jwt and has to click again.
  - Repeated placeholder spam: the "Break then fix" section on /jwt repeats a fix call to action once per challenge (8 times) under a paragraph that already says fix mode is not available for this module yet. One notice would do; eight identical dead ends train clickers to ignore the section.
  - The token form is a bare textarea with placeholder "eyJhbGciOi..." and a single Submit button on every challenge. No example of a filled in submit, no inline error location. After a denial you are on a new page and must use the back link and paste again, losing your last attempt.
  - Denied pages explain the outcome in one short line only (for example "Signature invalid or role is not admin."). That merges two different failures: bad signature and wrong role. A clicker who fixed one of them gets the same sentence and learns nothing.
  - The alg-confusion key copy is fragile in a way nothing warns about. The signature only verifies with the exact published key bytes; any copy path that trims the trailing newline off the key text produces a token that fails with the same generic denial. I hit this live: my first minted token was rejected, and re-minting with the exact bytes from the page earned the flag. A browser copy keeps the bytes intact, but any trimming tool breaks it silently.
  - Scoreboard rows are plain text, confirmed live in the rendered table (name and difficulty, no challenge link in the row), so after earning a flag a clicker cannot jump from the scoreboard row back to that challenge. Same museum feeling reported by other clickers.
  - Search filter behaviour is split: the home filter submits q and difficulty to the server, and also carries client side data attributes. With JavaScript off or with a long pasted string, a clicker gets a full page reload and loses scroll position on /jwt style long pages. Long strings and special characters are accepted with no visible length hint.
- Hint quality (helpful? spoilery? useless?): Helpful ladder shape, spoilery at level 3, which is honest for this persona. Every JWT card and challenge page uses the same 3 level ladder (nudge, technique, explicit). Level 1 hints are good nudges (weak-secret: the secret is a classic default). Level 2 teaches the method (sign candidate admin tokens and replay them). Level 3 is basically the recipe: alg-confusion states the server uses its own public key bytes as the HMAC secret, none-admin spells out the exact unsigned token shape, no-expiry says outright to replay the leaked token as-is, and jku level 3 names the exact header fields to set. Live check: the level 2 and 3 recipes I followed worked exactly as written, including the jku header fields and the public key signing step. That helps a stuck clicker finish fast, but a student who opens all hints first can complete several challenges without understanding them. kid-sqli level 1 is the most balanced: it asks what a quote in the kid does before giving the shaping steps.
- Difficulty fairness: Fair on labels, and the live run backs that up: all 8 were solved in one sitting. Easy (none-admin, no-expiry) really are copy, tweak, submit. Medium (weak-secret, kid-sqli, aud-bypass, kid-default) each need one real idea plus a tool step. Hard (alg-confusion, jku) need multi step work (fetch a key, mint offline, or run the in-lab key server then craft a header), which matches Hard. The unfair part is not difficulty, it is addressing: the wrong localhost:3000 starting points add fake difficulty to 7 of 8 challenges, and aud-bypass is easier than its Medium label once you read its page, because the partner admin token is handed to you on the page itself (confirmed live: submitting it as-is earned the flag).
- Burp-first feasibility: Feasible and clearly the intended path: every starting point and most hints are written Burp first (Proxy, Repeater, Intruder, Decoder), and every challenge accepts a plain form POST. My live run used curl as a Repeater stand-in and the mapping is one to one: one POST per token, read the response, adjust, resend. Two frictions: the Burp instructions assume the lab at localhost:3000 (wrong port here, see Bug 1), and the jku and alg-confusion flows require offline token minting. The module brief does advertise node one-liners for minting, and that is exactly what I used, so a clicker who reads the brief gets unstuck; a pure clicker with only Burp still stalls at the minting step.
- Suggestions (concrete):
  1. Build every starting point and the JWKS address from the actual request host and port (or use relative paths like the jku card does), and grep the whole repo for localhost:3000 in student facing copy.
  2. Add an explicit empty submit message on all 8 JWT token forms ("You submitted an empty token. Paste a token and try again."), matching the good 400 message already on /jwt/aud/mint.
  3. Split the denied message into two cases: signature or format invalid, versus valid token but role is not admin.
  4. Keep the submitted token in the form after a denial (re-render the challenge page with the token preserved and the error inline) so clickers can tweak one segment instead of re-pasting.
  5. Replace the 8 repeated fix calls to action on /jwt with one section level "not available yet" notice.
  6. Make scoreboard challenge names link to their challenge routes, and make scenario and path deep links use the real challenge route, not the module anchor.
  7. Validate the attacker key server form with a short inline note (kid and secret are both required, secret is case sensitive, it must match the secret you sign with) instead of silently publishing junk.
  8. The pool is back up (coordinator restart, verified live in this re-run). Still add a health check: a fresh visitor hitting / should never get connection refused post-reboot without a status page.
- Rating: 1-5: 4
  - Raised from 3 now that the module is proven live. Everything a clicker is promised actually works: all 8 challenges are solvable end to end, flags award instantly, cheats are blocked, and the scoreboard tells the truth. It loses one point because the first instruction on 7 of 8 cards still sends you to localhost:3000, and denied pages still cannot tell an empty submit from a wrong token.
