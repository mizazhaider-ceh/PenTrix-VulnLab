# Student Review: Grinder Mo (intermediate-07)

- Modules tested: crypto (8/8 challenges), jsonp (5/5), race (8/8). Plus SOLUTIONS.md verification duty: ssti RCE, xxe file import, auth brute-force (OTP), race coupon double-spend. All exploits done with curl-equivalent requests (Burp simulation); brute-force jobs stood in for Burp Intruder. Note: the pool VM rebooted twice during testing (~01:36 UTC and ~02:47 UTC, all 10 instances, fresh per-boot secrets both times); every result below was re-verified after the second reboot unless marked otherwise.
- Scoreboard re-confirmed on the live instance after the second reboot: 10/201 flags on my session after a purely sequential solve batch (crypto-b64, crypto-cbc, crypto-md5, crypto-keyjs, crypto-xor, crypto-hashext, jsonp x5, plus one extra b64 check). Race flags were confirmed in responses (11/12 coupon, 9/10 stock, 9/10 vote, 9/10 balance, 7/10 referral, 9/10 register, 15/20 ratelimit, upload-scan yes) but did not stick on the scoreboard, see bug 3 below. crypto-rand-pin is the one challenge I could not capture; see friction.
- What worked well:
  - Module briefings are genuinely good teaching: crypto explains the mindset ("not the ciphers, the usage"), jsonp gives the JSONP history and the exact attacker-page URLs, race gives the literal `xargs -P20` command and the "reset first" advice. I never felt lost about what to do.
  - Hint ladders (Nudge / Technique / Explicit) are honest and tiered well. The crypto hash-ext hints straight up tell you Burp Decoder will not do the padding step for you, which saved me time.
  - Anti-cheat is real: garbage beacons get 400, token replay gets 400 (single-use tokens), wrong-role cookie gets "Valid session, wrong role" with no flag, wrong ECB guess gets 400, sequential coupon redeem after use shows "Already redeemed". I could not get any flag without doing the actual attack.
  - Every challenge awards the flag in the response the moment the exploit succeeds, and the scoreboard tracks it correctly for normal sequential sessions.
  - /race/reset exists and works, which is essential because race state is global.
- Bugs found (with reproduction):
  1. Cookie jars kept in /tmp vanished mid-session (twice). Repro: `curl -c /tmp/cookies-intermediate-07.txt ...`, do work, come back later: `ls: cannot access ... No such file or directory`. The scoreboard then reads 0/201 because the session is gone. Keep jars in ~/workspace instead (they survive). Not a lab bug, but the task instructions say to use /tmp, so future testers will hit it.
  2. Parallel curl processes sharing one jar file clobber each other's cookies (last process to exit wins). Repro: fire a 10-process parallel stock burst with `-c/-b` on one jar, then check the scoreboard: it shows 0/201 even though 9 of 10 responses contained a flag, and the session id in the jar changed.
  3. Session tracking is fragile under parallel load even from one process. Repro: do one sequential solve (scoreboard reads 1/201, session id stable), then run a parallel burst (10-20 concurrent requests, threads sharing one cookie jar) on the same session; afterwards the scoreboard reads 0/201 and the jar's session id has changed. Reproduced three times, including after the full post-reboot re-verification sweep (24 awards in responses, scoreboard 0). Consequence: a student doing a race-condition attack (the whole point of the race module) can silently lose their session and every previously captured flag. Under normal sequential use the scoreboard tracks perfectly.
  4. Same-session multiple flag responses from one parallel burst: 19 of 20 coupon responses (and 9 of 10 stock, vote, balance, referral responses) contained a flag in the same session, because the once-per-session award check races the parallel requests too. Scoreboard counts it once, so no real gain, but the 19 flag boxes are noisy.
  5. The lab instance went down twice during my testing window (~01:36 UTC and ~02:47 UTC; per the coordinator notices these were full VM reboots of all 10 pool instances, so not caused by my traffic). Flag it because a student mid-grind loses all per-boot progress with no warning; nothing on the module pages mentions that reboots reset secrets and race state.
  6. SOLUTIONS.md speed claim is not reproducible on my instance: "A script with 100 concurrent keep-alive connections found the PIN in about 72 seconds (206,469 guesses, roughly 2,800 requests/second)". Measured: ~22 requests/sec single-threaded, ~130-150/sec with 20-24 concurrent workers. At that rate the full 1M PIN space is roughly a 1-2 hour grind, not 72 seconds.
- Friction/confusion points:
  - Race hints push "Burp Intruder with concurrent requests", but Burp Community Intruder is single-threaded and cannot do parallel bursts. A student who follows only the hint ladder in Community will fail every race challenge. The module page's `xargs -P20` curl command is the real feasible path; the hint ladders should mention it as the primary route.
  - crypto-rand-pin hints say "One million guesses is an Intruder job". In Burp Community (single-threaded), 1M requests at ~22/sec is about 12.5 hours. The realistic path is a Python script, and the page should say so. I ran the grind as a script (123k guesses in 16 minutes across 12 workers, zero lockouts, correct 401/200 behavior) but could not finish the full 1M space in my window; mechanism verified, flag not captured. The challenge logic itself is sound.
  - The jsonp "executed beacon" claim is bypassable without a browser: I earned all five jsonp flags with pure curl by scraping the per-session token out of the feed response and beaconing it directly. filter-bypass and mimetype add an attempt-shape check on the feed request, but curl satisfies those too. The beacon proves the feed was fetched, not that script executed. For Easy/Medium this is an acceptable design tradeoff, but the page text overclaims.
  - Auth OTP brute force changes the admin password globally on the shared instance (my test set it). Any other tester relying on the admin account will find their password broken. Worth a warning on the page.
- Hint quality (helpful? spoilery? useless?):
  - crypto: helpful, well tiered. b64's level 3 tells you the exact Decoder workflow without handing the answer. cbc's hints walk you to the IV layout without doing the XOR math for you. hash-ext is the best: it names the exact steps (glue padding, restore digest as state, continue with ;admin=1) while leaving the implementation to you. ecb's hint 3 is the full byte-at-a-time recipe, appropriately explicit for a Hard.
  - jsonp: helpful. callback-xss hint 3 tells you to load the tampered URL in Burp's browser, which is the actual hard step. array-hijack's page explains the 2007 trick and why `new Array` is the hook.
  - race: the hint content is fine but, as noted above, the "Intruder parallel mode" instruction is not feasible in Burp Community, which makes the hints feel useless until you find the xargs command on the module page.
- Difficulty fairness:
  - crypto: b64 Easy (fair, 5 minutes), md5 Easy (fair, wordlist is in-lab), keyjs Easy (fair), xor Medium (fair, crib is given), cbc Hard (fair, Burp Decoder XOR workflow genuinely works by hand), hash-ext Hard (fair, pure Python ~60 lines), ecb Hard (fair but heavy: ~3,600 oracle queries; the scripted inhex input the page documents makes it feasible), rand-pin Easy by mechanics but the 1M grind is the real boss (call it Medium effort).
  - jsonp: all fair. callback-xss Easy, csrf-data Medium, filter-bypass Medium, mimetype Easy/Medium, array-hijack Hard (fair, the page teaches the history).
  - race: all fair given the exact burst commands on the module page. upload-scan Hard is fair: the 2-second scan window is generous for a Repeater/curl fetch.
- Burp-first feasibility:
  - Yes for crypto except rand-pin (use a script; Community Intruder cannot do 1M) and ecb full loop (script is sane; the page supports scripted inhex input, which it documents).
  - Yes for jsonp, but you need Burp's built-in browser (or any browser) for the three reflection labs; Repeater alone can craft, only the browser executes.
  - Partial for race: Community Intruder cannot do parallel bursts, so the Burp-first path as written does not work. The xargs/python path the module page gives is the feasible one. This is the biggest Burp-first gap in the three modules.
- Suggestions (concrete):
  1. Add a one-line note to every race hint ladder: "Burp Community Intruder is single-threaded and cannot do parallel bursts; use the xargs command on the module page or a small Python script instead."
  2. Same for rand-pin: change hint 3 to recommend a Python script for the 1M space, keeping Intruder as the tool for the smaller OTP space.
  3. Fix the SOLUTIONS.md crypto speed claim (72 seconds at 2,800 req/s) to match measured reality, or scope it to the author's machine.
  4. Add a visible note on race pages that race state (and all per-boot secrets) is shared/global: resetting helps you but burns other students' progress on a shared instance.
  5. Soften the jsonp "only an executed beacon captures the flag" wording to "only a beacon carrying the live per-session token", which is what is actually enforced.
  6. Warn on the OTP page that a successful reset changes the admin password for everyone on a shared instance.
  7. Tell testers to keep cookie jars outside /tmp.
  8. Fix the session fragility under parallel load (bug 3): scoreboard progress must survive the race module. If sessions must rotate under load, warn the student in the UI ("your session changed, previous progress was reset") instead of silently showing 0/201.

## SOLUTIONS.md accuracy

Checked live on http://127.0.0.1:18402/ (post-reboot, fresh per-boot secrets).

1. ssti RCE: ACCURATE. Section 9 ("SSTI to Remote Code Execution") documents `GET /ssti/exec?expr={{require("child_process").execSync("id").toString()}}`; the route exists, the verbatim request renders the command output in the page, and the lab awarded the flag. Note: section 2 is titled "SSTI to RCE" but documents the scope-leak challenge (the module itself names it "Scope Leak (Data Exposure, Not RCE)"); the steps there also work verbatim, but the heading is misleading. The real RCE walkthrough is section 9 and it is correct.
2. xxe file import: ACCURATE. The verbatim `POST /xxe/import` payload with the DOCTYPE entity works and the lab awarded the flag. Note: the walkthrough hardcodes the author's absolute workspace path; it happened to match this deployment, and the collector page shows the correct path, so keep the path but point readers at the collector page as the source of truth.
3. auth brute-force (4-digit OTP): ACCURATE. The documented flow works verbatim: token extracted from `/auth/otp-reset` with the documented regex, brute force 0000-9999 against `/auth/otp-reset/verify` with no rate limiting (my post-reboot-2 run found the code in about 55 seconds and the lab awarded the flag), and login at `/auth/login` with the new password succeeds. Correction to my own earlier suspicion: the Python snippet in the file is valid; the rendering that made it look broken was my tool output redacting a credential-looking line. The snippet is fine as written.
4. race coupon double-spend: ACCURATE. The documented route exists, `GET /race/reset` works, and the `xargs -P20` parallel redeem burst double-spends the coupon and the lab awarded the flag (11-19 flag responses per burst in my runs). Note: race state is global/shared, so on a shared instance the "hit /race/reset first" advice is not optional, it is required.
