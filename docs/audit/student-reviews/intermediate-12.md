# Student Review: Grinder Rosa (intermediate-12)
- Modules tested: Open Redirect (5/5 exploited, the lab awarded the flag each time), Cross-Site Scripting (9/9 exploited, the lab awarded the flag each time), Cryptographic Failures (8/8 exploited, the lab awarded the flag each time). Extra duty: the "Shop Takeover" kill-chain scenario, completed end to end with all 4 stages captured in order and the lab awarding the scenario flag on the scenario page. All results were re-verified on the live instance after the second VM reboot (about 02:47 UTC), because per-boot state had been reset again; after the re-runs, the scoreboard for this session read 22 captured out of 201 total challenges (exactly the 22 assigned challenges), and the scenario was re-completed in its own session. All testing was done with curl against the shared pool instance (sleep 1 between bursts, PIN brute force excepted as it is that challenge's intended method), simulating Burp Proxy and Repeater traffic.
- What worked well:
  - Redirect module is a clean on-ramp: every challenge answers with a real HTTP 302, so the Location header is checkable proof in Repeater, and the flag lands only when the evil destination is genuinely honored. Negative tests behaved correctly: the legit allowlisted target gave 302 with no flag awarded, a blocked target gave 400 with no flag awarded, and the pollution endpoint honored a single evil parameter but awarded no flag until a second parameter was supplied.
  - The XSS beacon model is excellent anti-cheat design and I could not break it. A flag is awarded only when the beacon arrives with non-empty stolen data and the page-bound token that was rendered into the challenge page as window.__px. I verified each sink in the served HTML first (raw reflection, attribute breakout, JS string and template literal contexts, guestbook persistence, the innerHTML fragment sink), then fired the beacon exactly as the page's own payload would, and the lab awarded the flag for all 9. Re-verified after the second reboot, cheat tests still failed properly: a fabricated token returned 400 and no flag was awarded; replaying a consumed token returned 400; an empty data parameter returned 400; an unknown vuln id returned 400; a beacon for the DOM clobbering challenge (which never issues a token) returned 400. The claim-status widget also behaves: unknown id returns 400 with an error, and a captured challenge returns captured:true.
  - DOM clobbering is the standout challenge: the sanitizer genuinely strips script tags (I verified my script was removed while form markup survived), and the admin panel awarded the flag only after markup that really shadows window.settings.isAdmin (form id plus input name). Sending nothing earned an "Access denied" page and no flag. Re-verified after the second reboot.
  - Crypto labs are real attacks, not puzzles with fake depth. ECB: block size 16 confirmed, ECB confirmed with repeated blocks, and a byte-at-a-time attack through the hex oracle recovered the full secret; submitting it awarded the flag, a wrong secret returned 400 with no flag awarded. CBC: XORing the IV bytes over the known role value with a guest-to-admin delta produced a forged cookie the server accepted as admin; a garbage cookie returned 400. Hash length extension: I rebuilt the glue padding for the stated secret length, restored the digest as compression state in a small pure-Python SHA-256, and the forged MAC for the extended message verified; the signing endpoint also refuses any message containing "admin" (400), so the extension is truly required. XOR crib dragging with the known document header recovered the key (length 8) and the full plaintext. MD5 crack: the in-lab wordlist cracks the leaked hash offline instantly, then login awards the flag; a wrong password returns 401. Key-in-JS: the key sits in the served JavaScript exactly as briefed, the IV is prepended, offline AES-128-CBC decryption recovered the note. The reset PIN also falls to its intended solve: after the second reboot I generated a fresh PIN and swept the space with a threaded script; the correct guess then returned the flag. All crypto challenges were re-verified after the second reboot against the fresh per-boot values.
  - Shop Takeover is coherent and the gating works. The scenario page shows the story, explains how the scenario flag is earned, opens stage 1 with an Enter link, and shows stages 2 to 4 as locked with "Complete the previous stage to unlock". Capturing each stage flag unlocked exactly the next stage (lock counts went 3, 2, 1, 0 across my run). The chain reads like a real attack: SQLi login bypass as admin, then signing in as bob and walking straight into the admin panel, then buying the $50 hoodie for $1.00 (the receipt says "You paid: $1.00"), then a stored guestbook beacon. When the last stage flag landed, the scenario page awarded the scenario flag, and revisiting the page showed the flag banner again with all 4 stages marked captured, so a student can re-copy it. The whole scenario was re-completed after the second reboot with the same behavior.
- Bugs found (with reproduction):
  - BUG 1 (minor, HTTP semantics): the DOM clobbering denied page returns the wrong status code. Reproduction: with a fresh session, GET /xss/clobber-admin with no saved profile markup. Expected: HTTP 403. Actual: HTTP 200 with an "Access denied" body, so scripts and Burp response filters keyed on status code miss the denial. Confirmed again after the second reboot.
  - BUG 2 (shared-instance design): the reset PIN appears to be one shared value for the whole instance, so other students' activity can change it while you are mid-solve. Symptoms from my runs: I generated a PIN and swept the entire 000000 to 999999 space at about 12,500 requests per second without a hit, while another student was brute-forcing the same challenge at the same time and the instance was intermittently unresponsive in that window; the active PIN at sweep time can therefore not have been the one I generated, or it was no longer active. After the second reboot, on a fresh PIN and a quieter instance, the same sweep found the PIN (guess number 344477 of 1,000,000) and the correct guess awarded the flag, so the award path itself works. The design still makes students race each other on shared state. Recommendation: make the PIN per session, or shrink the space.
  - BUG 3 (progress persistence is inconsistent across pool resets): award-preserved titles vanished from my scoreboard more than once, without any action from me. Symptoms and times only, because the mechanism was not determined: (a) before any reboot, after a period of very heavy load on the instance, my scoreboard showed only 1 of the 21 titles I had captured in that session, and re-solving restored them; (b) after the first VM reboot (about 01:37 UTC), the scoreboard still showed my 6 most recent captures, so progress survived that reboot; (c) after the second VM reboot (about 02:47 UTC), the scoreboard read 0 captured for my session, so progress was gone. Two resets, two different outcomes. A student grinding for hours can lose their visible progress unpredictably; recommend saying so on the scoreboard page and advising students to save each flag as they earn it.
  - BUG 4 (shared-instance design): stored guestbook comments appear to be shared across sessions, unlike the DOM clobbering profile, which behaves per session. My beacon comment sits in the shared guestbook and would execute in any other student's browser who opens that page. On a shared pool this lets one student interfere with another student's run (or their graded screenshots). Consider scoping guestbook entries per session like the clobbering profile.
  - Note (not a code bug): during load I intermittently got connection failures (curl code 000) on ordinary pages, including the scenario page and the trusted redirect endpoint; each succeeded on retry once load dropped. Worth load testing the pool with several students active.
- Friction/confusion points:
  - XSS with curl: the payloads cannot literally execute in curl, so I verified by confirming the sink in the HTML and then sending the beacon the documented payload would send. That works and the claim box on every page shows the exact payload shape, but a student should know a real browser plus Burp is where they would watch it fire live. The module briefing does say this, so it is honest friction, not a trap.
  - Markdown challenge: using double quotes inside the javascript: link target silently breaks it, because the rendered href attribute ends at the first inner quote and the link becomes a broken fragment. The claim box payload uses single quotes and works; deviating from it fails silently with no error anywhere. A one-line note in the briefing ("use single quotes, double quotes break the attribute") would save real debugging time.
  - The SVG upload token dance is the fiddliest flow in the XSS module: the uploaded file is its own document, the token travels in the file URL as ?n=, and the script must read it from location.search and sit inside CDATA or the XML parse breaks. The claim box explains all of this, and following it literally worked first try, but it is a lot of moving parts for a Medium.
  - Module navigation is inconsistent: XSS challenge cards have an "Open challenge" button, while redirect and crypto cards only describe a starting path as text. Students have to hand-type the challenge URLs in two of the three modules.
  - The scenario's stage gating is presentational: locked stages hide their briefings and links, but the underlying challenges stay directly reachable by URL from their module pages, so the kill chain can be done out of order and the scenario simply reflects captured flags. The scenario flag still requires all 4 stage flags, so nothing is skippable, but a student expecting hard gating may be confused when a stage they never "unlocked" shows as captured.
  - The PIN sweep speed swings wildly with instance load: about 12,500 requests per second when I had the instance nearly to myself, about 265 requests per second while other students were active, which turned my post-reboot solve into a roughly 22 minute sweep even before the answer happened to sit early in the space. Students should expect this challenge to take real time on a busy pool.
- Hint quality (helpful? spoilery? useless?): Helpful, and well graded across all three modules. Level 1 nudges (what to look at), level 2 teaches the technique, level 3 shows the payload shape without pasting a complete copy-paste answer. The crypto hints are refreshingly honest about tooling limits: the length extension hints admit Burp Decoder will not do the padding step for you, and the XOR hints tell you a small script is expected. The redirect and XSS level 3 hints name the key insight (two slashes, last parameter wins, script tags never run via innerHTML) without doing the whole job. One inconsistency: the PIN challenge card says to use Burp Intruder while the module page says a 6-digit space is a scripting job; the card should match the page.
- Difficulty fairness: Redirect labels are fair (Easy for protocol-relative, Medium for the rest; backslash and pollution genuinely need one insight each). XSS labels are fair: reflected and stored are properly Easy, DOM clobbering earns its Hard. Crypto is mostly fair: MD5, base64 cookie and key-in-JS are quick Easy wins; XOR is a fair Medium for someone who can write 20 lines of Python; ECB, CBC and hash length extension are real Hard attacks but well scaffolded (known plaintext layouts, stated secret length, hex oracle for scripting). The exception is the reset PIN: it is labeled Easy, but it is a 1,000,000-guess grind whose wall-clock cost depends entirely on instance load and on no other student touching generate in the meantime; on a busy pool it was the slowest challenge in the module by far. Either relabel it, shrink the space, or make it per session.
- Burp-first feasibility: Strong overall. Redirect is pure Repeater work (send, read Location, done). Every XSS challenge is doable Burp-first: Proxy to load pages and read tokens, Repeater to shape payloads, the embedded browser to execute them; DOM clobbering even skips the beacon entirely. Crypto is mixed by design and the pages say so: base64 cookie (Decoder), CBC (Decoder XOR transforms), MD5 (hash the wordlist, or paste hashes into any cracker) and key-in-JS (Repeater to read the JS, offline decrypt) are all feasible; ECB is feasible but tedious in Intruder and far saner as a script, which the oracle page quietly supports with its hex input mode; length extension and XOR crib dragging need a small script and the hints admit it. The one weak spot is the PIN: Burp Community throttles Intruder hard, so 1,000,000 guesses through Intruder is not a realistic student path; the honest tool is a script, which contradicts the challenge card's Intruder instructions.
- Suggestions (concrete):
  1. Fix the clobber-admin denial to return a real HTTP 403 status alongside the error page.
  2. Make the reset PIN per session (like the clobbering profile already behaves) and consider a 4 or 5 digit space, or keep 6 digits but state on the card that a script is the intended tool and Intruder Community will be too slow.
  3. Explain the progress persistence behavior on the scoreboard page: students saw captures survive one pool reset and vanish after another, so tell them to save each flag as they earn it.
  4. Scope the stored guestbook per session on shared deployments, or add a periodic reset, so one student's payload cannot fire in another student's browser.
  5. Add "Open challenge" buttons to the redirect and crypto module cards to match the XSS module.
  6. Add one line to the markdown challenge briefing: build the javascript: URL with single quotes only.
  7. Add a short "how verification works" note to the scenario page stating that stage flags are the source of truth and stages can be captured from the module pages too, so the soft gating does not confuse anyone.
- Rating: 4
