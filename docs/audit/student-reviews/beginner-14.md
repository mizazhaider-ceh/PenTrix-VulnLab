# Student Review: Day-One Mia (beginner-14)
- Modules tested: HTTP Layer Flaws (/http: crlf-log, verb-tamper, cache-deception), postMessage Flaws (/postmsg: no-check, wildcard, data-xss, substring, csrf-action). All 8 challenges exploited via curl with a dedicated cookie jar (/tmp/cookies-beginner-14.txt). Total 8 flags earned: 3 in HTTP (one credited to a fresh "attacker" session for cache-deception), 5 in postMessage. No other servers touched, nothing in the repo changed.

- What worked well:
  - The module briefing pages taught the concept first (what CR/LF bytes are, what a cache key is, how postMessage and event.origin work) in plain words before any attack steps, which kept me from feeling lost at the start.
  - HTTP verb-tamper worked in one request: GET /http/feedback?msg=... and the lab awarded the flag in the response body with a "Feedback submitted over GET" confirmation card. The scoreboard went from 0/201 to 1/201 and showed the challenge as Captured immediately.
  - HTTP crlf-log felt like real forensics: I sent a ref with %0d%0a, the track page confirmed "CR/LF bytes were written straight into the access log", and opening /http/admin/log showed my forged line rendered as its own line plus a "Forged log line confirmed" card with the flag. The evidence-based design (the flag only lands when the forged line really renders in the viewer) taught me something.
  - HTTP cache-deception behaved exactly like the walkthrough: login as alice, GET /http/account.css (X-Cache: MISS, personalized CSS), then a fresh cookie-less session fetched the same path and got X-Cache: HIT with the flag in the X-Flag response header and alice's stylesheet in the body. The /http/cache dashboard with the "Cache state" card and purge button made the whole attack visible.
  - postMessage no-check: loading /postmsg/no-check exposed the page token in the page source, and firing the beacon request exactly the way the victim page's JavaScript does it earned the flag with an "Exploit confirmed" page. Same pattern worked for data-xss and substring (with ?simulateOrigin=https://pentrix.lab.evil.com loaded first).
  - postMessage wildcard: the victim page source clearly showed the token broadcast with targetOrigin '*', and replaying the beacon with the captured per-session token earned the flag.
  - postMessage csrf-action: POST /postmsg/csrf-action/delete returned {"status":"account deleted (lab only)"}, then the beacon with the matching shape earned the flag.
  - Cheat resistance was solid everywhere I probed: a bare beacon with no token got HTTP 400 "No flag"; replaying an already-used no-check beacon got 400 (single-use); the csrf-action beacon with the right shape but no account deletion in that session got 400; an unknown vuln id got 400; viewing /http/admin/log in a fresh session with no injection earned nothing; GET /http/feedback with no msg showed only the form, no flag. I could not find any shortcut that awarded a flag without performing the actual exploit.

- Bugs found (with reproduction): None that block the lab. One display confusion that is not a bug in the scoreboard itself but worth flagging: after I completed cache-deception, my main session's scoreboard stayed at 2/3 with Cache Deception "Not captured", because the flag was awarded to the fresh attacker session (its own scoreboard showed 1/201 with Cache Deception "Captured"). The counts and names were correct in both sessions; it only looked broken for a moment until I realized the capture belongs to whichever session fetched the poisoned cache.

- Friction/confusion points:
  - The cache-deception capture belonging to the attacker session (see above) confused me for a few minutes. As a beginner I expected "saved to your scoreboard" to mean the scoreboard in my main browser window. The briefing does say every capture is saved to the scoreboard, and the challenge page says the flag is returned in the header, but nothing says the capture lands on the session that read the poisoned CSS. A one-line note on the /http/cache page ("the flag is saved to the scoreboard of the session that pulls the cached stylesheet") would remove the confusion.
  - The CRLF challenge page has a "Try this payload" block that hands over the complete working payload (/http/track?ref=homepage%0d%0a2026-10-02 FAKE admin login from 10.9.9.9). As a beginner I solved it in two requests without reading a single hint. It is the biggest spoiler in either module.
  - postMessage flows genuinely need a real browser (iframes, postMessage between pages). I could not drive a browser here, so I simulated the exact requests the victim pages make (loaded each victim page, then fired the same beacon request a real browser would send). The DOM delivery part (iframe receives the message, handler fires) is the one part I did not run end to end in a browser. The hint ladders describe the browser flow well enough that I am confident about it, but this review covers the browser flows only by proxy.
  - The wildcard challenge's "Starting point" says to browse to /postmsg/wildcard (the victim page) first, while the actual flag-earning flow lives on /postmsg/wildcard/attacker. A beginner following only the starting point lands on the widget page with no visible next step; I only found the attacker link because the victim page links it at the bottom. The other labs' starting points point straight at the attacker pages.
  - The /http/cache page lists two victim logins (alice and bob) but the attack works with either; fine, but the walkthrough only ever mentions alice, so I wasted a minute wondering if bob was a trap.

- Hint quality (helpful? spoilery? useless?):
  - The three-rung ladders are mostly helpful and honestly graduated: rung 1 nudges ("The ?ref= parameter is logged raw"), rung 2 teaches the mechanism (what %0d and %0a become after URL decoding), rung 3 describes the full flow. For verb-tamper and wildcard I only needed rung 1 plus the starting point, and I felt taught, not handed the answer.
  - Spoilery: the CRLF "Try this payload" block on the challenge page bypasses the whole ladder. Also the postMessage attacker pages do everything with one "Fire payload" button, and the "How to claim this flag" cards spell out each step including the beacon URL shape; by lab 3 I was just clicking a button rather than thinking about the vulnerability. For a beginner module this is kind, but rung 3 plus the button means there is no rung left that I had to climb.
  - Not useless: none. Every hint I read was accurate and pointed at the real mechanism. The csrf-action attacker page even warns that a bare Repeater request to the beacon gets a 400, which saved me from a dead end and is excellent anti-cheat documentation.

- Difficulty fairness:
  - verb-tamper (Easy) and wildcard (Easy): fair. Both teach one idea and the first success builds confidence.
  - crlf-log (Medium): fair once you read the briefing; the two-step "inject then view" pattern is well scaffolded.
  - cache-deception (Medium): fair and my favorite; the two-session dance is the right level of challenge, the session confusion above is the only rough edge.
  - postMessage no-check, data-xss, substring, csrf-action (Medium): fair as a set, though they start to feel similar (load page, get token, fire beacon). The substring lab's simulated-origin banner honestly explains what is real and what is simulated, which I appreciated.

- Burp-first feasibility:
  - All 3 HTTP challenges are fully doable in Burp Community with Repeater alone: verb-tamper is a method change plus moving msg into the query; crlf-log is editing the request line in Repeater and then requesting /http/admin/log in the same tab (session handling matters, Repeater cookies on); cache-deception is two Repeater tabs, one with the alice login cookie and one with cookies cleared, reading the X-Flag in the response headers. No Intruder or paid features needed.
  - postMessage challenges need a browser plus Burp, not Burp alone: the exploit is a message posted between an attacker page and a victim iframe. Burp Community Proxy is enough to watch the beacon fire in HTTP history and send it to Repeater, which matches exactly what the hints describe. A beginner with Burp Community and any browser can do every challenge.

- Suggestions (concrete):
  1. Remove or gate the "Try this payload" block on the CRLF track page (show it only after hint rung 3 is opened, or replace it with the generic shape). It currently short-circuits the best-designed hint ladder in the module.
  2. Add one line on the /http/cache page noting that the flag is saved to the scoreboard of the session that fetches the poisoned stylesheet, so the attacker's private window (not the victim window) shows the capture.
  3. Fix the wildcard starting point to send the student to /postmsg/wildcard/attacker first, matching the other four labs.
  4. The postMessage "Fire payload" buttons are great for lab 1; consider making labs 4 and 5 require the student to type the payload themselves (the payload shape is already shown in a code block) to keep one lab that demands active construction.

- Rating: 4
