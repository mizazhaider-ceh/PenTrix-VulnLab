# Student Review: Prof. Ada (instructor-01)
- Modules tested: LFI (all 9 challenges), CSTI (all 5 challenges), and the API Hacker career path walked end to end (all 10 steps, path page shows 10/10, certificate PNG downloaded). Final scoreboard on the live instance: 24/201 in my session. Note on verification: the lab VM rebooted at about 01:37 UTC during my session and all earlier progress was wiped (scoreboard back to 0/201 with the same cookie jar), so every capture above was re-run and re-confirmed on the live instance after the reboot. All results in this review are post-reboot verified unless stated otherwise.
- What worked well: Module briefings are genuinely teachable. Each module page opens with a short concept brief (the CSTI page explains the engine, both delimiter syntaxes, and the beacon protocol in plain language), a learning track line with prerequisites and difficulty, then one card per challenge with a starting point and a 3-level hint ladder (Nudge, Technique, Explicit). LFI is the strongest module: the nine challenges build one idea at a time (plain traversal, a filter that strips once, a filter that checks before decoding, language parameter, config read, absolute path, deep nesting, process environment leak, log poisoning chain), and after a capture each page shows a "The fix" panel with the defensive pattern and an OWASP cheat sheet link, which is exactly the bridge from attack to defense I want in a classroom. Awards are technique-gated, not content-gated: in a fresh session, reading the LFI secret file by its plain name showed the secret marker but no flag was awarded; only a real traversal request earned it. Students learn the method, not just the target file. The API Hacker path is a coherent curriculum: data exposure first, then mass assignment, then missing rate limiting (the credential needed there is visible in the exposure step's output, so the chain teaches itself), then JWT attacks in rising order (none, weak secret, algorithm confusion), an OAuth login CSRF, an API key IDOR, a version authorization bypass, and CORS last. Order is sensible, each step note tells the student what to think about without naming the payload, and finishing all ten produced a downloadable PNG certificate with a per-install verification code plus a verify page, which is a usable hand-in artifact for coursework. The scoreboard is clear: per-module progress bars, search, and a captured/not captured filter.
- Bugs found (with reproduction): (1) Progress does not survive a server restart, and there is no warning. Reproduction: capture flags until the scoreboard shows progress, restart or reboot the instance (as happened at about 01:37 UTC), reload /scoreboard with the same browser session: it shows 0/201 again. For a class this is the single biggest operational risk: one mid-lesson restart wipes every student's visible progress. (2) The instance stopped responding entirely for several minutes during my first testing window (connection refused on the lab port, then it recovered); I could not tie this to any specific request of mine, and a reboot was later announced, but an instructor should know the pool can drop mid-session. (3) The LFI document viewer leaks the server's absolute filesystem path in its read error message. Reproduction: request a nonexistent file one directory up in the viewer and the error text prints the full resolved server path. It teaches information disclosure by accident rather than by design, and it hands students the exact directory layout, which short-circuits the depth-guessing the traversal hints are trying to teach. (4) OAuth login CSRF awards the flag to whichever session visits the callback link, which reads as a bug from the student's side. Reproduction: mint the attacker link in one browser profile, open it in a second profile (the natural way to simulate a victim) and complete the attack; the second profile gets the flag, the first profile's path page still shows the step as not captured (my path sat at 9/10 while the attack had visibly succeeded). The behavior is defensible, but nothing on the page tells the student which session earned it.
- Friction/confusion points: CSTI cannot be solved with HTTP requests alone in the naive way, because evaluation happens in the browser; with curl I had to load the lab page, read the page-bound token from the source, save the payload, and replay the beacon request by hand. That works and the claim box on each page explains the protocol honestly, but a student driving only Burp Repeater will stall until they understand that Repeater alone never triggers evaluation. The constructor challenge (rated Medium) is the hardest of the five CSTI labs in practice: the student must author the beaconing JavaScript string themselves, which is a bigger jump than the label suggests. The JWT algorithm confusion step is byte-sensitive in a way students will trip on: I extracted the published RSA public key from the page markup, signed with it, and was rejected, because the copy lost the trailing newline of the key text; copying the on-page block in a browser avoids this, but the rejection gives no hint that the key bytes were the problem. The API rate limit step note says "work through a sensible wordlist", but the actual success condition is a run of failed guesses followed by one correct login, and the correct password is sitting in the first step's output; a student who takes the note literally will brute force longer than the challenge intends. The log poisoning lab page itself prints the marker string and the exact read-back request on the page, which makes a Hard-rated challenge close to a copy exercise. There is no in-app way to reset a single challenge or a single student; clearing cookies is the only reset I could find.
- Hint quality (helpful? spoilery? useless?): Helpful overall, with a spoiler gradient that leans generous at level 3. Level 1 hints nudge without giving anything away (good). Level 2 hints teach the technique and usually name the Burp tool and the exact parameter to work on (very good for a lab that wants students to learn workflow, not just payloads). Level 3 hints are close to worked solutions: for several LFI challenges they describe the precise string manipulation to perform, and the CSTI basic lab's claim box prints the literal winning expression as part of explaining the beacon. For self-paced learning this is fine and even kind. For graded classroom use it is a problem: a student can open all three hints and finish most Easy and Medium challenges without forming a hypothesis. Per-challenge ratings: LFI traversal, filter bypass, double encode, nested deep: good ladders, level 3 spoilery but earned. LFI lang and config read: level 3 nearly dictates the request; fine for Easy. LFI log poison: the lab page spoils more than the hints do, so the ladder barely matters. CSTI basic: spoilery by design (payload printed on the page). CSTI filter bypass and attr: good ladders, technique-focused. CSTI constructor: the best ladder of the set; level 3 points at the mechanism and explicitly leaves the one creative step to the student. API path steps have no hint ladders of their own beyond the module cards, and the step notes sit at about level 1.5: directional, not spoilery.
- Difficulty fairness: Mostly fair. LFI runs 5 Easy, 3 Medium, 1 Hard and the curve inside the module feels right, except log poisoning is labeled Hard while the demo page hands over the marker and the read-back path, making it easier than two of the Mediums. CSTI runs 2 Easy and 3 Medium; constructor plays like a Hard for a first-timer, and stored (Easy) is correctly easy. The API Hacker path is labeled Intermediate and earns it: steps 1 to 3 are warm-ups, the JWT trio and the OAuth step are the real work, and algorithm confusion as step 9 is the right peak before the lighter CORS closer. One fairness caveat: several challenges silently depend on exactness (byte-exact key material, attempt counts, token freshness) where a near-miss looks identical to a wrong idea, so weaker students can burn a long time without feedback about which assumption failed.
- Burp-first feasibility: Strong for LFI and the API path, workable with caveats for CSTI. Every briefing is written around Proxy, Repeater, Intruder and Decoder, and my curl equivalents of those workflows succeeded on all 9 LFI challenges and all 10 path steps, including the Intruder-style brute force run for the rate limit step and the Repeater-style header edit for log poisoning. CSTI is the exception that proves the design: the intended flow is Burp's embedded browser, and the pages say so; a pure request-replay workflow needs the manual beacon step described above. Nothing in my assigned modules required a real browser beyond what the briefings themselves disclose, and the CORS path step even ships a prove endpoint so a request-only student can confirm the misconfiguration without a second origin.
- Suggestions (concrete): (1) Give the instructor a roster view: named or token-based student seats, a per-student progress grid, and a CSV or JSON export of captures with timestamps. Right now progress lives in an anonymous browser session, so I cannot track 30 students, cannot verify who did what, and cannot grade from the app at all. (2) Add a per-student reset (one challenge and one whole seat) that does not require clearing cookies, and a per-class reset that does not wipe other classes on a shared instance. (3) Persist progress across restarts, or at minimum show a banner when a restart has reset state; losing a full class's scoreboard to one reboot is not survivable in a graded setting. (4) Make flags and evidence harder to share: flags already differ between boots (I confirmed the same challenge produced different flag values before and after the reboot), but within one class on one boot, students share one flag set, so add per-seat flag values or require the certificate verification code as the hand-in instead of raw flags. (5) Ship the student deployment without the solutions material that sits next to the app in the repo; if students can read the install tree, every challenge is one search away from a full walkthrough. (6) Add a hint policy for graded mode: lock level 3 hints behind instructor release, or log hint usage per student so I can grade process, not just captures. (7) Rebalance two labels: log poisoning down to Medium (or remove the printed read-back request from its demo page to keep it Hard), and CSTI constructor up to Hard. (8) Finish fix mode for LFI and CSTI: the break-then-fix editor exists for other modules and shows "coming soon" for both of mine, and the fix half is where the classroom value doubles. (9) On the OAuth step, state plainly that the flag lands in the session that opens the callback link. (10) Trim the absolute server path out of the LFI error message, or make that leak an explicit, labeled part of one challenge. With (1), (2) and (3) done, I would run a class on this as-is; without them I would run it only as ungraded practice.
- Rating: 4
