# Student Review: Zero-Day Zoe (ctf-08)
- Modules tested: misconfig (10/10), session (6/6), api (5/5). All captures re-verified on the live instance after the ~01:37 UTC pool reboot; pre-reboot results were wiped with per-boot state and re-run from scratch post-reboot, so every result below is post-reboot verified. Target: http://127.0.0.1:18405/. Time to first flag: misconfig ~1 minute (GET /misconfig/debug?err=1), session ~1 minute into the module (fixation), api ~2 minutes in (mass assignment). Scripted clean re-run of all 21 took under 10 seconds of requests once the paths were known.
- What worked well: The intended technique is genuinely required for every challenge except the rate-limit one (see bugs). The git object walk is realistic (.git/HEAD to ref to objects/<2 chars>/<rest> and reading the commit diff), the PUT round trip is clean (201 on PUT, GET read-back awards), TRACE reflects, backup.zip is a real downloadable zip, and the X-Forwarded-For lockout bypass behaves exactly as the card describes (4 bad attempts from my IP returned 429, then the correct password with a spoofed X-Forwarded-For header won). Negative controls all blocked properly: cross-lab sid replay on leak-admin, no-cookie access on predictable/admin, random sid on legacy-admin, no-login on logoutdemo/secret, no-login on v2/users/3, plus .env.bak, debug?err=0, ..%2f.env, .git/config and a PUT path-traversal attempt all returned 404 or no award. No generic bare-claim endpoint exists; nothing falls without the exploit.
- Bugs found (with reproduction):
  1. env challenge hint L3 lies: it says "Read the ADMIN_API_TOKEN line in the response, that value is the flag", but GET /misconfig/.env returns ADMIN_API_TOKEN=<redacted> (and SESSION_SECRET=<redacted>). The flag IS awarded on the request, but silently in the plain-text response with no capture banner, so a student following the hint stares at a redacted line and misses the win. Either fix the hint or stop redacting.
  2. Cross-challenge interference, api: a successful POST /api/v1/login snapshots the user record's role into the app session. If you solve mass-assignment first (alice's role becomes admin in her record), then log in via v1, your session stays admin and api-version-bypass can no longer award (it requires a non-admin caller), while GET /api/v1/users/3 keeps answering 200 instead of 403. Fix: re-login via GET /api/login/alice to reset the snapshot. Repro: PATCH /api/me {"role":"admin"} as alice, POST /api/v1/login with her password, then GET /api/v2/users/3 as anyone. Students doing the module top to bottom will hit this with no explanation.
  3. Session credit binds to the app session cookie: winning requests made without carrying connect.sid (e.g. replaying an admin panel URL in a fresh browser/incognito, or a tool that drops it) still render the "Flag captured" banner on the page but earn zero scoreboard credit. I watched this happen on predictable (banner visible, scoreboard stuck at 2/6) and had to replay carrying both cookies. The session brief should say the app session cookie must stay attached.
  4. Rate-limit counter is shared per username across all sessions on the pool instance (in-memory, global). Once anyone has built 15+ attempts for alice, any later correct login hands out the flag with zero brute force. Repro post-my-run: POST /api/login {"username":"alice","password":"alice123"} with no wrong attempts in that request returned {"ok":true,"attempts":17} and the lab awarded the flag. CHEAT-WORKS on a shared instance. Scope the counter per session plus username to fix.
  5. urldemo: the admin's proxy-log entry is only seeded on first visit to /session/urldemo, so going straight to /session/urldemo/proxy-log shows an empty log. The card text does say to visit urldemo first, but students who deep-link the log get confused. Seed it at boot instead.
- Friction/confusion points: predictable on a busy pool is racy: each visit with an unknown lab_sid issues a new guest sid and the "admin signed in right after you" value shifts under concurrent players (I saw 1001, then 1003 within a minute), so the printed value can go stale between reading and replaying. Solo it is trivial. Also, curl -b with a jar that holds an old lab_sid can collide with a manual --cookie override; Express reads the jar's value first, so use a clean cookie header when swapping identities.
- Hint quality (helpful? spoilery? useless?): Helpful overall. The ladder structure works: L1 nudges, L2 teaches, L3 hands the payload shape. For a CTF player they border on spoilery (you can solve most challenges from the card alone), which is fine for a learning module but means flags rarely require the intended reasoning if you read everything. One actively wrong hint: env L3 (see bug 1). The exposure card correctly states the viewer page never awards and the flag only comes via the X-Pentrix-Flag response header, which saved me from a rabbit hole.
- Difficulty fairness: Fair. Easy challenges are single-request guesses a real attacker would try; Medium ones need one genuine insight (fixation cookie persistence, XFF spoofing, v1 to v2 path flip). The only unfair moment is bug 2 (order-dependent lockout of api-version-bypass) and bug 4 (shared-pool free flag). Both are fixable without changing intended difficulty.
- Burp-first feasibility: 100 percent feasible. Every attack is a Repeater edit (method change, header edit, path flip, cookie swap, query param). curl was faster for the repetitive ones (14 wrong guesses, sequential sid reads) and the payload blocks with copy buttons made Burp hand-offs easy. No challenge needed a real browser beyond reading pages.
- Suggestions (concrete):
  1. Fix the env L3 hint or stop redacting ADMIN_API_TOKEN in the response.
  2. On silently-awarded challenges (backup.sql, secret.txt download, PUT read-back, .env), add a one-line "flag awarded, check your scoreboard" note to the response, or render the banner anyway, so students see the capture moment.
  3. Scope the POST /api/login attempt counter per session plus username, not global per username, to kill the shared-pool free flag.
  4. In api-version-bypass, re-read the caller's role from their record at request time (or document that v1 login snapshots the role), so mass-assignment cannot permanently lock the challenge.
  5. Seed the urldemo admin proxy-log entry at boot, not on first page visit.
  6. Add one line to the session module brief: winning requests must carry your app session cookie or the scoreboard will not credit you.
- Rating: 1-5: 4
