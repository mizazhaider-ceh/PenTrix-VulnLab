# Student Review: Logger Liam (burp-06)
- Modules tested: cors (CORS Misconfiguration, 6 challenges), idor (Broken Access Control, 7 challenges)
- What worked well: All 13 challenges are solvable with Burp Community Proxy plus Repeater alone; no Pro features needed anywhere, and the one Intruder suggestion (cors-regex) is optional since Repeater handles a 3-entry origin list faster. The shared /cors/prove endpoint is the best teaching mechanic in either module: you submit an Origin, the server makes the request like a browser would, and shows you the exact response headers before awarding the flag, so you learn the browser's actual check instead of just header-spotting. The hint ladders name the right Burp tool for each step (Proxy to capture, Repeater to replay and mutate) and the IDOR cards show the endpoint plus the exact request shape to change. The scoreboard is honest: my jar went 0/201 to 13/201 exactly as I solved things, and replays do not inflate the count (re-running the same cors prove twice kept the score at 6/201 pre-reboot). Cheat resistance is good where tested: bare /cors/prove with no origin param shows only the form, an unknown vuln param returns 400, viewing your own profile or your own invoice awards nothing, unauthenticated /idor/admin returns 401 with no flag, and deleting an already-deleted comment returns 404 with no double award. The apikey-regen award check is genuinely strict: presenting someone else's key is not enough, the rotation has to have been done through the IDOR by your own session, which closes the "I was shown the key" shortcut.
- Bugs found (with reproduction):
  1. cors-subdomain /cors/prove gate is stricter than the actual vulnerability. Reproduction: request GET /cors/api/partner with header Origin: https://mine.trusted.pentrix.lab; the endpoint answers Access-Control-Allow-Origin: https://mine.trusted.pentrix.lab plus Access-Control-Allow-Credentials: true, which is exactly the vulnerable combination the challenge teaches. Then open /cors/prove?vuln=cors-subdomain&origin=https://mine.trusted.pentrix.lab; the page answers "Not vulnerable for this Origin" and no flag is awarded. The prove check requires the hostname to contain the literal string "evil", which the need text never mentions. Hint 2 even encourages the student to "swap in a subdomain label of your own choosing", so a student who follows the hint with their own label (mine, attacker, test) gets a silent fail despite demonstrating the vuln correctly. Verified on the fresh post-reboot instance, so it is not stale state.
  2. Pre-reboot, alice (id 2) had role admin on the shared instance, and every IDOR challenge whose guidance says "Log in as alice" (profile, admin, idor-download, idor-email-change, idor-apikey-regen, function-browse) silently awarded nothing, because the award logic requires a non-admin role. Reproduction from that session: logged in as alice, GET /idor/users/1, GET /idor/users/3, GET /idor/admin all rendered with no flag banner, while the same requests as bob (role user) awarded the flag. After the second reboot the fresh per-boot state shows alice as role user, matching the repo seed, so the earlier state was shared-instance bleed from concurrent activity on the pool. Root cause aside, the student-facing gap is real: the lab never tells students to sanity-check the "Signed in as ... role ..." line on the module page, so a student on a polluted instance can follow every instruction perfectly and get nothing with no explanation. I only found it by accident when debugging why the admin profile view did not award.
  3. Stale host in payload blocks and start texts. All six CORS payload blocks hardcode "Host: localhost:3000", the cors-expose-headers start text says to open http://localhost:3000/cors/expose, the idor-apikey-regen start text says to visit http://localhost:3000/idor/login/alice, and the idor-comment-delete start text says to visit http://localhost:3000/idor/login/bob, but the pool instance runs on 127.0.0.1:18401. Copying a block verbatim into Repeater sends the wrong Host. Harmless here (the server ignores Host) but a Burp-first learner wonders why the given block does not match their target, same bug class as the proto module's stale Host lines.
- Friction/confusion points:
  - cors-null hint 3 says to "collect the flag in the Burp proxy browser at /cors/prove?vuln=cors-null&origin=null". That URL is a plain GET; any browser (or Repeater) opens it. The "Burp proxy browser" wording makes a trivial step sound tool-specific and had me hunting for a reason the proxy mattered.
  - cors-reflect hint 3 says "Through Burp Proxy, let the attacker page (127.0.0.1 origin) fetch the victim API with credentials. The secret comes back in the response." This describes a cross-origin fetch demo from an attacker page through the proxy, which is fiddly and unnecessary; the actual graded path is Repeater headers plus /cors/prove. The hint reads like a different intended path than the how/start fields describe.
  - cors-regex hint 2 says to "Fire up Intruder (Sniper) over the Origin header with a small list of origins". Burp Community Intruder is throttled, and for 3 or 4 origins editing the header in Repeater is faster; the start text already describes the Repeater path. Suggesting Intruder here pushes learners toward an awkward approach for a problem that is really one regex insight.
  - cors-expose-headers start text says to click "Check session status" to capture the request, send it to Repeater, and "replay it with an attacker Origin". The button's fetch is same-origin and sends no Origin header at all, and the graded check does not need an attacker Origin either; the page works fine when you just replay and read the response headers, then open the prove URL. The instruction teaches a slightly wrong model of what proves the vuln.
  - IDOR Proxy setup is inconsistent: profile and admin start texts include the full "Start Burp Suite Community, set Proxy on 127.0.0.1:8080, point your browser through it" setup, but idor-download, idor-email-change and idor-comment-delete just say "in Burp Proxy" with no setup. A student who starts at the download card has no setup instructions on it.
  - The IDOR login buttons log you in with one GET; a Burp-first learner must have the proxy on BEFORE clicking, or the session cookies never pass through Burp and the Repeater steps silently lose the session. Worth one line on the module page or each card.
  - cors-expose-headers start says "Open http://localhost:3000/cors/expose through the Burp proxy browser", but Burp Community's built-in browser works fine for this; the confusing part is the stale port, not the browser choice.
- Hint quality (helpful? spoilery? useless?): Mostly helpful and well-staged. The cors-null ladder is a model: try values and watch the headers, learn that null is the magic string, then the exact prove URL. The CORS ladders correctly sequence nudge (what to watch in the response headers), technique (what the flaw class means), explicit (the payload shape). The IDOR ladders sequence well too: proxy the request, send it to Repeater, change the id. comment-delete hint 2 ("click it once with Burp intercepting, then send that POST to Repeater and try a different id") is the cleanest two-step in the module, and function-browse hint 3 is explicit about force-browsing without spoiling the exact path. Spoilery in the right places: the how fields and payload blocks hand over exact origins and payloads, but only after the hints have done the teaching. Misleading spots: cors-reflect hint 3 (the attacker-page-through-proxy demo), cors-null hint 3 ("Burp proxy browser" for a plain GET), cors-expose-headers start (replay with an attacker Origin), and the cors-subdomain need text which omits the hidden "evil" hostname requirement.
- Difficulty fairness: Fair overall. cors-wildcard-data and cors-expose-headers Easy land right (spot the header, prove it). cors-reflect, cors-null, cors-regex, cors-subdomain Medium are fair single-idea puzzles; the regex one is the most satisfying because the fuzz list makes the boundary bug visible. IDOR profile/admin/email-change/comment-delete Easy are fair. idor-download and function-browse Medium are fair; apikey-regen Medium is fair as the module capstone since it is a genuine two-step (rotate through the IDOR, then authenticate with the fresh key) with the strict anti-cheat check.
- Burp-first feasibility: 13/13 doable in Burp Community. Proxy captures the login GETs and the form POSTs (urlencoded, no special Content-Type work needed); Repeater replays and mutates everything, including the Origin header CORS probes and the user_id/id parameter swaps. The built-in browser handles the cookie flows. Nothing needs Intruder at scale, Comparer, Decoder beyond eyeballing, Sequencer, or any Pro-only feature. The lab's guidance names the right tool every time (Proxy to capture, Repeater to replay); it just over-suggests Intruder once (cors-regex) and over-specifies the browser twice (cors-null hint 3, cors-expose-headers start). Missing from the lab's own Burp guidance: a pointer to where the built-in browser lives for students without another proxied browser, and the reminder to proxy BEFORE clicking the login buttons.
- Suggestions (concrete):
  1. Fix the cors-subdomain prove check: drop the requirement that the hostname contain the literal string "evil", so any attacker-controlled subdomain under trusted.pentrix.lab that gets echoed with credentials earns the flag. If the requirement stays for some reason, document it in the need text and on the challenge page ("your invented subdomain must contain the string evil").
  2. Harden the IDOR challenges against shared-instance state bleed: add a one-line identity sanity check to every challenge start text ("check the module page shows Signed in as alice, role user; if the role says admin, log out and back in"), or make the award logic independent of the mutable role field. Students should never get silent no-awards while following the instructions exactly.
  3. Replace hardcoded "localhost:3000" in all payload blocks, Host lines and start texts with the instance host/port or a {HOST} placeholder plus a note that the Host value does not matter.
  4. Rewrite cors-reflect hint 3 to describe the real graded path (Repeater header checks plus /cors/prove) instead of the attacker-page-through-proxy demo; rewrite cors-null hint 3 to drop "Burp proxy browser" (it is a plain GET); fix the cors-expose-headers start text to stop instructing a replay "with an attacker Origin".
  5. Change cors-regex hint 2 to recommend editing the Origin header in Repeater (or qualify the Intruder suggestion: "a 3-entry list; Repeater is faster in Burp Community").
  6. Give every IDOR challenge card the same Proxy setup line profile/admin already have ("Burp Proxy on 127.0.0.1:8080, browser routed through it"), and add one line that the login-button clicks must happen through the proxy so the session cookies land in Burp.
  7. On the shared pool, state-changing exploits (email changes, key rotations, comment deletes) affect other testers; I restored the emails I changed during testing. Consider noting expected etiquette on the module page, or snapshotting per-session test data.
- Rating: 4
