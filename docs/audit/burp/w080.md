## crypto-key-in-js: Key in JavaScript

### Verdict
BURP-CLEAN. The exploit chain is plain HTTP plus offline AES decryption: GET the
served JavaScript bundle, read the hardcoded key, GET the challenge page, copy
the ciphertext, decrypt offline, then POST the plaintext to the solve endpoint.
No raw sockets, no binary bytes Burp would mangle, no curl-specific behavior,
no non-HTTP protocol. Every step maps to Proxy, Repeater, and Python.

### Tools: old -> new
- Old: `DT, P` (DevTools, Python)
- New: `BZ, DT, P` (Burp/ZAP first, DevTools kept, Python kept)
- Why: BZ leads the Burp-first voice; fetching app.js and submitting the solve
  POST are Repeater work. DT stays because the key is also readable in browser
  devtools sources. P stays because the AES-128-CBC decryption is done offline
  in Python. No wordlist tooling here (no W), the key is a literal constant in
  the bundle, not a secret to guess.

### Burp workflow steps
1. Set Burp Proxy as the browser proxy and browse to the Secure Notes vault
   note page (`/crypto/keyjs`). The page shows the ciphertext (hex) and links
   the served JavaScript bundle.
2. In Proxy history (or by clicking the link), fetch `/crypto/keyjs/app.js` and
   Send to Repeater. Read the `ENCRYPTION_KEY` constant, that is the flaw:
   a key the browser can read is a key the attacker can read.
3. Copy the ciphertext (hex) from the page into a local Python script. The IV
   is prepended to the ciphertext (first 16 bytes), so split it off and
   decrypt the rest with AES-128-CBC using the key from the JS.
4. Submit the vault note login form once with anything in it. In Proxy history,
   find `POST /crypto/keyjs/solve`, right-click, Send to Repeater.
5. In Repeater, replace the `plaintext` field with the decrypted note and send.
   The response shows the decrypted note page with the flag.
6. Intruder is not required; this is one key and one known ciphertext.

### Issues
- None blocking. Old tool tags (`DT, P`) and a curl one-liner as the starting
  point did not match the Burp-first voice (D16).

### Changes applied
- `modules/crypto/challenges/crypto-key-in-js.js` (vuln object only):
  - tools: `DT, P` -> `BZ, DT, P`
  - start: curl one-liner replaced with a Burp-oriented starting point
    (Proxy to the vault note page, open the linked app.js in Repeater, read
    the served JavaScript)
  - hints: now name the Burp steps (send app.js to Repeater and read the key
    constant; decrypt offline in Python; submit the plaintext with a Repeater
    POST to the solve endpoint); nudges only, no exploit pasted
  - how: Burp-flavored phrasing, same meaning
- Verified: `node --check` passes, zero em dashes in the diff, scratch server
  booted (DB_PATH=/tmp/burp-w080.db PORT=18080) with `GET /crypto#crypto-key-in-js`
  and `GET /crypto/keyjs` returning 200, plus `GET /crypto/keyjs/app.js`
  returning 200. Server killed afterwards.
- No changes to tests/ and no git push, per constraints.

## crypto-md5-crack: Crack the MD5

### Verdict
BURP-CLEAN. The exploit chain is plain HTTP plus an offline dictionary attack:
GET the challenge page for the leaked unsalted MD5 hash, GET the in-lab
wordlist, hash every candidate with MD5 until one matches, then POST the
recovered password to the login form. No raw sockets, no binary bytes Burp
would mangle, no curl-specific behavior, no non-HTTP protocol. Every step maps
to Proxy, Repeater, and wordlist tooling. W stays because hash cracking
genuinely needs it: the password must be found by hashing every wordlist entry
(the test helper does exactly this loop), so W is kept alongside BZ and P.

### Tools: old -> new
- Old: `W, P` (Wordlist, Python)
- New: `BZ, W, P` (Burp/ZAP first, Wordlist kept, Python kept)
- Why: BZ leads the Burp-first voice; fetching the hash and the wordlist and
  submitting the login POST are Repeater/Proxy work. W stays because the
  dictionary attack genuinely needs wordlist/hashcat tooling (an unsalted MD5
  of a dictionary word, cracked by hashing every candidate). P stays as the
  offline hashing helper.

### Burp workflow steps
1. Set Burp Proxy as the browser proxy and browse to the LegacyBox login page
   (`/crypto/md5`). The page shows the leaked unsalted MD5 hash of the demo
   account password and links the in-lab wordlist.
2. Fetch `/crypto/md5` and `/crypto/md5/wordlist.txt` in Repeater (or through
   the proxied browser) and copy both the hash and the wordlist locally.
3. Crack offline: hash every wordlist entry with MD5 (a short Python loop or
   hashcat with mode 0) until one matches the leaked hash.
4. Submit the login form once with anything in it. In Proxy history, find
   `POST /crypto/md5/login`, right-click, Send to Repeater.
5. In Repeater, set the `password` field to the cracked password and send.
   The response renders the "Welcome back" page with the flag.
6. Intruder is not required here either; the wordlist attack is done offline,
   one login attempt is all it takes.

### Issues
- None blocking. Old tool tags (`W, P`) and a curl two-liner as the starting
  point did not match the Burp-first voice (D16). W is genuinely needed and
  was kept, per the wordlist rule.

### Changes applied

    (Proxy to the LegacyBox login page, fetch the leaked hash and the
    wordlist in Repeater)
  - hints: now name the Burp steps (copy the leaked hash and the in-lab
    wordlist into Repeater tabs; hash every entry with MD5 until one matches;
    log in with it through Burp Proxy); nudges only, no exploit pasted
  - how: Burp-flavored phrasing, same meaning
- Verified: `node --check` passes, zero em dashes in the diff, scratch server
  booted (DB_PATH=/tmp/burp-w080.db PORT=18080) with `GET /crypto#crypto-md5-crack`
  and `GET /crypto/md5` returning 200, plus `GET /crypto/md5/wordlist.txt`
  returning 200. Server killed afterwards.
- No changes to tests/ and no git push, per constraints.
