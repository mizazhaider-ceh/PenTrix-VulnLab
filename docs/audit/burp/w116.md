# w116, Burp-first audit: data-xss (postMessage)

Challenge: `modules/postmsg/challenges/data-xss.js`
(id `data-xss`, "Unsanitized Message Data Rendered as HTML")

## Verdict

**BURP-CLEAN.** The exploit chain is browser-driven with Burp
delivering and observing, exactly the D16 pattern for postMessage labs.
No redesign needed.

## Why it stages cleanly with Burp Community

The victim page is ordinary browser HTML: a `message` listener renders
`event.data.html` into `innerHTML`, and the victim's own handler fires a
standard HTTP GET beacon (`/postmsg/beacon?v=data-xss&d=...&n=...`)
carrying its page-bound token. The award is a plain server response to
that beacon request.

Chain with Burp:

1. Point the lab browser at Burp Proxy.
2. Load `/postmsg/data-xss/attacker` (embeds the victim iframe).
3. Fire the payload (the Fire button, or `postMessage` from the
   DevTools console): the victim page renders the markup and its own
   handler fires the beacon with the page token.
4. The beacon request and the flag-bearing response both appear in
   Proxy > HTTP history.
5. Send the beacon to Repeater to inspect the `v`, `d`, `n` parameters,
   tweak, and re-fire. (Tokens are single-use per page load, so each
   fresh fire needs a fresh victim page load, which is itself observable
   in Proxy.)

Every step is Proxy, Repeater, browser, DevTools: all inside Burp
Community plus the browser.

## Tools old -> new

Old: `B, DT`
New: `BZ, B, DT`

`BZ` leads because the beacon capture and replay is the Burp work.
`B` and `DT` stay: the message itself is sent from the browser
console (DevTools) or the lab's attacker page, since postMessage is
inherently browser-driven.

## Burp workflow steps (for the writeup)

1. Start Burp Proxy and route the lab browser through it.
2. Open the attacker page `/postmsg/data-xss/attacker`.
3. Fire the payload at the victim iframe (Fire button or console
   `postMessage`).
4. In Proxy > HTTP history, find the GET to `/postmsg/beacon` and open
   the response: it carries the flag.
5. (Optional) Send the beacon to Repeater to study or re-fire the
   parameters.

## Issues found

None blocking. The only pre-audit problem was voice: `start` was a
`curl` one-liner (`curl -s http://localhost:3000/postmsg/data-xss | head -20`)
that never runs the actual exploit chain, and `how` pasted the payload
inline while `tools` omitted Burp entirely.
