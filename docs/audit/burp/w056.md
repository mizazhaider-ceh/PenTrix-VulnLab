## 1. upload-overwrite (Avatar overwrite, Medium)

**Verdict:** BURP-CLEAN

**Tools:** `C` -> `BZ, C`

**Burp workflow steps:**
1. Browse the challenge page and upload any avatar through the widget while Burp Proxy intercepts, or build the request directly in Repeater: `POST /upload/avatar?user=alice` with a raw body of your choosing.
2. Send the intercepted request to Repeater.
3. In Repeater, change the `user` query parameter to `bob` and resend.
4. Open `GET /upload/avatar/bob` in the browser: it now serves your bytes, proving Bob's avatar was overwritten and capturing the flag.

**Issues:** none. Plain raw-body POST over standard HTTP, query-string parameter for the target user, no multipart encoding to fight, no byte-level tricks. Burp handles raw bodies natively.

**Changes applied:** tools `C` -> `BZ, C`; `start` rewritten Burp-first (Repeater POST to `/upload/avatar?user=bob`, then GET the avatar to confirm, no curl one-liner); hint 2 now names the Burp step (Proxy intercept, send to Repeater, change the username in the query string); hint 3 keeps KEY INSIGHT, Burp-flavored; `how` is Burp-flavored and tool-neutral. Verified: `node --check` passes on the file, git diff shows zero em dashes, scratch server boot (DB_PATH=/tmp/burp-w056.db, PORT=18056) returned 200 on `/upload`.

**Burp workflow steps:**

## General notes

- Both exploit chains are raw request bodies over POST with the interesting input in the query string. That is the best-case shape for D16: Burp Repeater reproduces them byte-for-byte with zero transformation risk.
- The on-page fetch widgets already mirror the raw-body upload form, so Proxy capture is also a viable starting path and hint 2 of upload-overwrite mentions it.
- Nothing in either challenge requires raw sockets, malformed HTTP, or curl-specific behavior, so no redesign was considered for either.
