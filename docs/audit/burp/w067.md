# Burp-first audit: w067, no-state (Login CSRF, Missing state Parameter)

- Module: oauth
- Challenge file: `modules/oauth/challenges/no-state.js`
- Routes: `GET /oauth/no-state` (lab page), `GET /oauth/no-state/attacker` (code minting for the attacker), shared `GET /oauth/client/callback` (exchanges any code, never checks state)

## Verdict

**BURP-CLEAN.** The full exploit chain works with plain, standard HTTP through Burp Proxy and Repeater. Log in to the IdP as bob, request the attacker link generator, lift the malicious callback link from the Proxy history response, then replay that callback request in a session whose IdP user is alice. No raw sockets, no malformed HTTP, no timing dependency, no byte mangling, no curl-specific behavior, no non-HTTP protocol. Community edition is enough.

## Tools

Old: `B` (Browser)
New: `BZ, B` (Burp/ZAP first, then Browser)

The exploit is two GET requests with cookies, plus one replayed GET. Burp is the recommended tool because the natural workflow is Proxy to mint the attacker's code, then Repeater to replay the malicious callback link as the victim. Plain browser also works (two browser profiles), so `B` stays as secondary.

## Burp workflow steps

1. Proxy: route your browser through Burp. Log in to the IdP as bob via `GET /oauth/login/bob`.
2. Proxy: open `GET /oauth/no-state/attacker`. The response renders the malicious login link (`/oauth/client/callback?code=<code>`) minted for bob's own account.
3. Repeater (or a second browser profile proxied through Burp): log in to the IdP as alice (`GET /oauth/login/alice`) so the session belongs to the victim.
4. In alice's session, replay the malicious callback link. The shared callback exchanges the code with no state check and logs alice's client session in as bob. The flag is awarded on that response.
