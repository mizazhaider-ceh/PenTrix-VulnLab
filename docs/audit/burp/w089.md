# Burp-first audit w089: change-pass-noverify

Challenge: Password Change Without Current Password (`/auth/change-password`)
Module: auth. Route trust check only: POST changes the account password while a session
exists, never asking for the old password.

## Verdict

BURP-CLEAN

## Tools

- Old: `B` (browser only, plus a curl one-liner start)
- New: `BZ, B` (Burp/ZAP first, browser second; curl tag removed from the start)

## Burp workflow steps

1. Proxy: set Burp as the browser proxy (127.0.0.1:8080) and import the CA cert.
2. Browse to `/auth/login` through the Proxy and log in as bob (bob123). Confirm
   the session cookie (`connect.sid`) in the Proxy HTTP history.
3. Browse to `/auth/change-password` through the Proxy. Note the form has no
   current-password field.
4. In Proxy, right-click the POST to `/auth/change-password` and send it to
   Repeater.
5. In Repeater, set a new `newPassword` value and send. The 200 response shows
   "Password changed" and renders the flag. No old password is ever required.

## Issues found

None. The exploit chain is two plain form POSTs (login, then change-password)
carried by a standard session cookie. Burp's Proxy captures it untouched and
Repeater replays it byte for byte. No raw sockets, no mangled bytes, no
curl-specific behavior, no non-HTTP protocol.

One note for accuracy: flags render as `PENTRIX{<32 hex>}`, not `FLG-...`.
My initial curl grep for `FLG-` missed the flag on a successful POST; the second
check confirmed `PENTRIX{...}` in the response.
