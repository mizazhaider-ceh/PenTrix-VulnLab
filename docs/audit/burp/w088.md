# w088 verdicts

## auth/brute-force

- Verdict: BURP-CLEAN
- Tools: "B, P" -> "BZ, B"
- Burp workflow:
  1. Open http://localhost:3000/auth/login in a browser with Burp Proxy intercepting, and submit the sign-in form once with any password.
  2. In Burp Proxy history, find the POST /auth/login request, right-click it, and send it to Intruder.
  3. In Intruder, choose a Sniper attack and place the single payload marker (§) around the password field value (leave username=alice fixed). Load a short weak-password wordlist as the payload set (e.g. a custom list containing guesses like password, letmein, qwerty, alice1, alice123).
  4. Start the attack with the session cookie intact across all requests (Intruder reuses the cookie from the captured request; do not start a fresh session mid-attack, because the failed sign-in counter is per browser session and the flag needs 5+ failures in one session before the successful login).
  5. Sort results by response length or filter for the response containing "Welcome back" / the flag box. That request used the correct password. If the correct password landed before 5 failures accumulated, re-run: first make 5 failed attempts in Repeater with the same cookie, then send the correct password once.
  6. In Repeater, replay the successful login POST (same session cookie, 5+ failed attempts recorded) to observe the flag box on the dashboard page.
- Issues: none. Plain form-urlencoded POST /auth/login, no rate limiting, no lockout, no CAPTCHA, no raw-socket or byte-mangling behavior. The only Burp-relevant gotcha is session affinity: the counter lives in the server session, so the attacker must keep one cookie through the attack; Intruder does this by default.
