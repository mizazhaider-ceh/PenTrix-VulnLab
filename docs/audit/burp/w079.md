# w079 verdict

## crypto-hash-ext

- Verdict: BURP-CLEAN
- Tools: "P, C" -> "BZ, P"
- Burp workflow:
  1. In Burp Proxy, open the challenge page at /crypto/mac in the browser and submit the signing form with msg=role=user. Let the GET /crypto/mac/sign request flow through Proxy.
  2. Send the sign response (JSON with the 64-hex MAC) to Repeater. The digest is the leaked Merkle-Damgard internal state after the server absorbed the 16-byte secret plus your message.
  3. Build the glue padding for 16 + len("role=user") bytes by hand or in a tiny script: a 0x80 byte, zero bytes, then the total bit length as a 64-bit big-endian number. Burp Decoder cannot restore a SHA-256 compression state, so this step is a small script.
  4. In that script, restore the digest as your SHA-256 compression state and continue the hash with ";admin=1". The script outputs the extended message as hex (original + glue padding + suffix) and the forged MAC.
  5. In Repeater, POST the form to /crypto/mac/verify with fields msghex=<extended hex> and mac=<forged MAC>. The response renders "Length extension worked" with the flag box.
  6. Optional: confirm the MAC value in Repeater's response before submitting by comparing with a wrong MAC first (the page tells you MAC valid: false), to prove the flag comes from the forged MAC, not the form.
- Issues: none. The whole chain is standard HTTP: a GET sign endpoint returning JSON, and a POST form verify endpoint that takes hex-encoded ASCII fields. No raw sockets, no binary bodies Burp would mangle, nothing curl-specific (the old start was only a curl one-liner for the sign endpoint, which Burp handles identically via the page form or Repeater). The only non-Burp step is the SHA-256 state continuation, which a tiny script is the sane path for (hence keeping P).
