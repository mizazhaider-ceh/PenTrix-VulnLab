# Burp Audit w062: race-register (Duplicate Username Registration) and race-stock (Oversell the Stock)

## Challenge 1: race-register (Duplicate Username Registration)

### Verdict
BURP-CLEAN. The full exploit chain is a standard urlencoded HTTP POST to `/race/register`. Burp Intruder's concurrent-request mode reproduces the parallel-burst race reliably, and the tests use plain concurrent HTTP bursts (`burstN`), no raw-socket tricks. No redesign needed. Flag award logic and the flag secrecy model were left untouched.

### Tools
old: `P, C` (python, curl)
new: `BZ, C` (Burp/ZAP, curl)

Rationale: the attack is N copies of the same form POST fired at the same instant. Burp Proxy captures the signup request, Repeater confirms the baseline, and Intruder fires the concurrent burst. Curl stays as the secondary tag for the sequential baseline checks.

### Burp workflow
1. Proxy your browser through Burp and open GET `/race/register`.
2. Submit the signup form once with a fresh username; in Proxy HTTP history, find the POST to `/race/register` and send it to Repeater.
3. In Repeater, replay the signup for a brand-new username and confirm the response page shows "Account created" and the accounts table lists the name once. This is the sequential baseline.
4. Send the POST to Intruder. Keep the body parameters fixed (same username on every thread), set the concurrent-request count high (e.g. 10), and start the attack so all requests hit the check-to-insert gap together.
5. After the attack, reload GET `/race/register` and count rows: two rows with the same username proves the uniqueness check lost the race, and one of the parallel responses carries the flag box and fix panel.

### Issues
None blocking. Notes for the operator:
- The race window is the `await sleep(WINDOW())` between the uniqueness check and the insert. Sequential signups are correctly rejected with "Username taken", so only a true parallel burst awards.
- Intruder Community's concurrent mode is sufficient: tests use `burstN(c, '/race/register', ..., 5)` with five parallel requests and award reliably.
- Reset lab state via GET `/race/reset` before the burst so the username is free; a leftover duplicate from an earlier run answers "Username taken" instead of racing.

### Changes applied
Edited the `vuln` object in `modules/race/challenges/race-register.js`:
- `tools`: `"P, C"` to `"BZ, C"`.
- `start`: replaced the curl one-liner with a Burp-oriented starting point (capture the POST, send to Intruder, run with concurrent requests enabled).
- `hints`: rewritten to name the Burp step at each stage (Repeater baseline, Intruder concurrent burst, reload the signup page to count duplicates). Nudges only, no exploit pasted.
- `how`: tool-neutral wording describing the parallel burst against the check-then-insert gap.

No redesign proposal needed (verdict is CLEAN).

## Challenge 2: race-stock (Oversell the Stock)

### Verdict
BURP-CLEAN. The full exploit chain is a standard urlencoded HTTP POST to `/race/stock/buy`. Burp Intruder's concurrent-request mode reproduces the parallel-burst race reliably, and the tests use plain concurrent HTTP bursts (`burstN`), no raw-socket tricks. No redesign needed. Flag award logic and the flag secrecy model were left untouched.

### Tools
old: `P, C` (python, curl)
new: `BZ, C` (Burp/ZAP, curl)

Rationale: the attack is N copies of the same buy POST fired at the same instant. Burp Proxy captures the buy request, Repeater confirms the single-order baseline, and Intruder fires the concurrent burst. Curl stays as the secondary tag for the sequential baseline checks.

### Burp workflow
1. Proxy your browser through Burp and open GET `/race/stock`, which shows the live stock and sold counts.
2. Submit the buy form once with qty=5; in Proxy HTTP history, find the POST to `/race/stock/buy` and send it to Repeater.
3. In Repeater, replay one order of 5 after a lab reset and confirm the page shows "Total sold: 5" with no flag. This is the sequential baseline.
4. Send the POST to Intruder. Keep qty=5 on every thread, set the concurrent-request count high (e.g. 10), and start the attack so every order passes the stock check against the same pre-sale level.
5. Reload GET `/race/stock` (or read the response pages): total sold above 5 proves the shop oversold, and the awarding response carries the flag box and fix panel.

### Issues
None blocking. Notes for the operator:
- The race window is the `await sleep(WINDOW())` between the stock check and the decrement. One order of 5 never oversells, so only a true parallel burst awards.
- Intruder Community's concurrent mode is sufficient: tests use `burstN(c, '/race/stock/buy', { qty: '5' }, 10)` with ten parallel requests and award reliably.
- Reset lab state via GET `/race/reset` before the burst: after a single baseline order of 5, stock is 0 and further sequential orders are rejected as "Out of stock".

### Changes applied
Edited the `vuln` object in `modules/race/challenges/race-stock.js`:
- `tools`: `"P, C"` to `"BZ, C"`.
- `start`: replaced the curl one-liner with a Burp-oriented starting point (capture the POST, send to Intruder, run with concurrent requests enabled).
- `hints`: rewritten to name the Burp step at each stage (Repeater baseline, Intruder concurrent burst, check total sold above 5). Nudges only, no exploit pasted.
- `how`: tool-neutral wording describing the parallel burst against the check-then-decrement gap.

No redesign proposal needed (verdict is CLEAN).
