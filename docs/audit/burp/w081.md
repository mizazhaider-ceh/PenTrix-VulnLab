# Burp audit w081: crypto-rand-pin (Predictable Reset PIN)

## Verdict
BURP-CLEAN. The full exploit chain is plain HTTP form traffic: one POST to
generate the PIN, then repeated POSTs of candidate PINs to the verify form with
no rate limiting and no lockout. No raw sockets, no binary bytes Burp would
mangle, no curl-specific behavior, no non-HTTP protocol. Brute-forcing a
6-digit space is Intruder's native job.

## Tools: old -> new
- Old: `P, C` (Python, curl)
- New: `BZ` (Burp/ZAP first)
- Why: the verify POST is captured via Proxy and brute-forced with Intruder's
  null payload set generating 000000-999999. Curl is no longer needed as a
  starting point, so C drops; Python is no longer needed as a helper, so P
  drops.

## Burp workflow steps
1. Set Burp Proxy as the browser proxy and browse to
   `http://localhost:3000/crypto/pin`. The page explains a 6-digit reset PIN is
   drawn from Math.random() and there is no rate limiting.
2. Click "Generate reset PIN" (the POST to `/crypto/pin/generate` returns 302).
3. Submit the verify form once with anything in it. In Proxy history, find
   `POST /crypto/pin/verify`, right-click, Send to Intruder.
4. In Intruder, mark the `pin` parameter as the attack position. Use payload
   type "Numbers", range 0-999999, min integer digits 6, or a null payload set
   generating 000000-999999.
5. Start the attack. Guesses are `application/x-www-form-urlencoded` posts; the
   challenge confirms no throttling (the test suite asserts 60 rapid guesses
   all return clean 401s).
6. Watch for the single 200 response among the 401s. Open it: it renders the
   "Reset authorized" page with the flag.

## Issues
- None blocking. Old tool tags (`P, C`) and a curl one-liner as the starting
  point did not match the Burp-first voice (D16).

## Changes applied
- `modules/crypto/challenges/crypto-rand-pin.js` (vuln object only):
  - tools: `P, C` -> `BZ`
  - start: curl one-liner replaced with a Burp-oriented starting point
    (Proxy to the page, click Generate, send the verify POST to Intruder,
    attack the PIN field with a null payload generating 000000-999999,
    look for the 200)
  - hints: now name the Burp steps (load the verify POST into Intruder,
    brute-force the PIN space, watch for a 200 among the 401s); nudges only,
    no exploit pasted
  - how: Burp-flavored phrasing, same meaning
- Verified: `node --check` passes, zero em dashes in the diff, scratch server
  booted (DB_PATH=/tmp/burp-w081.db PORT=18081) with `GET /crypto/pin`
  returning 200, `POST /crypto/pin/generate` returning 302, and
  `POST /crypto/pin/verify` with a wrong PIN returning 401. Server killed
  afterwards.
- No changes to tests/ and no git push, per constraints.

# Burp audit w081: crypto-xor-crib (XOR Crib Dragging)

## Verdict
BURP-CLEAN. The full exploit chain is standard HTTP: a GET that renders the
ciphertext hex in a page payload block, offline crib-dragging against the known
header `{"user":"` (key lengths 1-12, decrypted in Python), then a form POST of
the recovered plaintext to `/crypto/xor/solve`. No raw sockets, no binary
bytes Burp would mangle, no curl-specific behavior, no non-HTTP protocol. Copy
via Proxy, compute in Python, submit via Repeater.

## Tools: old -> new
- Old: `P` (Python)
- New: `BZ, P` (Burp/ZAP first, Python kept as a helper)
- Why: the ciphertext capture and the final plaintext submission are Burp
  work (Proxy, Repeater); the XOR key derivation itself is done offline in
  Python, so P stays as a genuine helper.

## Burp workflow steps
1. Set Burp Proxy as the browser proxy and browse to
   `http://localhost:3000/crypto/xor`. The page shows the ciphertext as hex in
   a payload block, states the key is a short repeating XOR key (length 1-12),
   and gives the known plaintext header `{"user":"`.
2. Copy the ciphertext hex from the payload block (the Copy button), or grab
   it from the proxied GET response in Proxy history.
3. Offline in Python: XOR the crib against the ciphertext for each candidate
   key length 1-12, derive each candidate key, decrypt, and keep the one that
   yields valid JSON.
4. In Proxy history, find `POST /crypto/xor/solve`, right-click, Send to
   Repeater. Replace the `plaintext` field with the recovered document and
   send.
5. Response 200 renders "Plaintext recovered" with the flag. A wrong guess
   returns 400.

## Issues
- None blocking. Old tool tag (`P`) alone and a curl one-liner as the
  starting point did not match the Burp-first voice (D16).

## Changes applied
- `modules/crypto/challenges/crypto-xor-crib.js` (vuln object only):
  - tools: `P` -> `BZ, P`
  - start: curl one-liner replaced with a Burp-oriented starting point
    (Proxy to the page, copy the ciphertext hex, do the crib-drag offline,
    submit through Repeater)
  - hints: still crypto-math nudges for the crib-drag, with the final hint
    naming the Repeater submission step; nudges only, no exploit pasted
  - how: Burp-flavored phrasing, same meaning (copy via Burp, derive in
    Python, submit through Repeater)
- Verified: `node --check` passes, zero em dashes in the diff, scratch server
  booted (DB_PATH=/tmp/burp-w081.db PORT=18081) with `GET /crypto/xor`
  returning 200, and `POST /crypto/xor/solve` with a wrong plaintext returning
  400. Server killed afterwards.
- No changes to tests/ and no git push, per constraints.
