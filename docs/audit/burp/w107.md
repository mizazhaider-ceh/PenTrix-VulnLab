# w107 Burp Audit: cors-expose-headers (Exposed Admin Token Header)

## Verdict
BURP-CLEAN. The full exploit chain works with Burp Suite Community (Proxy, Repeater) plus a standard browser for the actual cross-origin read. Origin header manipulation is a plain Repeater edit, the vulnerable endpoint is a simple GET with no preflight, and the cross-origin impact demonstration is done in the browser through the shared /cors/prove page. No raw sockets, no Burp-mangled bytes, no curl-specific behavior, no non-HTTP protocol. FLAG BAR and FLAG SECRECY are preserved (the endpoint itself never awards; only the prove check does).

## Tools old -> new
- Old: `B`
- New: `BZ, B`

## Burp workflow steps
1. Proxy: open `http://localhost:3000/cors/expose` in the Burp browser and click "Check session status". The captured `GET /cors/api/token` request is sent to Repeater.
2. Repeater: replay the request with an added `Origin: https://evil.com` header. The response shows `Access-Control-Allow-Origin: *`, `Access-Control-Expose-Headers: X-Admin-Token`, and a live `X-Admin-Token` value. The endpoint answers any Origin the same way, so the Origin header is optional proof of the "any origin" claim.
3. Browser (proxied through Burp if desired): visit `/cors/prove?vuln=cors-expose-headers&origin=https://evil.com`. The page makes a real request with the attacker Origin, inspects the response headers the same way a browser would before allowing a cross-origin read, confirms the header combo, and awards the flag. This stands in for the attacker page on evil.com reading the exposed header with `fetch` and `response.headers`.
4. Intruder is not needed here; a single Repeater request proves the header combo.

## Issues
- The page template still carries a "Try it raw" `payloadBlock` with a curl one-liner (`curl -si http://localhost:3000/cors/api/token`). Harmless: it is an optional raw view of the endpoint, not part of the exploit chain, and nothing about it requires curl. Left in place because this audit is limited to the vuln object.
- The `X-Admin-Token` header value is random per boot and only exists in memory. This is fine for Burp work: Repeater shows the value, and the prove endpoint reads it server-side, so no token needs to be captured or replayed by the attacker.

## Changes applied
In `modules/cors/challenges/cors-expose-headers.js` (vuln object only):
- `tools`: `B` -> `BZ, B` (BZ first).
- `start`: replaced the curl one-liner with a Burp-oriented starting point: open the challenge page through the Burp proxy browser, capture the session API request, send it to Repeater, and replay it with an attacker Origin to read the response headers.
- `hints`: rewritten as Burp-step nudges (Repeater header inspection, the Expose-Headers whitelist, then the prove run). No exploits pasted.
- `how`: Burp-flavored: confirm the header combo in Repeater, then prove it in the browser at the /cors/prove URL.
