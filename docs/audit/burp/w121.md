# w121 Burp Audit: csrf-data (JSONP Data Theft) and filter-bypass (Callback Filter Bypass)

## Challenge 1: csrf-data, JSONP Data Theft

### Verdict
BURP-CLEAN

### Tools old -> new
`B, DT` -> `BZ, B`

`BZ` now leads since the full chain runs through Proxy and Repeater. `B` stays: a real browser loads the attacker page. `DT` dropped: DevTools inspection is not needed, Proxy HTTP history shows the feed pull and the beacon POST.

### Burp workflow steps
1. Proxy your browser through Burp and browse to `/jsonp/attacker`. The page plays the role of evil.example: a plain `<script>` tag pulls `/jsonp/data?callback=steal` cross-origin, and the callback beacons the data with `fetch` to `/jsonp/beacon`.
2. In Proxy HTTP history, open the `/jsonp/data` response: the callback argument carries the user object including the per-session `secret`.
3. Find the POST to `/jsonp/beacon` in Proxy history, send it to Repeater, and replay it. The beacon carries the stolen secret, so the response returns `{ ok: true, flag }` and the scoreboard marks the challenge captured.
4. Pure-Repeater alternative: GET `/jsonp/data?callback=steal` with the session cookie, copy the secret from the response, then POST `{"secret":"..."}` to `/jsonp/beacon`. Same result, verified against the scratch server.

### Issues
- Old `start` was a curl one-liner that did not fit the Burp-first doctrine.
- `tools` lacked the `BZ` tag even though the chain is fully Proxy/Repeater compatible.

### Changes applied
File: `modules/jsonp/challenges/csrf-data.js` (vuln object only)
- `tools`: `"B, DT"` -> `"BZ, B"`
- `start`: Burp-oriented (browse to /jsonp/attacker through Proxy, watch the script-tag pull and the beacon, replay the beacon in Repeater). No curl one-liner.
- `hints`: rewritten to name Burp steps (nudges only, no exploits): proxy the browser and open the attacker page, read the secret in the /jsonp/data Proxy response, find the beacon POST and replay it in Repeater.
- `how`: Burp-flavored description of the chain (attacker page pulls the feed and beacons the secret; beacon replay in Repeater works too).

Verification: `node --check` passes; zero em dash characters in the diff; scratch server (`DB_PATH=/tmp/burp-w121.db PORT=18121`) served `/jsonp`, `/jsonp/attacker`, and `/jsonp/filtered?callback=test` with HTTP 200; the full Repeater-style chain (feed request with session cookie, secret extraction, beacon POST) was executed against the scratch server and the beacon returned the flag. Server stopped afterwards. Tests (`tests/jsonp.test.js`) were not modified.

### Flag secrecy notes
The secret is per-session (`jsonpSecret`), rotates after a valid beacon, and forged beacons are rejected with 400. The flag is only issued by the server-side `award()` call. No redesign needed: FLAG BAR and FLAG SECRECY preserved.

## Challenge 2: filter-bypass, Callback Filter Bypass

### Verdict
BURP-CLEAN

### Tools old -> new
`B` -> `BZ, B`

`BZ` now leads since the filter probing, token extraction, and beacon all happen in Repeater with standard HTTP GETs. `B` stays: the winning callback is meant to be loaded as a script tag on a page the user controls, and the Burp browser covers that.

### Burp workflow steps
1. Browse to `/jsonp/filtered?callback=test` through Burp Proxy and send the request to Repeater. The feed reflects the callback in a JavaScript function call and embeds a per-session token.
2. In Repeater, probe the filter: `callback=alert(1)` returns 400, proving the blocklist is literal and only bans the typed word.
3. Rebuild the banned word at runtime by joining string pieces, so the filter never sees the literal text; the feed returns 200. This request also records the bypass attempt server-side.
4. Extract the `token` from the 200 response in Repeater, then GET `/jsonp/beacon-xss?v=filter-bypass&n=<token>`. The beacon returns the flag and the scoreboard marks the challenge captured. Verified against the scratch server with a session cookie.
5. End-to-end alternative: load the winning callback as a `<script>` tag on a page you control in the Burp browser (the pattern shown on the blocked page), so the payload executes and beacons the token itself.

### Issues
- Old `start` was a bare curl one-liner that showed nothing about the filter behavior and did not fit the Burp-first doctrine.
- Old `how` pasted a concrete payload example; replaced with a Burp-flavored description (no exploit paste).
- `tools` lacked the `BZ` tag even though the chain is standard GET traffic fully Repeater compatible.

### Changes applied
File: `modules/jsonp/challenges/filter-bypass.js` (vuln object only)
- `tools`: `"B"` -> `"BZ, B"`
- `start`: Burp-oriented (browse to the feed through Proxy, send to Repeater, confirm reflection, then probe the filter: try the banned word, read the 400, rebuild it at runtime). No curl one-liner.
- `hints`: rewritten to name Burp steps (nudges only, no exploits): send the banned word in Repeater and read the 400, rebuild it at runtime and watch the 200 come back, extract the token and beacon it.
- `how`: Burp-flavored description of the chain (defeat the blocklist in Repeater with runtime concatenation, read the token, beacon it); the concrete payload example was removed.

Verification: `node --check` passes; zero em dash characters in the diff; scratch server (`DB_PATH=/tmp/burp-w121.db PORT=18121`) served all probed endpoints with HTTP 200; the full Repeater-style chain (concat callback feed request with session cookie, token extraction, beacon GET) was executed against the scratch server and the beacon page contained the flag. Server stopped afterwards. Tests (`tests/jsonp.test.js`) were not modified.

### Flag secrecy notes
The token is per-session (`jsonpNonce` for filter-bypass). Token-less beacons are rejected with 400, and the beacon additionally requires a recorded concatenation attempt in the session, so plain callbacks earn nothing. The flag is only issued by the server-side `award()` call. No redesign needed: FLAG BAR and FLAG SECRECY preserved.
