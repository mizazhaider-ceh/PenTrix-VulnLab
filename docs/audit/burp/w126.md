# w126 verdicts

## hostheader/host-ssrf

- Verdict: BURP-CLEAN
- Tools: "C" -> "BZ, C"
- Burp workflow:
  1. Set Burp Proxy as the browser proxy and visit /hostheader/status. The page shows the server-side fetch target built from the Host header and names the loopback-only agent's address.
  2. Send the GET /hostheader/status request to Repeater (right-click > Send to Repeater).
  3. In Repeater, edit the Host header so the server's fetch target points at the internal agent's address instead of the public site, then send the request.
  4. Observe the response: the "Upstream response" block now shows the internal agent's JSON secrets (db_password, admin_api_key) and the flag box renders.
- Issues: none. The attack is a single header edit on a normal GET; Burp Repeater sends headers verbatim and does not normalize them.
- Changes applied: vuln object in modules/hostheader/challenges/host-ssrf.js updated. tools now "BZ, C" (Burp first). start rewritten as a Burp-oriented starting point ("Open /hostheader/status in the browser with Burp Proxy on, send the request to Repeater, then edit the Host header in Repeater and re-send until the upstream response shows the internal agent secrets.", no curl one-liner). hints ladder now names the Burp step (send to Repeater, edit Host in Repeater, think about whose network the fetch runs from); no exploit pasted. how made Burp-flavored: "In Burp Repeater, send GET /hostheader/status with Host: 127.0.0.1:13919 so the server fetches the loopback-only internal agent for you." (the address and port are already disclosed on the challenge page itself).
- Verification: node --check passes. grep for em dash over the challenge file: zero. Scratch server (DB_PATH=/tmp/burp-w126.db PORT=18126 node app.js) returned HTTP 200 for /hostheader (both challenge links resolve here). GET /hostheader/status with Host: 127.0.0.1:13919 returned a page containing ak-internal- secrets and the flag path, confirming the end-to-end chain over plain HTTP. Server killed afterwards (only my instance, other workers' instances untouched). Note: the internal agent port was already bound by another worker's live instance on this VM, so the fetch reached that loopback agent; the mechanism verified is identical.

## hostheader/host-xforwarded

- Verdict: BURP-CLEAN
- Tools: "C" -> "BZ, C"
- Burp workflow:
  1. Set Burp Proxy as the browser proxy, visit /hostheader/forgot-xfwd, and submit the form with any email address. Intercept the POST /hostheader/forgot-xfwd request (Proxy > Intercept).
  2. Send the intercepted POST to Repeater. In Repeater, add a forwarded-host header (X-Forwarded-Host or X-Host-Override) naming a domain you control, then send the request.
  3. Observe the response: the lab email view now shows the reset link built from your forged header, carrying a valid token.
  4. Copy the token from the poisoned reset link and request /hostheader/evil-collect?token=<token> in Repeater (or the browser); the collector renders the flag box.
- Issues: none. Adding a custom request header and reading a token out of an HTML response are core Repeater operations; no raw sockets, no malformed HTTP, no bytes Burp would mangle.
- Changes applied: vuln object in modules/hostheader/challenges/host-xforwarded.js updated. tools now "BZ, C" (Burp first). start rewritten as a Burp-oriented starting point ("Open /hostheader/forgot-xfwd in the browser with Burp Proxy on, submit the form, send the POST to Repeater, add a forwarded-host header in Repeater and re-send. Read the token from the lab email view, then request /hostheader/evil-collect with that token.", no curl one-liner). hints ladder now names the Burp step (capture the POST, send to Repeater, add the header, re-send, carry the token to the collector); no exploit pasted. how made Burp-flavored: "In Burp Repeater, POST /hostheader/forgot-xfwd with X-Forwarded-Host: evil.com (or X-Host-Override: evil.com), then request /hostheader/evil-collect carrying the token from the poisoned reset link."
- Verification: node --check passes. grep for em dash over the challenge file: zero. Scratch server (DB_PATH=/tmp/burp-w126.db PORT=18126 node app.js) returned HTTP 200 for /hostheader; the existing test suite covers the full poison-and-collect chain over standard HTTP (poisoned X-Forwarded-Host and X-Host-Override both award, unpoisoned does not). Server killed afterwards (only my instance, other workers' instances untouched).
