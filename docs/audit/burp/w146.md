# w146 Burp-first audit: crlf-log, verb-tamper

## 1. crlf-log (CRLF Log Injection)

### Verdict
BURP-CLEAN. The full exploit chain works through Burp Suite Community with
Proxy + Repeater. Key check on the CRLF question: the test sends CRLF
percent-ENCODED (`%0d%0a`) inside the query string, and Express URL-decodes
it before logging. Burp Repeater sends the request line raw and does not
normalize percent-encoded bytes in the path/query, so it reproduces the
test identically. No literal CRLF is needed in a header value and no request
smuggling tricks are involved, so Burp never strips or mangles anything.
Session identity travels in a normal session cookie (`req.session.crlf_probe`
holds the injected ref); the flag awards on GET /http/admin/log only when
this session's probe is in the log AND rendered lines outnumber stored rows.

### Tools: old -> new
- old: `C` (curl)
- new: `BZ, B, C` (Burp/ZAP first, then Browser, curl)

### Burp workflow steps
1. Send the browser through Burp Proxy. Visit /http/track?ref=homepage and
   send the request to Repeater.
2. In Repeater, edit the ref value in the request line so it carries encoded
   carriage-return and line-feed bytes followed by forged log text, then
   send it. The response confirms the CR/LF bytes were written to the log.
3. Request /http/admin/log in the same Repeater session (cookies preserved)
   and confirm the forged line renders in the log viewer. The flag box
   appears once the forged line is really observed there.

### Issues
- The old `start` field was a curl one-liner, which contradicts the
  Burp-first doctrine (D16).
- The old hints said nothing about which Burp step to use.
- The old `tools` did not lead with Burp/ZAP.

### Changes applied
In `modules/http/challenges/crlf-log.js`, vuln object only:
- `tools`: `C` -> `BZ, B, C`.
- `start`: rewritten as a three-step Burp workflow (proxy the visit, edit
  ref in Repeater with encoded CR/LF bytes, open the log viewer in the same
  session); no curl one-liner.
- `hints`: nudges only, each names the Burp step (Repeater request of
  /http/track, adding encoded bytes in the request line, confirming the
  forged entry in the viewer). No exploits pasted.
- `how`: Burp-flavored rewrite ("Send CR/LF bytes inside the ref value
  (Burp Repeater request line) so a forged line renders in the admin log
  viewer").

Verified: `node --check` passes; zero em dashes in the file; scratch server
booted (DB_PATH=/tmp/burp-w146.db PORT=18146), /http and /http/track
returned 200, and the percent-encoded CRLF injection plus a same-session
log-viewer request awarded the flag; server stopped afterwards.

## 2. verb-tamper (Verb Tampering)

### Verdict
BURP-CLEAN. The exploit is a plain GET /http/feedback?msg=... instead of
the documented POST; the GET route runs the same submit handler. This is
vanilla HTTP method tampering, reproducible in Burp Repeater or even the
browser address bar. No raw sockets, no malformed HTTP, no byte tricks,
no non-HTTP protocols.

### Tools: old -> new
- old: `B` (Browser)
- new: `BZ, B, C` (Burp/ZAP first, then Browser, curl)

### Burp workflow steps
1. Send the browser through Burp Proxy. Open /http/feedback and submit the
   form, intercepting the POST.
2. Send the intercepted request to Repeater, change the method to GET, and
   move the msg parameter into the URL query string.
3. Send it and read the response. The feedback is recorded over GET and the
   flag box appears.

### Issues
- The old `start` field was a curl one-liner, which contradicts the
  Burp-first doctrine (D16).
- The old hints said nothing about which Burp step to use.
- The old `tools` did not lead with Burp/ZAP.

### Changes applied
In `modules/http/challenges/verb-tamper.js`, vuln object only:
- `tools`: `B` -> `BZ, B, C`.
- `start`: rewritten as a three-step Burp workflow (proxy the form submit,
  change the method in Repeater, move msg into the query); no curl one-liner.
- `hints`: nudges only, each names the Burp step (intercept in Proxy,
  change method plus move parameter in Repeater, replay over GET). No
  exploits pasted.
- `how`: tool-neutral tweak ("Replay the feedback submission over GET
  (move msg into the URL query) instead of POST").

Verified: `node --check` passes; zero em dashes in the file; scratch server
booted (DB_PATH=/tmp/burp-w146.db PORT=18146), /http/feedback returned 200,
and GET /http/feedback?msg=... awarded the flag; server stopped afterwards.
