# Burp audit w134: referer-bypass

## Verdict
BURP-CLEAN

## Challenge
Weak Referer Check Bypass (modules/csrf/challenges/referer-bypass.js).
POST /csrf/api/nickname changes the logged-in user's nickname only when the
Referer header contains the substring 'pentrix.lab'. Forging a Referer on an
untrusted host that merely contains that string (e.g. a foreign URL with the
trusted domain in a query parameter) passes the check and awards the flag.

## Tools: old -> new
C -> BZ, B

## Burp workflow steps
1. Open Burp Suite, set your browser to use Burp Proxy, and browse to
   /csrf/nickname.
2. Log in once as alice so the nickname POST is captured in Proxy history.
3. Send the POST /csrf/api/nickname request to Repeater.
4. Edit the Referer header by hand: craft a URL on an untrusted host that
   still contains the trusted domain string (the check is a plain substring
   match).
5. Send and read the response: the server changes the nickname and the
   response body carries the flag box (non-same-origin Referer = forgery).

## Issues
None. The exploit chain is one logged-in POST with a rewritten Referer
header, which is exactly what Repeater is for. The test asserts the
authenticated forged-Referer request returns 200 with the flag, while a
missing Referer is 403, a foreign Referer without the magic string is 403,
a same-origin Referer gets 200 with no flag, and an unauthenticated request
is 401. All plain HTTP: no raw sockets, no malformed requests, no
curl-specific behavior, no intruder scripting needed.
