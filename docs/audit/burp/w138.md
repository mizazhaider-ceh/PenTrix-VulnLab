Worker: w138 | Module: api | Challenges: rate-limit, ratelimit-xff | Date: 2026-10-19

## Challenge 1: rate-limit (Missing Rate Limiting)

### Verdict
BURP-CLEAN.

### Tools old -> new
`"P, C"` -> `"BZ, C"`.

### Burp workflow steps
1. Proxy on, capture one POST `/api/login` (JSON body, username/password) from a normal login on the `/api` page, then send the request to Intruder.
2. Get alice's correct password (the leaked user list from the exposure challenge reveals it; a Sniper run can also brute-force it, since nothing ever blocks guesses).
3. In Intruder, run a Sniper attack on the password position with a list of 14 wrong passwords. Watch the responses: `attempts` climbs, `ok` stays false, and no 429 or lockout ever appears. This is the vulnerability, visible in plain response JSON.
4. In Repeater, send the same request with the correct password as attempt 15 or later. The response JSON carries the flag.

The exploit chain is a series of standard HTTP POSTs with JSON bodies, all driven from Proxy history, Intruder, and Repeater. No raw sockets, no malformed HTTP, no timing tricks, no byte mangling, no curl-only behavior. The attempts counter is per-username and in-memory, so the 15 attempts can mix wrong and right guesses; only the final success needs the correct password.

### Issues
- `tools` listed `P, C`; Burp was not named despite the repeat-fire-and-watch flow being the textbook Intruder/Repeater use case.
- `start` was a curl one-liner (`curl -s -X POST ... /api/login`), contrary to Burp-first doctrine.
- `hints` were tool-agnostic and never named the Burp steps that make the attempt-counting flow easy to drive (Proxy, Intruder, Repeater).

### Changes applied
- `tools`: `"P, C"` -> `"BZ, C"` (Python dropped: Intruder Sniper is now the primary automated path).
- `start`: replaced the curl one-liner with a Burp-oriented starting point (proxy one login, send to Intruder, Sniper with wrong-password list for alice).
- `hints`: rewrote all three to name Burp steps (Intruder, Sniper run, Repeater) as nudges only; no exploit pastes. The final hint states the attempt-15 rule without dictating payloads.
- `how`: made Burp-flavored (Intruder for the guesses, Repeater for the final login; flag on success at 15+ attempts).
- `hint` (short field): left unchanged, it was already tool-neutral.

## Challenge 2: ratelimit-xff (Rate Limit Bypass via X-Forwarded-For)

### Verdict
BURP-CLEAN.

### Tools old -> new
`"C"` -> `"BZ, C"`.

### Burp workflow steps
1. Proxy on, capture one POST `/api/v1/login` from a normal login on the `/api` page, then send the request to Repeater.
2. In Repeater, send 4 wrong-password logins in a row and watch the responses: after the third, the server returns 429 "Too many attempts" and stays locked. The real client IP is now past the lockout, confirmed by the 429 on a correct-password attempt with no extra headers.
3. Still in Repeater, add one header (`X-Forwarded-For`) with a fresh IP address and swap in the correct password, then forward. The limit counts the spoofed identity, the login returns 200 `ok: true`, and the flag is awarded because the real IP was genuinely locked out.

The whole chain is standard HTTP in Repeater: JSON POSTs, status-code watching, and one header edit. XFF spoofing is exactly the Repeater-header-edit case named by D16. No raw sockets, no malformed HTTP, no timing tricks, no byte mangling, no curl-only behavior.

### Issues
- `tools` listed only `C`; Burp was not named despite the lockout-then-spoof flow being a pure Repeater exercise.
- `start` was a curl one-liner (`curl -s -X POST ... /api/v1/login`), contrary to Burp-first doctrine.
- `hints` were tool-agnostic and never named the Burp step that makes header spoofing trivial (Repeater header edit).

### Changes applied
- `tools`: `"C"` -> `"BZ, C"`.
- `start`: replaced the curl one-liner with a Burp-oriented starting point (proxy one login, send to Repeater, edit headers and resend at will).
- `hints`: rewrote all three to name Burp steps (Repeater header add/edit) as nudges only; no exploit pastes. The final hint describes the lockout-then-spoof order without dictating the header value.
- `how`: made Burp-flavored (lockout via bad passwords, then one Repeater header edit before resending the correct login).
- `hint` (short field): left unchanged, it was already tool-neutral.
