# Burp Audit w049: xxe-external-dtd (External DTD Exfiltration)

## Verdict
BURP-CLEAN. The full exploit chain works through standard HTTP requests that Burp Suite Community can capture, replay and modify with no special handling. The challenge is a genuine multi-step out-of-band flow: hosting a DTD on the in-lab collector, importing it through a parameter entity, and waiting for the server-side pingback to the collector log. Every step is a plain form POST (application/x-www-form-urlencoded) to `/xxe/collector/dtd` and `/xxe/dtd`, so Proxy captures both requests and Repeater replays them cleanly.

## Burp workflow
1. Proxy your browser through Burp and open GET `/xxe/collector`.
2. In the "Host your DTD" form, paste a DTD that reads the secret file into a parameter entity and declares a pingback entity pointing at `/xxe/collector/log` with the file content in the query string; submit the form.
3. In Proxy HTTP history, find the POST to `/xxe/collector/dtd` and confirm the 302 redirect; the DTD is now hosted.
4. Open GET `/xxe/dtd`, fill the XML textarea with a DOCTYPE whose external subset imports the hosted DTD URL through a parameter entity, and submit.
5. In Proxy HTTP history, find the POST to `/xxe/dtd` and send it to Repeater for iteration.
6. Reload the collector log page (`/xxe/collector`) and confirm the pingback landed with the secret in it; the import result page reports the pingback count and the flag box appears when the award gate is met.

## Issues
None blocking. Notes for the operator:
- The award gate is strict in the right way: the flag is awarded only when THIS request caused a new pingback whose `d` value carries the module secret (`oobLog` delta filtered on the secret marker). A replay of the import XML after clearing the collector also works only because the pingback refires server-side; each award still requires a real exfiltration.
- The external-DTD expander only honors double-quoted `SYSTEM` URIs, so the hosted DTD and the import XML must use double quotes. The on-page starter template already does.
- The flag box is rendered inline in the POST response (`flagBox(award(...))`) and the session is marked captured via `award()`; FLAG SECRECY holds because `award()` resolves the flag through `flagFor()`, a DB lookup. No flag literal exists in the challenge file; the `XXE-SECRET-4471` substring the gate checks is the module-secret marker from `modules/xxe/secret.txt`, not a flag.
- FLAG BAR holds: a bare request (no DTD hosted, no parameter-entity import) cannot satisfy the gate, since nothing pings the collector with the secret.
