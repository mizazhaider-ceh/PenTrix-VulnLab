## biz-refund (Tampered Refund Amount)

**Verdict: BURP-CLEAN**

The exploit chain is plain HTTP through and through. Buy the $50 hoodie via a
normal form POST to /bizlogic/refund/buy, then tamper the hidden `amount` field
in the refund POST to /bizlogic/refund and submit a value above the order total.
The server parses `application/x-www-form-urlencoded` with
express.urlencoded({ extended: false }), clamps nothing, and awards the flag
when amount > order.total. No raw sockets, no malformed HTTP, nothing
Burp normalizes away, no non-HTTP protocol.

**Tools old -> new:** `BZ, B` -> `BZ, B` (unchanged, BZ already first, B kept)

**Burp workflow steps:**
1. Start Burp Proxy and open http://localhost:3000/bizlogic/refund in the
   proxied browser.
2. Click "Buy the $50 hoodie first", an ordinary proxied POST.
3. The orders table renders a refund form with hidden fields order_id and amount.
4. Click Refund, catch the POST in Proxy, send it to Repeater.
5. In Repeater, raise the `amount` parameter above the order total and send.
   The response shows "Over-refunded" and the flag banner.

**Issues:** None blocking. The in-page text still shows a curl one-liner under
the refund table, which clashes with the Burp-first voice but lives outside the
vuln object and was left untouched per the minimal-edit rule. A follow-up could
reword it to "Try it in Repeater".

**Changes applied:**
- `tools`: kept `BZ, B` (BZ first, B kept).
- `start`: replaced the curl one-liner with a Burp-oriented starting point:
  proxy the page, buy the hoodie, send the refund POST to Repeater.
- `hints`: rewritten as Burp-step nudges (proxy the page, send the POST to
  Repeater, edit the amount in Repeater, notice it is never clamped). No
  exploit pasted.
- `how`: tool-neutral wording, "changing the hidden amount field before
  sending" instead of a curl recipe.

## biz-workflow-skip (Checkout Step Skipped)

**Verdict: BURP-CLEAN**

The exploit chain is a plain order-of-operations trick over standard HTTP.
Step 1 (cart) and step 3 (confirm) are ordinary urlencoded POSTs; the confirm
endpoint never checks that step 2 (pay) ran. Skipping a request needs no
byte-level trickery: in Repeater you simply do not send the pay request, then
send confirm. Body parsing is express.urlencoded({ extended: false }), no
raw-socket needs, nothing Burp would normalize or mangle, no non-HTTP
protocol.

**Tools old -> new:** `BZ, C` -> `BZ, B` (BZ first, C dropped, B kept as the
driving client)

**Burp workflow steps:**
1. Start Burp Proxy and open http://localhost:3000/bizlogic/workflow in the
   proxied browser.
2. Click "Step 1: add hoodie to cart", an ordinary proxied POST.
3. Catch the "Step 3: confirm order" POST in Proxy and send it to Repeater
   without ever touching the Step 2 pay button.
4. Send the confirm request from Repeater. The response shows "Free order"
   with "Payment step completed: false" and the flag banner.
   (Alternatively, record all three requests in Proxy history and replay only
   steps 1 and 3 from Repeater.)

**Issues:** None blocking. The empty-cart guard means the attacker must call
the cart step first, which is a deliberate design point, not a Burp blocker.

**Changes applied:**
- `tools`: `BZ, C` -> `BZ, B` (BZ first; B is the actual client, curl is no
  longer needed since the guide no longer references it).
- `start`: replaced the curl one-liner with a Burp-oriented starting point:
  proxy the page, add the hoodie to the cart, send the confirm POST to Repeater
  and replay it before paying.
- `hints`: rewritten as Burp-step nudges (proxy each step, replay confirm in
  Repeater, skip only the pay step). No exploit pasted.
- `how`: tool-neutral wording: POST /bizlogic/workflow/confirm directly,
  skipping the pay step entirely.
