## Burp workflow steps
1. Open Burp Suite Community, start Proxy on 127.0.0.1:8080.
2. Point your browser through the proxy and log in to the shop as bob (or alice).
3. In the browser, visit any shop page so the session cookie flows through Proxy.
4. Select the session-bearing request, right click, Send to Repeater (or open Repeater and issue GET /idor/admin with the captured session cookie).
5. Resend. The response renders the admin panel with the flag box, because the handler only checks "logged in" and never checks the role.
6. Burp note: no parameter change is needed for the core path. A classic Repeater variant is to change the path on an existing session request and resend, which is the canonical IDOR move.
7. Guest check: sending GET /idor/admin with no session cookie returns 401, confirming the panel is gated only by session existence.

## Issues
- The challenge shipped with curl-only tooling (`tools: 'B'` plus a curl one-liner `start`), which contradicted doctrine D16: every challenge must be fully solvable with Burp Suite Community (Proxy, Repeater, Intruder), and the voice must be Burp-first.
- First hint buried the Repeater step inside a curl-flavored nudge.

## Changes applied
- `modules/idor/challenges/admin.js`, vuln object only (router untouched):
  - `tools`: `B` -> `BZ, B` (Burp/ZAP first, browser kept for the login step).
  - `start`: replaced the two-line curl one-liner with a Burp-oriented starting point (Proxy on 127.0.0.1:8080, log in as bob through the proxy, send GET /idor/admin to Repeater and resend with the session cookies).
  - `hint`/`hints`: each hint now names the Burp step (Proxy, Repeater, direct request of the admin URL with a signed-in session). Nudges only, no exploit pasted.
  - `how`: now Burp-flavored: log in as a non-admin in the proxied browser, send GET /idor/admin to Repeater, resend.
