# Burp-first audit: w127 (CSTI Inside an HTML Attribute)

- Worker: w127
- Challenge: `modules/csti/challenges/attr.js` (vuln id `attr`)
- Doctrine: D16 (fully solvable via Burp Suite Community Proxy, Repeater, Intruder)

## Verdict

**BURP-CLEAN.** The full exploit chain is plain standard HTTP through a cookie session:
POST `/csti/attr` (urlencoded `tpl`), GET `/csti/attr` in the browser, and the page
auto-fires GET `/csti/beacon?v=attr&d=49&n=<page-bound nonce>` when the evaluated badge
contains 49. Burp Proxy can intercept the form POST, Repeater can experiment with the
`tpl` value, and Proxy history shows the beacon request and the flag in the response.
No raw sockets, no Burp-mangled bytes, no curl-specific behavior, no non-HTTP protocols.
FLAG BAR and FLAG SECRECY are preserved: the beacon requires the single-use page-bound
nonce rendered into the loaded page, so the template must genuinely evaluate in the
browser (or the page must be loaded) before the flag is awarded.

## Burp workflow steps

1. Configure the lab browser to use Burp Proxy. Browse to `http://localhost:3000/csti/attr`.
2. Intercept the "Save badge text" POST in Proxy and send it to Repeater. Vary the
   `tpl` value there; the response shows the value entity-encoded in the `value`
   attribute, which tells you server-side encoding is in play.
3. Save a template expression as the badge text, then reload the page in the
   browser. Proxy passes the session cookie, so the page-bound nonce stays tied to
   your session.
4. The browser runs `getAttribute('value')`, decoding the entities, and the
   client-side engine evaluates the template. When the badge renders 49, the page
   automatically fires the beacon GET `/csti/beacon?v=attr&d=49&n=<nonce>`.
5. Find the beacon request in Proxy HTTP history and open its response in
   Repeater: it contains the flag. The scoreboard marks the challenge captured.
   (Optional: Intruder can fuzz delimiter variants like `[[ ]]` for the sibling
   filter-bypass lab, but it is not needed here.)

## Issues

None blocking. The beacon fires automatically on page load once the saved badge
evaluates to 49, so no manual request crafting is required for the final step.
Session cookies are standard; nothing in the chain depends on curl-only flags or
raw socket behavior.
