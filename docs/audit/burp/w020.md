## Challenge 1: xss-js-context (XSS in a JavaScript String)

### Verdict
BURP-CLEAN.

### Tools old -> new
`"B"` -> `"BZ, B"`.

### Burp workflow steps
1. Proxy on, open `/xss/jsctx` in the Burp browser and submit the recipient-name form once normally.
2. In Proxy history, send the captured GET to Repeater. Inspect the response body: the `q` value reflects raw inside a single-quoted JS string (`var q = '...'`).
3. In Repeater, shape the `q` parameter: break out of the string with a quote and a semicolon, place a statement that fetches the `/xss/collect` beacon endpoint with the page token (`n=window.__px`, read from the fresh page load), and close the line with `//` so the leftover quote does not break the script. Plain URL encoding handles the whole payload; no raw bytes needed.
4. Load the final Repeater URL in the browser. The injected statement runs and fires the beacon with the fresh token, the claim box confirms, and the flag is awarded.

The exploit chain is one standard HTTP GET (crafted in Repeater) plus one browser page load (beacon fires from the browser). The payload is pure ASCII, carried by normal URL-encoded query parameters, so Burp neither mangles nor normalizes anything meaningful. No raw sockets, no malformed HTTP, no timing tricks, no curl-only behavior.

- `hints[2]` contained a near-complete exploit paste (explicit `fetch()` call with parameters `c`, `v=xss-js-context`, `n=window.__px` and the trailing `//`).

## Challenge 2: xss-dom-clobber (DOM Clobbering to Admin)

### Verdict
BURP-CLEAN.

### Tools old -> new
`"B, DT"` -> `"BZ, B, DT"`.

### Burp workflow steps
1. Proxy on, open `/xss/clobber` in the Burp browser and save some harmless profile HTML (e.g. `<b>hello</b>`) once normally.
2. In Proxy history, send the captured POST to Repeater. Inspect the response: the filter strips `<script>` tags but form/input markup survives and renders raw in the profile card.
3. In Repeater, shape the `html` field so the surviving markup rebuilds a truthy `window.settings.isAdmin` from DOM elements alone (e.g. a form id'd `settings` with a named control). All payload bytes are standard URL-encoded form data, so Burp sends them untouched. Burp Proxy keeps the session cookie, which scopes the stored markup per student.
4. Reload the profile in the browser so the injected markup runs, then open the admin panel link. The inline page script sees the clobbered `window.settings.isAdmin`, reveals the panel, and the server re-verifies the stored markup with its own parser before awarding the flag.

Multi-step flow is fine under D16: the POST (store) and the GET (verify) are both plain HTTP, and Proxy/Repeater maintain the session automatically. No raw sockets, no malformed HTTP, no timing tricks, no byte mangling, no curl-only behavior. No beacon is involved at all; the flag condition is server-side markup analysis of stored session state.

### Issues
- `tools` listed `B, DT`; Burp was not named despite the POST/replay/verify flow being ideal for Proxy history / Repeater.
- `start` was a curl one-liner (`curl -s ... | grep -n -A4 "<script>"`), contrary to Burp-first doctrine.
- `hints` were tool-agnostic and never named the Burp steps that make the store-then-verify flow easy to drive (Proxy, Repeater).

### Changes applied

- `start`: replaced the curl one-liner with a Burp-oriented starting point (Proxy, save test HTML, send POST to Repeater, tweak `html` while watching which tags survive, then reload the profile and open the admin panel).

- `how`: made Burp-flavored (Repeater-crafted profile-save POST, browser reload, admin panel link; flag awarded on server-side markup verification, no beacon).
- `hint` (short field): left unchanged, it was already tool-neutral.
