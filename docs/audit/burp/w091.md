# Burp-first audit w091: reset-predictable (SHA-256 Predictable Reset Token)

## Verdict

**BURP-CLEAN.** The full exploit chain runs through standard HTTP: a GET with a query
parameter, a SHA-256 computation that Burp Decoder performs natively, and a plain
form POST to the confirm endpoint. No raw sockets, no binary or non-UTF-8 bytes for
Burp to mangle (the token is hex ASCII), no protocol tricks, and no curl-specific
behavior anywhere in the chain. The flag awards only when the forged admin token is
submitted from a session that never legitimately received an admin reset, which maps
cleanly onto Repeater tabs with separate cookie jars.

## Tools

- Old: `B, P` (Browser, Python)
- New: `BZ, B, P` (Burp/ZAP first, then Browser, Python kept as fallback)

Rationale: the challenge is a token-forgery exercise. Burp is the natural primary:
Proxy to observe the recipe, Decoder to compute the SHA-256 digest, Repeater to
submit the forged confirm request. Browser stays for the confirm form; Python stays
as a hash fallback for learners who prefer scripting.

## Burp workflow (exploit chain)

1. **Proxy:** browse to `/auth/sha-reset?user=alice` and submit the reset form. Watch
   the request in Burp history; the response prints the token recipe (SHA-256 over the
   username plus a fixed string).
2. **Decoder:** feed the admin input per that recipe into Decoder and apply Hash ->
   SHA-256 to get the hex digest. Do NOT request a real admin reset link: the flag is
   only awarded when this session never legitimately received the admin token.
3. **Repeater:** POST `/auth/sha-reset/confirm` as
   `application/x-www-form-urlencoded` with `token=<forged admin digest>` and
   `newPassword=<chosen>`. The page reports "Password changed" for admin and shows
   the flag.
4. Verify by signing in as admin with the new password, or by checking the flag
   capture in Repeater's response.

Caution: keep the Repeater tab's cookies consistent with the Proxy session, and never
visit `/auth/sha-reset?user=admin`, which would mark the admin token as legitimately
issued and void the forgery.

## Issues found

- None blocking. One design note (not a defect): the "forged vs issued" distinction
  is session-based (`req.session.shaIssued`), so learners must use one Burp session
  per attempt. The guide now warns about this.
