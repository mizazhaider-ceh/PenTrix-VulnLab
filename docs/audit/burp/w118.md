# Burp Audit Verdict: wildcard (w118)

## Verdict
BURP-CLEAN

## Tools old -> new
Old: `B, DT`
New: `BZ, B, DT`

Burp/ZAP moves to first position per D16: the beacon traffic is standard HTTP that Proxy sees in full and Repeater can replay. The browser stays second because the frame-to-frame broadcast itself happens in the browser, and DevTools stays third for reading the victim's JavaScript in place.

## Burp workflow steps
1. Proxy: configure the browser to use Burp Proxy, then open the victim widget at `/postmsg/wildcard`. Find the GET response in Proxy > HTTP history and read the embedded script: it posts the per-session secret with `postMessage(data, '*')`.
2. Proxy: open the attacker page `/postmsg/wildcard/attacker` in the proxied browser. The embedded iframe loads the widget, the wildcard broadcast lands on the attacker's listener, and a beacon request `GET /postmsg/beacon?v=wildcard&d=wildcard:<token>` appears in the history. This is the exploit chain, fully visible in Proxy.
3. Repeater: send the beacon request to Repeater and replay it with the broadcast token to confirm the claim is awarded. FLAG BAR holds: replay it with a guessed token and nothing is earned, matching `tests/postmsg.test.js` (guessed secret earns nothing, real secret earns the flag). FLAG SECRECY holds: the token is a random 16-byte per-session value, never guessable.
4. Optional DevTools: on the attacker page, confirm the captured token renders in the "Captured token" card as the beacon fires.

## Issues
None found. The chain is plain same-app HTTP plus a browser postMessage hop: no raw socket control, no malformed HTTP, no timing sensitivity, nothing Burp would mangle. The wildcard origin is a server-rendered client-side flaw, so Proxy, Repeater, and the browser see it exactly as written.
