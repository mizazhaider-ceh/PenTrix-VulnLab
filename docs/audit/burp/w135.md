# Burp-first audit: api-version-bypass (w135)

## Verdict
**BURP-CLEAN.** The full exploit chain is plain HTTP GET requests with a session cookie: log in, request `/api/v1/users/3` (gets a 403), send the request to Repeater, flip the path version to v2, resend, read the leaked record and the flag. No raw sockets, no Burp-mangled bytes, no curl-specific behavior, no non-HTTP protocol. The v2 route even returns the flag in the JSON body, so no extra extraction step is needed.

## Tools
- Old: `C` (curl only)
- New: `BZ, C` (Burp/ZAP first, curl still listed as it works)

## Burp workflow
1. Start Burp, enable the Proxy, route your browser through it.
2. Browse to `http://localhost:3000/api/login/alice` to log in as alice. Find the session cookie in the response via HTTP history.
3. Browse to `http://localhost:3000/api/v1/users/3`. Note the 403 Forbidden: v1 enforces ownership.
4. Right-click that request in HTTP history and send it to Repeater (Ctrl+R).
5. In Repeater, change the path version segment (`v1` to `v2`) and hit Send.
6. Compare the two responses: v1 blocks, v2 returns the other user's full record plus the flag.

## Issues found
- `start` was a curl one-liner, which does not match the Burp-first voice required by D16.
- `tools` listed only curl even though the challenge is textbook Repeater work (API version/path tweaking).
- `hints` named no Burp step; the third hint nearly described the exploit but without the tool framing.
- No functional issues: challenge logic, flag awarding, and tests all pass unchanged. Scratch boot verified `/api` returns 200, v1 returns 403 for user 3 as alice, and v2 returns the record plus the flag.
