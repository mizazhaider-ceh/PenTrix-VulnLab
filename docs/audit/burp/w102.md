# Burp-first audit w102: session/predictable, session/url

Auditor: w102. Doctrine D16 (every challenge fully solvable via Burp Suite Community).
Both challenges are plain standard HTTP flows. No raw sockets, no Burp-mangled
bytes, no curl-specific behavior, no non-HTTP protocols.

## 1. Predictable Session IDs (session/predictable)

**Verdict: BURP-CLEAN.**

The demo page prints the user's sequential sid and the admin's sid side by side.
The admin panel checks only the `lab_sid` cookie against a per-lab store. The
whole chain is: read two integers off a page, swap one cookie value, replay.
That is textbook Repeater work (and textbook Intruder sniper/sequencer work on
the numeric cookie for the general case). Nothing about it needs curl or a
script. Flag bar and flag secrecy are untouched: the flag still awards only via
the admin cookie, and the admin's sid is still revealed only on the demo page.

**Tools old -> new:** `B, DT` -> `BZ, B, DT` (Burp/ZAP added first, browser kept).

**Burp workflow steps:**
1. Proxy: browse to `/session/predictable` and read your sid and the admin's sid in the response.
2. Repeater: send the `GET /session/predictable/admin` request, replace the `lab_sid` cookie with the admin's sid, and send.
3. (Alternative) Intruder: sniper attack on the `lab_sid` cookie value with a small numeric payload range around your own sid.

**Issues:** The old `start` was a curl one-liner (`curl -s -c jar -b jar ...`), not
Burp-first. Hints did not name the Burp step.

**Changes applied:**
- `tools`: `BZ, B, DT`.
- `start`: now points the browser at Burp, opens the demo page, and reads both sids there.
- `hints`: hint 1 names the Proxy step, hint 3 names the Repeater step (and the Intruder alternative). No exploits pasted, nudges only.
- `how`: Burp-flavored (Repeater or Match and Replace for the cookie swap).

## 2. Session ID in the URL (session/url)

**Verdict: BURP-CLEAN.**

The admin's sid lands in the shared proxy log as a full URL
(`GET /session/urldemo/home?sid=...`). The `/home` handler trusts whatever sid
arrives in the query string. The chain is: read the proxy log page, copy the
leaked URL, replay it. Proxy history and Repeater cover this entirely, and the
replay works even without logging in as anyone. Standard HTTP only. Flag bar and
flag secrecy are untouched: the flag still awards only when the leaked admin sid
reaches `/home`, and the sid is still revealed only through the proxy log page.

**Tools old -> new:** `B, DT` -> `BZ, B, DT` (Burp/ZAP added first, browser kept).

**Burp workflow steps:**
1. Proxy: browse to `/session/urldemo` and follow the proxy-log link on the page.
2. Scan the log for a `home?sid=` entry that is not yours (the admin seeded one).
3. Repeater: paste that full URL, send, and claim the flag.

**Issues:** The old `start` was a two-line curl one-liner, not Burp-first. Hints did
not name the Burp step.

**Changes applied:**
- `tools`: `BZ, B, DT`.
- `start`: now points the browser at Burp, opens `/session/urldemo`, then follows the on-page proxy log link.
- `hints`: hint 1 names the Proxy step ("Open the proxy log page through Burp"),
  hint 3 names the Repeater replay step. No exploits pasted, nudges only.
- `how`: Burp-flavored ("replay their home URL with it in Burp Repeater").
