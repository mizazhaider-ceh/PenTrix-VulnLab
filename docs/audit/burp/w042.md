## cmdi-backtick (Ping Gadget v6, `$()` blocked)

**Verdict: BURP-CLEAN**

The exploit chain is one standard GET: `/cmdi/ping6?host=<encoded payload>`. The payload characters (backtick `%60`, `$` `%24`) travel as standard percent-encoding in the query string, exactly like the tests' `encodeURIComponent` path, and Burp Repeater round-trips them identically (Decoder tab confirms what the server receives). The browser GET form encodes the same characters automatically when typed into the gadget page. No raw sockets, no malformed HTTP, no timing tricks, no non-HTTP protocol, no Burp-mangled bytes.

**Tools:** `B, C` -> `BZ, B, C`

**Burp workflow steps:**
1. Proxy the browser through Burp, open `/cmdi/ping6`, submit a normal ping.
2. Send that request from Proxy history to Repeater.
3. Edit the `host` parameter with the legacy substitution payload (percent-encoded; use Repeater's Decoder tab to confirm what the server receives).
4. Send and read the response body: the injected command's real output plus the flag box and fix panel.

**Issues:** none. No `curl --data-urlencode` quirks (GET request, query param, standard encoding on both sides).

**Changes applied:** `tools` now leads with `BZ`; `start` rewritten as a Burp Proxy/Repeater starting point (no curl one-liner); `hints` name the Burp step (Proxy, Repeater, Decoder) and are nudges only, no pasted exploit; `how` is Burp-flavored and tool-neutral.
