# w066 Burp-first audit: oauth / implicit (Implicit Flow Token in URL Fragment)

## Verdict
BURP-CLEAN. The full exploit chain is drivable through Burp Suite Community Proxy plus Repeater plus a normal browser. No step needs anything outside standard HTTP, Proxy, Repeater, or the browser. The fragment itself never goes over the wire, but the lab's client-side victim simulation POSTs the full URL, fragment included, to /oauth/client/history-log, and that POST is fully visible in Burp Proxy HTTP history. The attacker-visible history page and the userinfo claim are plain GETs that Repeater can drive.

## Tools old -> new
- Old: `B, DT` (Browser, DevTools)
- New: `BZ, B, DT` (Burp/ZAP first, then Browser, DevTools)
- Rationale: every step is Proxy/Repeater-driven, and the token recovery point is a Burp Proxy history entry. B and DT are kept because the flow starts in a real browser and the fragment is read from the address bar.

## Burp workflow steps
1. Proxy: route the browser through Burp. Open /oauth#implicit, log in as alice (the victim), click "Run the implicit flow" and approve the consent. The browser lands on the callback URL carrying #access_token=<48 hex chars> in the fragment.
2. Proxy: open /oauth/client/implicit-callback with that fragment pasted after the #. The page JavaScript reads location.hash and POSTs the full visited URL, fragment included, to /oauth/client/history-log. Find that POST in Proxy HTTP history: the fragment that never reaches the server is sitting in the request body.
3. Proxy: switch to an attacker session (fresh browser profile or cleared cookies) and open /oauth/client/history. The recorded full URL, token included, renders in the response.
4. Repeater: replay GET /oauth/idp/userinfo with the stolen access_token from the attacker session. Because the token is an implicit-grant token owned by alice while the presenting session is not alice's, the JSON response contains the flag.
5. Negative checks in Burp: the token owner's own userinfo call earns no flag, and the history page needs no session at all, which confirms the leak is real.

## Issues
1. `start` was a curl one-liner (log in plus authorize via curl). It violated the D16 Burp-first voice and skipped the browser entirely, which is the only place the fragment exists.
2. The tools tag `B, DT` named no Burp tool even though the whole chain is Proxy/Repeater native.
3. The hints and `how` were tool-neutral and generic ("Where do fragments end up?", "call userinfo with it"). They never named the Burp step where the token is actually recovered: the history-log POST in Proxy history.
4. FLAG BAR and FLAG SECRECY were already satisfied and remain so. The token is a fresh random 48-hex value minted at approval time, so the flag cannot be derived from source. The owner's own userinfo call earns nothing (covered by tests/oauth.test.js). No flag value appears in pages or in this audit.

## Changes applied
Edited only the `vuln` object in modules/oauth/challenges/implicit.js (tests/ untouched, nothing pushed):
- tools: 'B, DT' -> 'BZ, B, DT'
- start: replaced the curl one-liner with a Burp-oriented starting point (proxy the browser, run the implicit flow as alice, approve the consent, feed the fragment URL to the simulated victim browser callback, then watch Proxy history for where the token resurfaces).
- hints: rewrote the 3-step ladder to name the Burp steps: (1) find which in-lab page records the full URL and which Proxy history entry carries it, (2) lift the token from the history-log POST body in Proxy history, (3) present it to userinfo in Repeater from a non-alice session. Nudges only, no exploit text pasted.
- how: Burp-flavored one-liner.
- hint (single-line field): synced to the Burp voice.
