# Burp audit w084: bizlogic/biz-email-noreauth (Email Change Without Re-Authentication)

## Verdict
BURP-CLEAN. The full exploit chain is four plain HTTP requests against standard
urlencoded forms, all under one session cookie: GET /bizlogic/account,
POST /bizlogic/account/email (new_email), POST /bizlogic/account/forgot (email),
read the demo token from the response page, POST /bizlogic/account/reset with the
token and a new password. No raw sockets, no binary bytes Burp would mangle, no
malformed HTTP, no curl-specific behavior, no non-HTTP protocol. The token is
rendered on screen in demo mode (no email client needed). Every step maps to
Proxy, Repeater, and Target history.

## Tools: old -> new
- Old: `B` (Browser)
- New: `BZ, B` (Burp/ZAP first, Browser kept)
- Why: the chain is a classic multi-step account takeover that a tester runs by
  forwarding each form POST through Repeater; Proxy history is the natural
  session record. The browser stays useful for the initial page walkthrough and
  reading the demo token, so B stays behind BZ.

## Burp workflow steps
1. Set Burp Proxy as the browser proxy and browse to
   `http://localhost:3000/bizlogic/account`. The page shows the account email,
   a "Change email" form with no password field, and a "Forgot password" form.
2. In Proxy history find `POST /bizlogic/account/email`, right-click, Send to
   Repeater. Note the single form field `new_email`.
3. In Repeater, set `new_email` to an address you control (e.g.
   attacker@evil.com) and send. The response confirms the email changed with
   no password asked. Watch the cookie: the session is unchanged, only the
   account email moved.
4. Back in Proxy history, send `POST /bizlogic/account/forgot` to Repeater.
   Set `email` to the attacker address and send. The response is the demo
   "Reset link sent" page with the reset link and token printed on screen.
5. Copy the 32-hex-char token from the page (it is rendered in a `<code>` tag
   and inside the reset link href).
6. In Repeater, POST `/bizlogic/account/reset` with `token=<copied>` and
   `new_password=<your password>`. The response renders "Account takeover"
   with the flag banner.
7. Intruder is not required: this is a logic chain, not a brute-force job.
   The token is high-entropy (crypto.randomBytes), so guessing is out; the bug
   is the missing re-auth on the email change, not a weak token.
