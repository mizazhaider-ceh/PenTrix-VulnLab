# w124: Burp-first audit, host-cache-poison

Challenge: Cache Poisoning via Host (modules/hostheader/challenges/host-cache-poison.js)
Auditor: w124 | Date: 2026-10-19

## Verdict

BURP-CLEAN. The full exploit chain runs in Burp Suite Community with nothing but
standard HTTP.

## Multi-step flow (from the code)

1. GET /hostheader/app with Host: evil.com renders the portal page, bakes the
   attacker's Host into the absolute reset link, and stores it in pageCache
   keyed by path only.
2. GET /hostheader/app again with the normal host is served the cached copy.
   Since the visitor's host is local and the cached entry's host is not,
   award('hostheader', 'host-cache-poison') fires and the flag renders.
3. GET /hostheader/app/clear empties the cache for repeat attempts.

The test (tests/hostheader.test.js, "host-cache-poison: poisoned entry served to
a normal host earns the flag") does exactly this: clear, poison with a spoofed
Host, then fetch normally and expect the flag.

## Tools: old -> new

- old: C (curl)
- new: BZ (Burp/ZAP)

## Burp workflow steps

1. Proxy: route the lab app through Burp Proxy (or use the built-in browser).
2. Repeater: capture a GET /hostheader/app request and send it to Repeater.
3. Poison: in Repeater, rewrite the Host header to a domain you control and
   send. The response bakes your host into the cached reset link.
4. Victim: send the SAME path again, this time with the normal host restored.
   Burp sends it, the server serves your poisoned cached copy, and the page
   reports the cache poison with the flag.

No Intruder payloads, no raw sockets, no malformed HTTP, no response smuggling.
Two normal Repeater sends complete the chain.

## Issues found

None that require redesign. The Host header is one of Burp Repeater's most
trivially editable fields, and the flow is two sequential GETs to the same path,
exactly what Repeater excels at. The cache-clear link also lets a student
repeat the attack without restarting anything.
