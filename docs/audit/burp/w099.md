# Burp-first audit: w099, fixation (Session Fixation)

- Module: session
- Challenge file: `modules/session/challenges/fixation.js`
- Routes: `GET /session/fixation`, `GET /session/fixation/preset`, `POST /session/fixation/login`

## Verdict

**BURP-CLEAN.** The full exploit chain works with plain, standard HTTP through Burp Proxy and Repeater. Step 1 is a GET that returns `Set-Cookie: lab_sid=attacker123`. Step 2 is a normal form POST to the login endpoint carrying that cookie. No raw sockets, no malformed HTTP, no timing dependency, no byte mangling, no curl-specific behavior, no non-HTTP protocol. Community edition is enough. Cookie jar manipulation (fix the sid, reuse it on login) is core Burp Proxy and Repeater work.

## Tools

Old: `B, DT` (Browser, DevTools)
New: `BZ, B, DT` (Burp/ZAP first, then Browser, DevTools)

Burp is the natural tool here because the whole attack is cookie jar work: fix the sid via the preset link, then replay the login POST in Repeater with the fixed cookie attached. Browser stays for the attack console UI; DevTools stays as a secondary way to set the cookie.

## Burp workflow steps

1. Proxy: open `http://localhost:3000/session/fixation`. The console shows the attacker's step 1 link: "Set my session cookie to sid=attacker123".
2. Proxy: click the preset link. In Proxy HTTP history, find `GET /session/fixation/preset` and note the `Set-Cookie: lab_sid=attacker123` response header (302 back to the console).
3. Proxy: submit the login form on the console as admin (the page suggests the credentials). In Proxy HTTP history, find `POST /session/fixation/login`.
4. Repeater: send that login POST to Repeater. Make sure the `Cookie: lab_sid=attacker123` header is attached, then replay it. The response renders "Session fixation confirmed" plus the flag box, because the pre-login sid was kept after authentication instead of being regenerated.
