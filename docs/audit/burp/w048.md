# Burp Audit w048: xxe-billion-laughs (Billion Laughs, Entity-Expansion DoS)

## Verdict
BURP-CLEAN. The full exploit chain works through standard HTTP requests that Burp Suite Community can capture, replay and modify with no special handling.

## Tools
old: `C` (curl)
new: `BZ` (Burp/ZAP)

Rationale: the challenge is a single HTTP POST with an `application/x-www-form-urlencoded` body to `/xxe/billion`. Burp Proxy captures the form submit, Repeater edits the `xml` field, and the response page reports parse time and expansion size directly. Curl is no longer needed as a primary tool.

## Burp workflow
1. Proxy your browser through Burp and open GET `/xxe/billion`.
2. Fill the XML textarea with benign input (e.g. `<data>hello</data>`) and submit the form.
3. In Proxy HTTP history, find the POST to `/xxe/billion` and send it to Repeater.
4. In Repeater, replace the `xml` parameter with a nested entity cascade: define `lol`, then levels where each level references the previous one many times (`lol2`, `lol3`, ...), and reference the top level once in the document body.
5. Send the request. The result page shows parser busy time and expanded output size.
6. Tune the cascade depth and repeat count until the parse crosses the time threshold (1500 ms) or the size threshold (5 MB). The flag box and fix panel appear in the response when the award gate is met.

## Issues
None blocking. Notes for the operator:
- The award gate has two independent triggers (elapsed > 1500 ms OR expansion > 5000000 chars), plus `<!ENTITY` and `&\w+;` sanity checks on the input, so fast hardware cannot flake the flag: a 12 MB expansion from ~525 input chars crosses the size gate regardless of machine speed.
- Input cap is 3000 characters, enforced server-side with a clear error page; the classic lol-to-lol7 shape fits (test payload is ~525 chars).
- Repeater sends the `&` characters inside the URL-encoded body untouched, so entity references survive Burp processing with no mangling.
