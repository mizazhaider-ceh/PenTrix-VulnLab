# w006 verdict: order-by, groupby-having

## order-by (ORDER BY Injection)

- **Verdict:** BURP-CLEAN
- **Tools old -> new:** `B, C` -> `BZ, B, C`
- **Burp workflow steps:**
  1. Proxy: set Burp Proxy on, open `/sqli/sort` in the browser, submit the sort form once.
  2. Repeater: send the captured GET request to Repeater. Probe `sort` with benign values first (`price DESC`, then `2`) to confirm the parameter flows into ORDER BY.
  3. Repeater: inject a `CASE WHEN` expression with a subquery against the users table into `sort`. Sort by one column when the condition is true and another when false. The product row order flips with each true/false answer, which is the oracle.
  4. Intruder: feed candidate guesses (positions, character values) into a Sniper attack and watch the row order in each response to read the admin secret one position at a time.
  5. When the oracle executes cleanly against the users table, the flag is awarded.
- **Issues:** none. The injection is a plain GET query parameter. No malformed bytes, no raw-socket need, no timing, nothing Burp would normalize. Verified live: `GET /sqli/sort?sort=...` returns 200 and the `CASE WHEN ... THEN name ELSE price END` payload against the users table awarded the flag over HTTP (tested via curl as a Repeater stand-in). The `stripSqlNoise` guard correctly blocks keyword smuggling via string literals or comments, so only a real oracle earns the flag.
- **Changes applied:**
  - `tools`: `BZ, B, C` (Burp first).
  - `start`: Burp Proxy workflow, no curl one-liner.
  - `hints`: rewritten to name the Burp step (Proxy capture, Repeater oracle, Intruder sweep); nudges only, no exploit literals.
  - `how`: Burp-flavored (`Repeater` oracle, `Intruder` sweep).
- **Redesign proposal:** not needed.

## groupby-having (GROUP BY Injection)

- **Verdict:** BURP-CLEAN
- **Tools old -> new:** `B, C` -> `BZ, B, C`
- **Burp workflow steps:**
  1. Proxy: set Burp Proxy on, open `/sqli/stats` in the browser, submit the group form once.
  2. Repeater: send the captured GET request to Repeater. Confirm `by` works with `region`, then `product`, to see the grouping key echoed in the first column.
  3. Repeater: replace `by` with a subquery expression aimed at the users table. GROUP BY accepts any expression, and the page prints the grouping key back, so the admin secret itself becomes the group label.
  4. Read the secret straight from the stats output; one request is enough, no guessing loop.
- **Issues:** none. Plain GET query parameter, URL-encodable in Repeater, single request, deterministic response. Verified live: `GET /sqli/stats?by=region` returns 200 and the subquery payload against the users table awarded the flag over HTTP (tested via curl as a Repeater stand-in). The flag check requires the real secret to appear in the echoed group key, so benign groupings earn nothing.
- **Changes applied:**
  - `tools`: `BZ, B, C` (Burp first).
  - `start`: Burp Proxy workflow, no curl one-liner.
  - `hints`: rewritten to name the Burp step (Proxy capture, Repeater expression swap); nudges only, no exploit literals. The old hint 2 contained a payload-shaped fragment (`(SELECT secret FROM users...)`); that is gone.
  - `how`: Burp-flavored (Repeater points the GROUP BY expression at the users table).
- **Redesign proposal:** not needed.
