## Burp workflow steps
1. Proxy: configure the browser to use Burp Proxy, then open `/sqli/shop` and submit an ordinary search (e.g. `hoodie`). Confirm the request appears in the HTTP history and the results table renders.
2. Repeater: send the intercepted GET request (the `q` parameter) to Repeater. Try a plain `UNION SELECT` and confirm the filter strips it, no rows leak the admin secret.
3. Repeater (bypass): reshape the blocked keyword in Repeater, one variant at a time, and watch the response table. Case and comment tricks are the natural shapes to try.
4. Intruder (optional): mark the search term as a payload position and fuzz many keyword shapes quickly (Sniper attack). This is where the filter-bypass payloads shine as Intruder fodder.
5. Once a shape survives the filter, extend the query to UNION against the users table and pull the admin secret into the results table. The page awards the flag when the secret renders.

## Issues
None found. The whole chain is plain HTTP GET traffic through standard query parameters: no raw socket control, no malformed HTTP, no timing sensitivity, no byte-exact payloads that Burp would mangle. URL-encoded payloads survive Proxy, Repeater, and Intruder unchanged. The blocklist runs on the server after Burp delivers the request, so the filter bypass logic is unaffected by Burp's normalization.
