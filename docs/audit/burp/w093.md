# w093 Burp-first audit: support-impersonate, user-enum

Branch: main. Repo: ~/workspace/pentrix-vulnlab. Both challenges are plain HTTP
request/response work with no raw-socket, byte-mangling, or curl-specific
behavior, so both are fully solvable in Burp Suite Community.

## 1. support-impersonate (Support Ticket Impersonation)

- **Verdict:** BURP-CLEAN
- **Tools old -> new:** 'B, C' -> 'BZ, B'
- **Burp workflow:**
  1. Proxy: browse to /auth/support and submit a ticket number once so the
     GET request with the `ticket` query parameter is captured.
  2. Repeater: send the request there and step through ticket numbers around
     the recent range stated on the page (1001-1005). Each valid ticket signs
     you in as its owner, with no staff check.
  3. Intruder (optional full sweep): set a sniper payload position on the
     ticket value, load a numbers payload over the recent range, and look for
     the response that says "Acting as admin". The flag renders in that
     response; the settings page then confirms the admin session.
- **Issues:** None for Burp. The endpoint reads the ticket with a plain
  `parseInt` on a query parameter and renders the flag on a normal HTML page,
  so nothing in the chain needs raw sockets or exact-byte control.
- **Changes applied:**
  - `tools`: 'B, C' -> 'BZ, B' (BZ first, B kept)
  - `start`: replaced the curl one-liner with a Burp-oriented starting point
    (open the desk through the proxy browser, submit once, send to Repeater)
  - `hints`: rewritten as Burp-step nudges (Repeater walk, Intruder numbers
    payload); no exploits pasted
  - `how`: now Burp-flavored ("Walk the sequential ticket numbers at
    /auth/support/login in Burp Repeater or Intruder until a response lands an
    admin session.")

## 2. user-enum (Username Enumeration)

- **Verdict:** BURP-CLEAN
- **Tools old -> new:** 'B, C' -> 'BZ, B'
- **Burp workflow:**
  1. Proxy: open /auth/enum-login, submit the form once with a guess so the
     POST is captured in the proxy history.
  2. Intruder: send the login POST there, set a sniper payload position on the
     username field only, and load a short candidate wordlist.
  3. Discriminator: valid usernames return "Wrong password for user ..."
     while unknown ones return "... not found.", so add grep-match rules for
     the two error phrases (and sort by response length) to spot confirmed
     usernames in the results table.
  4. Claim: POST the confirmed username to /auth/enum-submit in the same
     browser session (the server records confirmations per session), and the
     flag renders on the result page.
- **Issues:** None for Burp. Both messages are plain HTML responses to a
  standard form POST; the only session nuance is that the submit must happen
  in the same session as the enumeration, which Burp handles via its normal
  cookie jar, and hint 3 now says so.
- **Changes applied:**
  - `tools`: 'B, C' -> 'BZ, B' (BZ first, B kept)
  - `start`: replaced the curl one-liner with a Burp-oriented starting point
    (open through the proxy browser, submit once, send the POST to Intruder)
  - `hints`: rewritten as Burp-step nudges (compare two responses, sniper
    over the username field, grep-match the error phrases, submit in the same
    session); no exploits pasted
  - `how`: now Burp-flavored ("Sniper through candidate usernames at
    /auth/enum-login in Burp Intruder, spot the valid ones by their different
    response, then submit a confirmed username in the same session.")
