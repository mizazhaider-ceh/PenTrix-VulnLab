# Burp Audit w055: upload / upload-double-ext (Extension blacklist bypass)

## Verdict

BURP-CLEAN. The exploit chain is a plain HTTP POST with a query parameter and
a raw request body, followed by a plain GET. Every step works in Burp
Community with only standard tools: Proxy to capture the upload POST, Repeater
to tweak the ?filename= value and the raw body, and the browser to open the
returned /upload/view/ link. No raw sockets, no malformed HTTP, no timing
tricks, no byte mangling, no curl-specific behavior, no non-HTTP protocol.

## Tools old -> new

`C` -> `BZ, C` (Burp/ZAP first, curl second).

## Burp workflow steps

1. Proxy the lab (e.g. http://localhost:3000) in Burp and browse to /upload.
2. Submit the v3 ext-blacklist upload form and send the captured POST to
   Repeater.
3. In Repeater, change only the ?filename= value: pick a name whose final
   extension passes the blacklist but whose full name still contains a
   dangerous extension segment.
4. Set the request body to SVG markup (raw bytes) and forward the request.
5. The response page hands back a /upload/view/ link: open it in the browser
   and confirm the file is served back as image/svg+xml or text/html.
6. The flag is awarded on the successful upload response when the stored name
   matches the double-extension pattern.

## Issues

One metadata issue found and fixed. The single `hint` string (not touched by
the prior worker's rewrite) claimed the same bypass shape works by smuggling
`shell.php.jpg` or using `.phtml`. That is off-topic for this challenge: the
award regex requires a `.svg.` / `.html.` / `.htm.` segment in the stored
name, and this lab has no PHP execution, so `.phtml` awards nothing here (the
vector is stored XSS via SVG/HTML). Fixed the hint to be on-topic.
