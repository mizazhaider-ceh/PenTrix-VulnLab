# Burp audit w071: jwt/aud-bypass (Audience Not Validated)

## Verdict
BURP-CLEAN. The full exploit chain is plain HTTP form traffic: a GET that renders
the signed partner token in the page, then a POST of that token to the login form.
No raw sockets, no binary bytes Burp would mangle, no curl-specific behavior, no
non-HTTP protocol. Every step maps to Proxy, Repeater, and Burp Decoder.

## Tools: old -> new
- Old: `B, C` (Browser, curl)
- New: `BZ, N` (Burp/ZAP first, Node/JWT kept as a helper)
- Why: the token copy-and-replay is Repeater work; Node is genuinely useful for
  forging custom aud claims with jsonwebtoken, so N stays. Curl is no longer
  needed as a starting point, so C drops.

## Burp workflow steps
1. Set Burp Proxy as the browser proxy and browse to
   `http://localhost:3000/jwt/aud`. The challenge page shows a signed partner
   token minted for `billing-service` with an admin role.
2. Copy the partner token from the page (the payload block has a Copy button).
3. Submit the login form once with anything in it. In Proxy history, find
   `POST /jwt/aud/login`, right-click, Send to Repeater.
4. In Repeater, paste the copied partner token over the `token` field and send.
5. Response renders the "Welcome, admin" page with the flag. The note under it
   names the accepted audience (`billing-service`), proving the aud claim was
   never validated.
6. Decoder (optional, for the JWT claim reading): paste the token into Burp's
   Decoder, use the JWT decode tab, and confirm the payload's `aud` is
   `billing-service` while the signature still verifies, that is the bug.
7. Intruder is not required; this is a single-token replay, not a fuzzing job.
