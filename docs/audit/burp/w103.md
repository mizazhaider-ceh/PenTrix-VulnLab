## Burp workflow steps

1. In Burp, open the built-in browser (Proxy tab, Open browser) and navigate to
   the Palette theme picker at `/proto/client`. Confirm the request appears in
   Proxy HTTP history.
2. Right-click the request and Send to Repeater. Study how the page parses the
   query string: the demo form and the "Try it" link show the nested-parameter
   syntax the parser expects.
3. In Repeater, add a nested query parameter whose path reaches the shared
   prototype's theme key, with any CSS color value other than the default.
   Send it and confirm a 200 response (the server just serves the page; the
   pollution is client-side).
4. Copy the crafted URL and load it in Burp's built-in browser (or any browser
   routed through Burp Proxy). The page's JavaScript runs the naive merge,
   reads the polluted theme from a fresh `{}`, and renders it in the theme box.
5. The page automatically reports the reflected theme to
   `/proto/client/claim`, which returns the flag. Read the flag from the claim
   response in Proxy HTTP history (or the rendered "Pollution demonstrated"
   page).
6. Optional check: request the claim endpoint directly with a theme value to
   see its 400 rejection behavior for empty/default themes.

## Issues

- FLAG BAR note, not a Burp blocker: the claim endpoint awards the flag to any
  request carrying a non-default theme value, so a plain Repeater GET to
  `/proto/client/claim?theme=<value>` also scores. This keeps the challenge
  solvable through Repeater alone (even without a browser), which is fine for
  D16, but the challenge's "demonstration" requirement rests on the browser
  redirect, not on server-side proof of pollution. If a future iteration wants
  to harden FLAG SECRECY, the claim could require a signed token minted when
  the polluted page actually renders, but that is a design choice, not a Burp
  blocker.
- No Burp-specific issues found: no binary payloads, no chunked smuggling, no
  header tricks Burp normalizes, nothing curl-specific in the original notes.
