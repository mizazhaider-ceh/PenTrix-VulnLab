# Burp-first audit: w141, redos/redos-username (Nested Quantifier Username)

## Verdict
BURP-CLEAN. The challenge is a single GET to `/redos/username?username=<input>` tested against the catastrophic pattern `^(a+)+$`; past 1000 ms of wall-clock time the page awards the flag. Nothing about the chain needs raw sockets, curl-specific behavior, or non-HTTP protocols: Proxy captures the form submit, Repeater tunes the input length, and the whole payload is plain ASCII in a query string that Burp never mangles. No redesign needed; only the vuln metadata needed Burp-first wording. Changes applied to modules/redos/challenges/redos-username.js only; router and flag logic untouched.

## Tools: old -> new
- Old: `B, C`
- New: `BZ, B, C`

## Burp workflow steps
1. Browser + Proxy: browse to /redos/username with Burp intercepting, submit the check form with any username, and send the request to Repeater.
2. Repeater: read the pattern off the page (`^(a+)+$`). The server shows both the pattern and the measured time in the result page, so Repeater's response view doubles as the timing oracle.
3. Repeater: fill the username parameter with a long run of the one character the pattern wants, then break the match with a final character it rejects. Increase the run length until the response time crosses 1000 ms.
4. Repeater: confirm the "Denial of service demonstrated" result and read the flag from the flag bar. The result page prints the exact milliseconds, so you can tune up or down against the cap of 30 characters.
5. Intruder (optional): put a payload position over the run length or sweep a small numeric set to find the minimum length that crosses the threshold on this machine.

## Issues found
1. Metadata was curl-first: `tools` was "B, C" and `start` was a curl one-liner, contradicting the Burp-first lab voice (D16).
2. The `hints` array named no Burp step: it described catastrophic backtracking in the abstract, so a student following the lab voice got no pointer toward Proxy/Repeater.
3. The `how` read as tool-neutral but machine-first ("if your machine is very fast"); reworded so the check is the response the student actually sees in Repeater.
4. No functional issues: the threshold, the 30-char cap, the 500-char server-side slice, and the 400 on over-length inputs all behave exactly as tests/redos.test.js (the benign-vs-evil test) relies on.

## Changes applied (modules/redos/challenges/redos-username.js, vuln metadata only; router untouched)
- `tools`: "B, C" -> "BZ, B, C" (BZ first).
- `start`: replaced the curl one-liner with a Burp-oriented start: browse the page with the Proxy on, submit the check form, send the request to Repeater.
- `hints`: rewritten to name the Burp steps (send the check request from Proxy to Repeater; tune the input length in Repeater; watch the response time in Repeater). Nudges only, no exploit pasted, no exact input length given.
- `how`: Burp-flavored, tool-neutral: in Repeater, submit the a-run plus a trailing breaking character, adding more up to the cap if the response comes back fast.
