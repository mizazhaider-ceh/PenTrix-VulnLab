## ssrf-redirect (Open-redirect SSRF)

- Verdict: BURP-CLEAN
- Tools: C -> BZ, C
- Burp workflow: Browse to http://localhost:3000/ssrf/fetch3 through Burp Proxy and submit any URL in the HopFetch form. Send the intercepted GET /ssrf/fetch3?url=... request to Repeater. In Repeater, first confirm /ssrf/jump?to=/ssrf/internal/status answers 302 (the open redirect works). Then change the url parameter of /ssrf/fetch3 to the full /ssrf/jump address aimed at the internal secret and send again. The server-side fetcher follows the 302 to the blocked host with no second blocklist check, and the rendered page shows the flag.
- Issues: none. The whole chain is two well-formed GET requests with plain query parameters; nothing raw-socket, no malformed HTTP, no timing, no bytes Burp would mangle.
- Changes applied: tools set to BZ, C. start now describes the Proxy capture plus Repeater workflow (confirm 302, then swap the url parameter), no curl one-liner. hints name the Burp steps (Proxy the form submission, send to Repeater, confirm the 302, set the url parameter to the /ssrf/jump address) as nudges only, no pasteable exploit. how reworded to Burp-flavored Repeater GET.

## ssrf-userinfo (Userinfo bypass)

- Verdict: BURP-CLEAN
- Tools: C -> BZ, C
- Burp workflow: Browse to http://localhost:3000/ssrf/userinfo through Burp Proxy and submit any partner URL in the VendorPulse form. Send the intercepted GET /ssrf/userinfo?url=... request to Repeater. In Repeater, submit a URL with no trusted string and read the 403, then submit one where the trusted string sits anywhere in the URL and see it pass. Finally, in Repeater, put the trusted name before @ and the loopback target after it in the url parameter: the raw-string allowlist passes while the URL parser connects to the host after @, and the page renders the internal secret plus the flag. The @ is URL-encoded in the parameter value (%40) by Repeater's parameter editor, which the server decodes normally.
- Issues: none. Standard GET with a single query parameter; the userinfo trick relies on URL parser semantics, not on byte-level tricks Burp would normalize. Repeater's parameter editor URL-encodes the @ correctly.
- Changes applied: tools set to BZ, C. start now describes the Proxy capture plus Repeater experimentation (observe the 403, then bypass), no curl one-liner. hints name the Burp steps (Proxy the submission, send to Repeater, read the 403, exploit the @ parsing in the url parameter) as nudges only, no pasteable exploit. how reworded to Burp-flavored Repeater GET.
