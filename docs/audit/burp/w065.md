# Burp-first audit: w065 code-replay (Authorization Code Replay)

## Verdict: BURP-CLEAN

The exploit chain is a textbook Repeater replay: one standard
application/x-www-form-urlencoded POST to /oauth/idp/token, sent twice
with the same session cookie. No raw sockets, no malformed HTTP, no
Burp-mangled bytes, no curl-specific behavior, no non-HTTP protocol.

## Tools

- Old: C (curl only)
- New: BZ, C (Burp/ZAP first, curl kept as the alternative)

## Burp workflow steps

1. Proxy: in the browser, open /oauth/login/bob (sets the IdP session
   cookie), then /oauth/idp/authorize?client_id=pentrix-spa&redirect_uri=...
   with response_type=code, and submit the approval form. The IdP shows the
   redirect target containing the 32-hex-char code; copy it.
2. Repeater: build POST /oauth/idp/token with
   client_id=pentrix-spa&code=<code> in the body and the session cookie
   from the proxy history. Send once, confirm a 200 with an access_token.
3. Repeater again: send the identical request unchanged. The second 200
   returns a different access_token plus the flag field.
4. Compare the two responses: two distinct valid tokens from one code,
   proving the code was never invalidated.

## Issues

- None found. The award condition (rec.uses >= 1 on a direct exchange of
  an owned code) fires on the second identical request, which is exactly
  what a Repeater resend produces.
- The code is plain 32-char hex: no special bytes for Burp to normalize
  or mangle, and no anti-replay logic that would distinguish a Burp send
  from a curl send.
