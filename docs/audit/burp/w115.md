# Burp-first audit: w115, postmsg/csrf-action (Privileged Action via Forged Message)

## Verdict

**BURP-CLEAN.**

## Reasoning

The exploit is browser-driven (postMessage into an iframe), but every part of the
attack chain is ordinary HTTP plus a normal browser action, all fully stageable
with Burp Suite Community Proxy plus a browser:

- The victim page (`GET /postmsg/csrf-action`) and the attacker page
  (`GET /postmsg/csrf-action/attacker`) are plain HTTP GETs. Burp Proxy
  intercepts them; the victim's message-listener source is readable in the
  Proxy history response to learn the exact message shape (`action:
  'delete-account'`), no origin check.
- The forged message is delivered by the attacker's "Fire payload" button in
  the browser (or any console line). The delivery itself is a same-document
  browser operation, but the setup and the consequences are all HTTP and
  visible in Burp.
- The victim's own script then issues `POST /postmsg/csrf-action/delete`
  (sets `pm_deleted` in the session) and the beacon
  (`GET /postmsg/beacon?v=csrf-action&...`). Both requests appear in Proxy
  history and can be replayed in Repeater.
- FLAG SECRECY verified live: a fresh session's beacon returns 400 before any
  deletion; only a real session-state deletion makes it 200 with "Exploit
  confirmed" and the scoreboard entry "Privileged Action via Forged Message".

No raw sockets, no Burp-mangled bytes, no curl-specific behavior, no
non-HTTP protocol is needed. D16 holds: solvable via Proxy (+ Repeater for
replay/observation) and a standard browser.

## Tools: old -> new

- Old: `B, DT`
- New: `BZ, B, DT`

BZ leads (Proxy to intercept victim/attacker pages and the delete+beacon
requests; Repeater to replay them). B and DT stay: the browser hosts the
attacker page and DevTools is the natural place to inspect the listener and
fire the forged message.

## Burp workflow (how an auditor solves it with Burp)

1. Set the browser to proxy through Burp (Suite Community).
2. Visit the victim settings page (`/postmsg/csrf-action`). In Proxy history,
   read the response: the `message` listener calls the delete endpoint for
   `e.data.action === 'delete-account'` with no origin check and no
   confirmation.
3. Visit the attacker page (`/postmsg/csrf-action/attacker`). It embeds the
   victim in an iframe and has a "Fire payload" button. Click it (or craft the
   forged message in DevTools console; both stay inside the browser).
4. Watch Proxy history: the victim's script issues
   `POST /postmsg/csrf-action/delete`, then the beacon. Send both to
   Repeater to confirm they are plain session-carried HTTP.
5. The beacon response is the flag award; the scoreboard flips to captured.
